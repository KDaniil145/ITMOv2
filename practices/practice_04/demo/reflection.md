Отчёт по Практике 4

1) Разбор готового TDD skill
- Skill нужен для строгого TDD: сначала пишем минимальный тест и смотрим его падение, затем добавляем минимальную реализацию и только потом рефакторим. Внутри — Iron Law (нет кода без падающего теста), цикл Red‑Green‑Refactor, правила хороших тестов и ссылка на writing-good-tests.md. Также подчёркнут запрет на «моки ради моков» и требование видеть красный и зелёный прогон полного набора тестов. На фичах A и B skill применялся так: писали минимальные падающие тесты, затем минимальный код и гоняли make test.

2) Рефлексия по практике
- Помогли: чёткие правила из AGENTS.md, минимальный объём кода, жёсткий цикл TDD и сам skill, который держит фокус на поведении.
- Влияние артефактов: AGENTS.md задавал рамки изменений и проверки; Context7 использовали для актуальной документации по инструментам/библиотекам; TDD skill дисциплинировал порядок шагов. Hook работал так:
  - не запрещает коммиты и не предотвращает изменения в неправильном worktree;
  - отслеживает изменения service.py и test_service.py и автоматически запускает make test;
  - возвращает PASS или FAIL, но успешный тест не гарантирует, что агент работал в правильной директории.
- Случай из практики: OpenCode сообщил об успешной реализации фичи B, но изменил worktree A. Ошибку обнаружили не через hook, а независимой проверкой git status и git diff. Изменения перенесли патчем в worktree B и самостоятельно проверили тесты. Вывод: результаты AI‑агента нужно проверять по реальным файлам и командам, а не только по его отчёту.
- Subagent указал на устаревшие инструкции в AGENTS.md; это учли при выполнении шагов и сверке поведения.
- Собственный MCP проверяли через FastMCP Client на корректном и ошибочном весе; реальный вызов клиента подтверждён, а прямые вызовы MCP самим агентом пока подтверждены только текстовым отчётом.

3) Краткое объяснение выбранных инструментов
- Context7 — для обращения к свежей документации по библиотекам/CLI и уточнениям синтаксиса/правил без устаревших знаний.
- TDD skill — чтобы удерживать процесс «тест вперёд», фиксировать правильные причины падения и не усложнять реализацию сверх требований.
- Hook — чтобы автоматически запускать make test при изменениях service.py и test_service.py и видеть PASS/FAIL; он не блокирует коммиты и не гарантирует работу в нужном worktree.
- Собственный MCP — чтобы вынести функцию choose_belt наружу как инструмент, проверить интеграцию и воспроизвести поведение сервиса через FastMCP.
