# Согласованная спецификация Kanban UI TaskFlow — v2

**Дата:** 2026-10-30. **Статус:** согласованная редакция UI по принятому пакету Q1–Q10/R1–R6; спецификация будущего поведения, не отчёт о реализации.

Основания: [неизменяемая UI v1](spec.md), [единый API-контракт](../../docs/sdd/kanban-api-contract.md), [итоговые решения](../../docs/sdd/kanban-decisions-final.md), [конституция](../../.specify/memory/constitution.md). Исторический серверный снимок: [Backend v1](../002-kanban-backend/spec.md); расхождения с ним разрешаются единым контрактом, а не копируются в UI.

API-контракт — единый источник истины для моделей, HTTP, нормализации, порядка валидации и кодов ошибок. Ниже описаны их пользовательские последствия и приёмка, без дублирования полного контракта и проектирования backend/SQLite. Документ не запускает планирование, задачи или реализацию; эти этапы требуют отдельного разрешения и соблюдения конституции.

## Пользовательские сценарии и проверка

### S1 — Доска и просмотр задачи (P1)

**Цель:** увидеть распределение работы и полные сведения задачи. **Независимая проверка:** подготовленная доска без использования формы создания.

1. При открытии приложения сразу видны заголовок, «Создать задачу», колонки «К выполнению», «В работе», «Готово», их счётчики и соответствующие карточки. Kanban-доска — единственный экран; отдельных разделов, навигации по ним и заглушек нет. После F5 доска остаётся стартовым экраном.
2. Карточка показывает название, описание до трёх строк с признаком сокращения, текстовый приоритет и локализованный срок. Пустое описание обозначается «Без описания», null-срок — «Без срока». Полное название и описание доступны в просмотре; длинные непрерывные строки не расширяют страницу.
3. При открытии карточки загружается актуальная задача; просмотр показывает полные пользовательские поля и действия «Редактировать», «Переместить», «Удалить», «Закрыть». Ожидание и ошибка чтения различимы; 404 обрабатывается по S6. Текст выводится безопасно как текст, без исполнения разметки.
4. После закрытия фокус возвращается на исходную карточку; если она отсутствует — на следующую карточку или заголовок исходной колонки. Фоновое обновление не перехватывает фокус.
5. Порядок карточек соответствует серверному created_at ASC, id ASC при группировке по статусу. Редактирование ключ не меняет. После создания, переноса и обновления страницы нет временного помещения в конец с последующей перестановкой. Проверяются различие времён только в микросекундах, одинаковые времена и откат часов.

### S2 — Создание и изменение (P1)

**Цель:** записывать и уточнять планы без потери введённых данных. **Независимая проверка:** создание на пустой доске; редактирование отдельно на подготовленной задаче.

1. Форма содержит подписанные название, описание, статус, приоритет и срок; обязательность названия обозначена. Начальные значения: «К выполнению», «Средний», пустое описание, отсутствие срока. Можно создать сразу в любом из трёх статусов, в том числе «Готово», с любым приоритетом.
2. При корректном вводе первая отправка создаёт одно намерение с клиентским UUID и исходным POST по S7. После 201 или допустимого 200-повтора принимается полная серверная Task, форма закрывается, карточка и счётчики обновляются, успех объявляется. Повторное открытие доски показывает сохранённую задачу.
3. При пустом/пробельном названии, превышении длины, недопустимом тексте или дате форма остаётся открытой, ошибки связаны с полями, фокус установлен на первом ошибочном поле в порядке формы. Ограничения длины показаны рядом с полями и совпадают с контрактом; серверная валидация остаётся обязательной.
4. Редактирование начинается с актуальных значений и версии. PATCH передаёт ожидаемую версию и изменяемые пользовательские поля; очищенный срок становится null, описание — пустой строкой. Пропущенные поля сохраняются. Успех отображается по полному ответу, включая нормализованный текст и новую версию. Неизменённую форму можно закрыть без запроса; PATCH только с version не отправляется.
5. При несохранённых изменениях отмена, закрытие или Escape предлагают продолжить редактирование либо явно отбросить черновик. Неизменённая форма закрывается сразу. Ошибка не считается согласием на потерю черновика. Если POST уже отправлен и исход неизвестен, закрытие формы не отменяет серверную операцию и не удаляет незавершённое намерение.
6. При отказе записи черновик остаётся доступен; при неизвестном результате показано «Не удалось подтвердить сохранение», без объявления успеха или доказанного неуспеха. Повтор возможен только по S6–S7, не вслепую.

### S3 — Перемещение между колонками (P1)

**Цель:** менять этап работы без изменения содержания задачи. **Независимая проверка:** подготовленная задача в каждой исходной колонке.

1. Перетаскивание выделяет допустимую цель; после подтверждённого PATCH статуса с ожидаемой версией карточка находится ровно в одной целевой колонке, счётчики обновлены. Все переходы свободны, включая возврат из «Готово»; срок и приоритет не ограничивают переход.
2. Действие «Переместить» с выбором статуса обеспечивает тот же результат клавиатурой и касанием без перетаскивания. Отмена или бросок в исходную колонку ничего не меняют.
3. Карточка занимает место в серверном порядке, а не место броска. После успешного переноса целевая колонка объявляется, карточка получает фокус и при необходимости прокручивается в видимую область, в том числе на мобильном экране.
4. Во время ожидания повторные действия над этой задачей блокируются, остальные задачи доступны. При обычном отказе остаётся последний подтверждённый локальный снимок. 404, 409 и неизвестный исход не обещают неизменность сервера и обрабатываются по S6.

### S4 — Удаление (P2)

**Цель:** убрать ненужную задачу без случайной потери. **Независимая проверка:** подготовленная задача, отдельно отмена и отказ сервера.

1. «Удалить» открывает подтверждение с названием, предупреждением о необратимости, «Отмена» и «Удалить»; начальный фокус на отмене. Отмена сохраняет задачу.
2. После подтверждения DELETE использует ожидаемую версию. На 204 карточка исчезает, счётчик уменьшается, результат объявляется; JSON у пустого ответа не разбирается. Фокус переходит к следующей карточке или заголовку колонки.
3. Обычный отказ оставляет последний подтверждённый снимок и возможность отменить/повторить после устранения причины. При 409 сначала актуальные сведения и новое подтверждение. При 404 — «Задача уже отсутствует», без приписывания удаления текущему пользователю. Неизвестный результат разрешается по S6.

### S5 — Темы, адаптивность и состояния данных (P1)

**Цель:** работать на компьютере и телефоне, понимая состояние системы. **Независимая проверка:** подготовленные ответы — загрузка, данные, пусто, ошибка; обе темы и ширины.

1. На 1440 px три колонки расположены рядом; на 390 px — вертикально, со своими заголовками и счётчиками. Горизонтальной прокрутки страницы, обрезанных кнопок и недоступных полей нет; мобильная форма занимает доступную ширину и прокручивается вертикально.
2. Переключение темы охватывает карточки, формы, меню, ошибки, диалоги и фокус. При доступном хранилище настроек выбор восстанавливается после перезагрузки; при недоступном переключение работает в сеансе. Не допускается вспышка противоположной темы при запуске.
3. До первого успешного ответа показано «Загружаем задачи», не пустая доска. После подтверждённого пустого списка видны все колонки и приглашение создать первую задачу. Отдельная пустая колонка содержит «Здесь пока нет задач».
4. Ошибка первой загрузки показывает причину в понятной форме и «Повторить». Ошибка обновления сохраняет предыдущие данные с предупреждением об устаревании. Создание доступно после успешной первоначальной загрузки; действия над ещё не полученными данными недоступны. Тема переключается всегда.
5. Неверная структура ответа, неизвестный статус или повреждённая Task не исчезают молча: показано сообщение о невозможности корректного отображения и обновление. Запись по повреждённой Task заблокирована; для некорректной оболочки списка сохраняется последний корректный снимок, пустота не имитируется. Health не подменяет состояние загрузки задач.

### S6 — Конфликты, отсутствие и неизвестный результат (P1)

**Цель:** не потерять черновик и не затереть чужое изменение из другой вкладки. **Независимая проверка:** две вкладки и управляемая потеря ответа с реально выполняющим операцию сервером.

1. При 409 version_conflict черновик сохраняется отдельно от подтверждённой Task; выполняется GET. Показываются актуальные и отличающиеся введённые значения. Пользователь выбирает принять актуальное либо явно применить выбранные изменения с прочитанной версией. Остальные поля не перезаписываются; новый конфликт проходит тот же процесс. Молчаливой подстановки версии и автоматического PATCH нет.
2. Для перемещения после GET уже целевой статус означает сообщение о текущем состоянии без лишнего PATCH. Другой статус допускает только осознанный повтор с актуальной версией. После конфликта удаления актуальная Task показывается перед повторным подтверждением.
3. 404 отсутствующей задачи приводит после сверки к удалению её из подтверждённого состояния и корректировке счётчиков. Черновик остаётся отдельно; перенос в новую задачу — только явное действие с новым намерением. Нельзя показывать несуществующую карточку как актуальную.
4. Разрыв связи, 503, 500 или непонятный ответ записи означают неизвестный исход. После восстановления сначала GET: для PATCH действуют сравнение и выбор пользователя; для DELETE 404 подтверждает отсутствие, а 200 требует нового подтверждения; для POST — S7. Совпадение полей после GET не доказывает авторство изменения.
5. Если GET сверки не удался, разрешение исхода не закончено: остаются черновик, предупреждение и возможность повторить чтение. Нет автоматического повтора записи. Последний снимок не объявляется актуальным.
6. При 409 version_exhausted показать «Достигнут предел версии задачи. Изменения не сохранены», сохранить черновик, не запускать retry и не менять ID. GET и удаление доступны; перечитывание не представляется лечением предела. No-op на актуальном максимуме допустим.

### S7 — Намерение создания и безопасный повтор POST (P1)

**Цель:** восстановиться после потери ответа без дубля или воскрешения удалённой задачи. **Независимая проверка:** отправка, потеря ответа и восстановление той же вкладки.

1. На одно намерение создаётся один канонический lowercase UUID v4 с корректным variant. После первой отправки удерживаются UUID и точное исходное тело POST до разрешения исхода. Повтор использует их же; изменённый черновик не подменяет исходное тело. Новый UUID не создаётся автоматически после ошибки или конфликта.
2. При доступном сеансовом хранилище намерение переживает перезагрузку открытой вкладки. При недоступном — только память; при неизвестном результате пользователь получает предупреждение об ограничении восстановления. Восстановление не отправляет POST автоматически. После разрешения исхода запись намерения удаляется; отдельный пользовательский черновик не теряется из-за её очистки.
3. После закрытия вкладки восстановление не гарантируется; при следующем открытии сначала загружается серверная доска, без автоматического POST. Это не обещание бессрочного хранения черновиков или восстановления всех операций после закрытия браузера.
4. После неизвестного исхода GET 200 позволяет сверить существующую задачу, не перезаписывая её. При отличиях показать актуальные данные и черновик для осознанного решения. GET 404 позволяет предложить повтор именно исходного POST с тем же ID: удалённый ID защищён серверной отметкой. Не трактовать 404 как доказательство «никогда не создавалась».
5. Допустимый повтор POST возвращает 200 только по условиям контракта §5.1: версия 1 и совпадение всех нормализованных пользовательских полей с default, включая срок. На task_id_conflict — сверка существующей задачи, сохранение черновика, без нового ID для обхода конфликта. Версия >1 остаётся конфликтом даже при возврате значений к исходным.
6. На task_id_retired показать «Задача уже удалена. Повторное создание отменено», завершить старое намерение и не повторять его. Новый замысел возможен лишь явным действием пользователя. Проверить поздний POST после удаления в другой вкладке и после перезапуска сервера: задача не восстанавливается.
7. Во время выполняющегося POST запрещены параллельные и автоматические повторы POST; противоречащие записи этого намерения блокируются. Пока сверка неизвестного результата не завершена, в том числе при ошибке GET, повторная отправка не выполняется. После успешной сверки GET 404 пользователь может явно выбрать один повтор первоначального POST с тем же UUID и неизменным телом по S7.4; во время такого повтора повторное нажатие блокируется. Если ответ снова потерян, перед следующим явным повтором требуется новая сверка. GET 200 не разрешает перезаписывать существующую задачу исходным POST. Ответ task_id_retired окончательно прекращает старое намерение по S7.6. Действия над другими задачами остаются доступными. Защита не распространяется на вручную созданные новые задачи с иными UUID и на сведения, утраченные при сбросе/откате хранилища.

## Требования и трассировка приёмки

Сценарии выше нормативны. Номера FR-001–013 сохраняют связь с v1; расширения перечислены отдельно. Для каждого требования приведены проверяемые результаты, а не утверждение уже пройденных проверок.

| ID | Требование | Критерий приёмки / сценарий |
| --- | --- | --- |
| FR-001 | Kanban-доска — единственный стартовый экран | S1.1; при открытии приложения и после F5 отображается доска; разделы «Обзор», «Календарь», «Проекты» и их заглушки отсутствуют |
| FR-002 | Колонки, счётчики и содержимое карточек | S1.1–2, S5.3; счётчики равны числу подтверждённых карточек каждой колонки |
| FR-003 | Полный просмотр и возвращение фокуса | S1.3–4; сокращённое описание раскрывается полностью, отсутствие задачи не маскируется |
| FR-004 | Подписанные формы, валидация, создание и редактирование | S2, S6–S7; поля и нормализованный результат соответствуют контракту §§2–5 |
| FR-005 | Подтверждаемое необратимое удаление | S4, S6.2–4; отмена без записи, успех только после ответа/сверки |
| FR-006 | DnD и равноценное перемещение без DnD | S3; проверка всех пар статусов, отмены, фокуса и серверного порядка |
| FR-007 | Различимые состояния данных и восстановление | S5.3–5, S6–S7; ошибка не становится пустотой, черновик сохраняется |
| FR-008 | Сохранение фирменного визуального стиля TaskFlow | В обеих темах использовать типографику, отступы, скругления, тонкие границы, сдержанные тени и акцентные действия; логотип и переключатель темы остаются доступны на широком и узком экранах |
| FR-009 | Обе темы через общие семантические переменные | S5.2; все цвета только через frontend/src/styles/index.css, без отдельных цветов компонентов; проверить каждое состояние |
| FR-010 | Адаптивность и сенсорное управление | S1–S7 на 390/1440 px; без горизонтальной прокрутки, формы и действия полностью доступны |
| FR-011 | Клавиатура, семантика, фокус, объявления | Все действия выполняются клавиатурой; элементы имеют доступные названия; диалог удерживает фокус внутри, Escape обрабатывается по S2.5; закрытие возвращает фокус; диктор объявляет ошибки и результаты; статус/приоритет/ошибка не передаются только цветом |
| FR-012 | Читаемость и размеры целей | Контраст обычного текста ≥4,5:1, крупного ≥3:1; цели касания ≥44×44 px; измерение обеих тем и контрольных ширин |
| FR-013 | Русский интерфейс и независимые состояния API | Все подписи/ошибки русские; доступный health при отказе списка не создаёт ложную готовность задач |
| FR-014 | Контрактная модель Task и календарь | Проверки раздела «Данные UI» ниже, S1–S2; отсутствие срока допустимо и не сдвигает день |
| FR-015 | Порядок с микросекундной точностью | S1.5, S3.3; после reload порядок тот же, сравнение через усечённый JavaScript Date не используется |
| FR-016 | Жизненный цикл UUID/POST и защита от воскрешения | Все S7.1–7; после удаления старый POST даёт task_id_retired, а не новую карточку |
| FR-017 | Версия, конфликт, отсутствие и исчерпание | S6; граничные проверки версий и no-op ниже; нет молчаливой перезаписи |
| FR-018 | Согласованная карта ошибок | Раздел «Ошибки»; проверка всех верхних кодов и 17 вложенных кодов без ветвления по message |

### Данные UI и граничные критерии

Полная Task обрабатывается по таблице контракта §2: id, title, description, status, priority, due_date, created_at, updated_at, version. Пользователь редактирует только пять пользовательских полей; идентичность, моменты и версия служебные, вводить их в форме не требуется. Все поля полной Task сохраняются при чтении ответа.

- **D1, строки:** title 1–200 кодовых точек после точной обрезки White_Space из §2.1; description 0–5000 без обрезки. Проверить границы, emoji, составные символы, U+FEFF, внешний/внутренний TAB, разрешённые переводы строк описания, управляющие и непарные суррогаты. Не полагаться только на UTF-16 maxlength, не приравнивать кодовые точки к графемам; NFC/NFKC, смена регистра и схлопывание пробелов не выполняются. Одинаковые названия разрешены.
- **D2, значения:** три статуса и три приоритета имеют русские подписи контракта §2.2; проверить все значения, создание сразу в done, обратные переходы, default todo/medium. Проверить запрет null у строк/enum и отсутствие неявного преобразования типов. PATCH omission сохраняет поле, default заново не применяется.
- **D3, срок:** необязательная существующая григорианская дата без времени, YYYY-MM-DD, 0001–9999; null очищает, пустая строка не отправляется как срок. Ручной ввод года доступен. Проверить границы лет, високосный день, невозможную дату, timestamp вместо даты, очистку и прошедший срок. Сравнение с локальным календарным днём без UTC: вчера просрочено только при status != done, сегодня не просрочено. Пересчитать при смене дня, возвращении во вкладку и изменении срока/статуса; проверить смену часового пояса.
- **D4, служебные моменты:** сохранить исходные UTC-строки с шестью дробными цифрами, неизменность created_at и неубывание updated_at при реальном изменении. UI сохраняет относительный порядок GET при группировке; после отдельного успешного ответа порядок должен соответствовать авторитетному списку. Допустимо перечитать список; ошибка такого обновления не отменяет подтверждённую запись, но требует предупреждения о неполном обновлении доски. Не пересортировывать через JavaScript Date с потерей микросекунд. Новая задача не обязательно последняя при откате часов.
- **D5, версии:** принимать только безопасное целое 1…9007199254740991 без округления; невалидная версия полученной Task запрещает её изменение до корректного чтения. PATCH ожидает версию всей задачи, DELETE использует один канонический query version по §4. Проверить максимум−1 → максимум, реальное изменение на максимуме → version_exhausted без изменения данных/updated_at, актуальный no-op → 200, DELETE → 204. Старый no-op получает version_conflict; некорректный запрос даёт валидацию до поиска задачи. Тестовую границу готовить без нового публичного API.
- **D6, обмен:** UI использует пять операций контракта §3, включая отдельное чтение актуальной задачи; перемещение — PATCH. Проверить items/total, полный пустой ответ, полную Task, 201/200 POST, no-op, отсутствие JSON у 204. Не добавлять неизвестные/служебные поля и query; не вводить локальный лимит 1000 или пагинацию.

### Ошибки: состояния интерфейса, а не копия протокола

Нормативная оболочка, полный словарь и приоритеты находятся в контракте §6. Верхний error.code определяет действие; details.field связывает ошибку с формой, details.code уточняет причину, message служит текстом человеку и не разбирается машинно.

| Класс ответа | Реакция UI и проверяемый результат |
| --- | --- |
| validation_error с известными редактируемыми полями | Ошибки у полей, сохранённые значения, фокус по порядку формы; независимые ошибки видны одновременно |
| Ошибки структуры/служебных полей, invalid_json, unsupported_media_type, method_not_allowed | Общая русская ошибка, черновик сохранён; нет автоматического повтора неизменённого некорректного запроса |
| task_not_found | S6.3 и S4.3: отсутствие, актуализация счётчиков, отдельный черновик |
| version_conflict | S6.1–2: GET, сравнение, осознанное решение, без автоматической записи |
| task_id_conflict / task_id_retired | S7.5–6: сверка либо завершение старого намерения, без обхода новым ID |
| version_exhausted | S6.6: конечная ошибка изменения, сохранённый черновик, просмотр/удаление доступны |
| storage_unavailable / internal_error | При чтении — ошибка и повтор; при записи — неизвестный исход и S6.4–5 |
| Неизвестный код/поле, неверная оболочка, не-JSON или сеть | Безопасное общее русское сообщение без технического содержимого; сохранить черновик; для неподтверждённой записи — сверка |

Контрактные проверки должны покрывать все 17 details.code из §6.2, в том числе invalid_unicode, read_only, duplicate_parameter, stale_version и retired, но не требуют 17 отдельных диалогов. Проверить одну зависимую ошибку на поле, сбор независимых и серверную сортировку details независимо от фокуса UI. При пересечениях применяются приоритеты §6.3: Unicode до длины, длина до управляющих, дубликат query до синтаксиса/диапазона, конфликт версии до no-op/исчерпания. Ошибки id/version/$ и неизвестных полей не превращаются в несуществующие поля формы. Проверить изменение текста message при неизменных кодах: реакция UI остаётся прежней.

## Критерии успеха и обязательная приёмка

- **SC-001:** все S1–S7, FR-001–018 и D1–D6 проверены; визуальные состояния и основные операции проходят на 390/1440 px в обеих темах. Протокол фиксирует проверенные комбинации, известные ограничения и непроверенные случаи; успешный частичный набор не означает полную готовность.
- **SC-002:** обязательный сквозной цикл с реально работающим backend: создать в каждом статусе → задать/очистить срок → прочитать → изменить → перенести → обновить клиент и перезапустить сервер → проверить сохранённые поля и порядок → удалить → убедиться в отсутствии. Основная UI/совместная доска — 30 задач; 1000 не ограничение данных. Подмена сервера подтверждает только изолированное поведение UI.
- **SC-003:** в каждой проверке ошибки записи черновик сохранён в пределах текущего сеанса; для исходного POST восстановление дополнительно соответствует S7. Не происходит повторного действия от нажатий во время ожидания, молчаливой перезаписи или воскрешения удалённого UUID. После авторитетной сверки отображается серверное состояние, а не обязательно старый снимок.
- **SC-004:** все основные действия доступны клавиатурой и касанием, без потери фокуса, недоступных целей и горизонтальной прокрутки. Проверить семантику, доступные имена, экранный диктор, объявления и все требования FR-011–012 вручную, а не только автоматическими средствами.
- **SC-005:** обе темы покрывают все состояния; при доступном хранилище настроек выбор восстановлен после пяти перезагрузок. Проверены недоступное хранилище, запуск без вспышки другой темы и контраст FR-012.
- **SC-006:** обязательны две вкладки, 409 формы/переноса/удаления, повторный конфликт, внешнее удаление, максимальная версия, потерянные ответы POST/PATCH/DELETE и отказ GET при сверке. Отдельно проверить обычный отказ и неизвестный исход, изменение данных после POST и поздний повтор после удаления/перезапуска. Сервер реально выполняет операции; потеря ответа не подменяется сервером-заглушкой.

Общая контрактная/серверная программа §8 остаётся обязательной и не заменяется UI-проверками: автоматические проверки бизнес-правил, форматов/ошибок/приоритетов, сохранности сроков и отметок, реальная файловая SQLite и новый процесс, гонки, блокировки/доступ/повреждение, сбои и отсутствие частичных результатов. В частности, 20 синхронизированных пар реальных изменений и 20 пар одинаковых POST не заменяются последовательными запросами. Для двух реальных PATCH одной версии успешен один; два no-op могут пройти; no-op перед реальным PATCH допускает оба успеха, обратный порядок даёт конфликт старому no-op. PATCH перед DELETE даёт конфликт удаления; DELETE перед PATCH — отсутствие задачи. UI должен корректно отображать эти ответы. Схема хранения и механика тестовых сбоев здесь не проектируются.

На будущем разрешённом этапе изменения frontend требуют npm run lint, npm run typecheck, npm run build; backend — python -m pytest. Эти команды не доказывают прохождение пользовательской приёмки. При создании данной документации приложение не меняется и будущие проверки не объявляются выполненными.

### Дополнительные диагностика и исследование

По R5 числовые показатели скорости диагностические до отдельного утверждения воспроизводимой методики: UI на 30 задачах — 2 с до доступности и 200 мс до видимой реакции; API на 1000 — 95 из 100 успешных ответов до 1 с отдельно для списка/GET/реального PATCH. Это не SLA и не обязательный барьер. Диагностический прогон UI на 1000 проверяет зависания/доступность карточек без выдуманного норматива. Отчёт содержит среду, сборку, тексты/объём, прогрев, точки замера, серии, сеть и полное пользовательское время. Быстрые ошибки не успех. Задержка ответа 2 с остаётся обязательным условием функциональной проверки ожидания и доступности остальных задач, а не порогом завершения записи.

По R6 исследование удобства на пяти участниках дополнительное. Без фактических сессий статус **«Не проводилось»**, результат 4/5 не заявляется. Если проводится: пять людей вне разработки, одинаковая доска из 30 задач со сбросом перед сессией, подготовленный текст задачи, без обучения действиям Kanban и подсказок, одна фиксированная конфигурация. Отдельно для каждого задания ≥4/5 создают за 60 с, находят/открывают за 30 с, перемещают за 15 с до видимого подтверждённого результата. Сеть фиксируется, но не вычитается. Подсказка нарушает условие самостоятельности. Это небольшое формирующее исследование, не оценка успешности всех пользователей. Координатор организует набор/дату, UI проводит, Backend обеспечивает данные и сервер; доступность людей и дата не предполагаются.

## Границы и открытые вопросы

Одна личная Kanban-доска; отдельные Dashboard, «Обзор», «Календарь», «Проекты» и заглушки не входят в интерфейс. Авторизация, совместная работа как продуктовая функция, облако, Docker, фильтры, поиск, подзадачи, вложения и ручная сортировка вне объёма. Несколько вкладок проверяются как источник конфликтов, без добавления многопользовательского продукта. Новые зависимости документом не предлагаются.
