# Backend v2: согласованная спецификация серверной логики Kanban TaskFlow

**Дата**: 2026-10-30. **Статус**: серверная спецификация, приведённая к принятому пакету Q1–Q10/R1–R6; реализация не выполнена и этим документом не разрешается.

Первоначальная [Backend v1](spec.md) сохраняется как неизменяемый независимый снимок. Нормативный источник внешнего поведения — [единый API-контракт](../../docs/sdd/kanban-api-contract.md), далее «контракт». Основания изменений — [итоговый журнал](../../docs/sdd/kanban-decisions-final.md). Применяются [AGENTS.md](../../AGENTS.md), [Constitution](../../.specify/memory/constitution.md), README.md и docs/foundation.md. UI v2 не использовалась как источник требований.

Этот документ определяет серверные обязанности, сценарии и доказательства приёмки. Полные транспортные правила, схемы, примеры и классификация ошибок находятся в контракте; здесь они не образуют альтернативный API. При существенном расхождении требуется остановить затронутую работу и согласовать источник, а не менять контракт самостоятельно. На момент подготовки существенных противоречий с итоговым журналом не выявлено.

## 1. Объём и границы

Сервер является источником истины для одной личной доски: проверяет запросы, применяет бизнес-правила и хранит задачи в локальной файловой SQLite. Несколько вкладок могут одновременно работать с одной задачей. Существующий GET /api/health и основа приложения сохраняются.

Не вводятся авторизация, облако, Docker, поиск, фильтры, пагинация, ручной порядок, архив, отмена удаления, история изменений, проекты, исполнители, вложения или подзадачи. Отметка UUID не является архивом. Схема таблиц, индексы, слои кода и механизм транзакций остаются предметом последующего разрешённого проектирования. Для минимальных отметок новые библиотеки не требуются; любая иная новая зависимость потребует отдельного обоснования.

## 2. Пользовательские сценарии и приёмка

### US1 — сохранить и вновь получить задачу (P1)

Пользователь записывает план и получает те же данные после повторного открытия приложения. Независимая проверка: создание, отдельное чтение, список и новый процесс сервера с тем же хранилищем.

- **AC-01**: пустое доступное хранилище даёт 200 и `{"items":[],"total":0}`. Недоступное хранилище не даёт этот успешный результат.
- **AC-02**: POST с обязательными **id и title**, без других пользовательских полей, даёт 201, Location с тем же ID и полную Task из девяти полей. Description="", status=todo, priority=medium, due_date=null, version=1; created_at=updated_at. POST только с title получает 422/missing для id и ничего не создаёт. Это исправляет неоднозначность истории 1.2 в v1.
- **AC-03**: отдельный GET и элемент списка совпадают по всем девяти полям; одинаковые заголовки при разных UUID разрешены. Total равен длине items; выдача не обрезается на 1000.
- **AC-04**: созданный срок, русский текст, emoji и остальные поля сохраняются после штатного и принудительного перезапуска. Ранее подтверждённые изменения не теряются; записи не зависят от cwd запуска.

### US2 — изменить содержание, срок и ход работы (P1)

Пользователь меняет актуальный план без незаметной перезаписи другой вкладки. Независимая проверка: подготовленная Task и запросы с известной версией.

- **AC-05**: один PATCH актуальной версии меняет несколько переданных полей целиком, сохраняет непереданные, возвращает 200 и полную Task; при реальном изменении version увеличивается ровно на 1, created_at/id сохраняются, updated_at не убывает.
- **AC-06**: проверяются все шесть переходов между разными статусами, создание сразу в done и установка текущего статуса. Срок и приоритет не ограничивают переходы.
- **AC-07**: отсутствие due_date в PATCH сохраняет срок; null очищает; новая корректная дата заменяет. Прошлые даты допустимы. Неверное поле в многочастном изменении отклоняет весь запрос, включая корректные поля и служебные значения.
- **AC-08**: актуальный no-op после нормализации возвращает 200 с прежними version/updated_at. PATCH только с version — 422/empty_update. Старая версия даёт 409/version_conflict даже при совпавших значениях.
- **AC-09**: два реальных PATCH исходной версии дают один 200 и один 409; победившее изменение не затирается. Исключения для no-op и точные гонки приведены в разделе 6.
- **AC-10**: на актуальной максимальной версии no-op даёт 200, реальный PATCH — 409/version_exhausted, details=[] и полностью прежнее состояние. Удаление этой версии разрешено.
- **AC-11**: список сохраняет порядок created_at ASC, id ASC после любого редактирования, переноса и перезапуска. Для одинакового момента сравнивается ID. Вход в конец колонки и хронология создания при откате часов не обещаются.

### US3 — удалить ненужную задачу без восстановления (P2)

Пользователь убирает задачу навсегда, а задержанный повтор создания её не возвращает. Независимая проверка: подготовленная Task, удаление, чтение и повтор POST в новом процессе.

- **AC-12**: DELETE актуальной версии даёт 204 без тела; GET даёт 404, список не содержит задачу. Повтор DELETE с корректным входом — 404, прочие задачи не меняются. Устаревшая версия существующей задачи — 409 без удаления.
- **AC-13**: удаление и минимальная отметка UUID атомарны и долговечны. После удаления и перезапуска валидный POST прежнего ID даёт 409/task_id_retired с details id/retired, независимо от содержания. Пользовательское содержание удалённой задачи не сохраняется как архив.
- **AC-14**: гонка POST/DELETE и искусственный сбой не оставляют состояния «задачи нет, отметки нет» после зафиксированного удаления. POST, завершившийся до удаления, может вернуть существующую Task; после удаления повтор не создаёт её заново.

### US4 — понять отказ и разрешить неизвестный результат (P1)

Пользователь получает причину отказа и может сверить состояние после разрыва связи. Независимая проверка: неверные запросы, потерянные ответы и восстановление чтения.

- **AC-15**: ошибки соответствуют оболочке, HTTP/error.code/details и приоритетам контракта, сообщения русские, без SQL, путей и трассировок. Отказ валидации, конфликт и исчерпание не изменяют Task.
- **AC-16**: повтор нормализованного POST существующей версии 1 возвращает 200 с прежними временами/версией и без дубликата. Сравниваются все пять пользовательских полей, включая due_date. Другая дата/содержание или version>1 дают 409/task_id_conflict; возвращение полей к первоначальным после реальных изменений этого правила не отменяет.
- **AC-17**: после потери ответа POST/PATCH/DELETE серверный GET позволяет сверить текущее состояние по правилам контракта §5.3. Старая версия PATCH не становится автоматически актуальной; 404 после DELETE доказывает отсутствие, но не авторство удаления. Отказ GET оставляет исход неразрешённым.
- **AC-18**: при недоступности хранилища — 503/storage_unavailable; при непредвиденной ошибке — 500/internal_error. Ни эти ответы, ни разрыв связи не являются доказательством отката уже сохранённой записи. После восстановления возможен только целый старый или целый новый результат, согласно моменту фиксации; частичный запрещён.

## 3. Модель и серверные правила

### 3.1. Task

Нормативная модель и строгая валидация — контракт §2–2.3. Все успешные представления Task, в том числе элементы списка, содержат девять полей:

| Поле | Серверная обязанность |
| --- | --- |
| id | Принять обязательный клиентский канонический lowercase UUID v4 с корректным variant; сохранить неизменяемым, проверять также в пути |
| title | Обязателен при создании; точная обрезка White_Space по контракту, затем 1–200 кодовых точек |
| description | Строка 0–5000 кодовых точек, без обрезки; default "", пустая строка очищает |
| status | todo/in_progress/done, default todo, свободные переходы |
| priority | low/medium/high, default medium, не ограничивает переходы |
| due_date | Необязательна на входе; в полном ответе всегда YYYY-MM-DD либо null; default null, PATCH null очищает |
| created_at | Серверный UTC `YYYY-MM-DDTHH:mm:ss.SSSSSSZ`, неизменяемый |
| updated_at | Тот же точный формат; равен created_at при создании, no-op не меняет, при реальном изменении не убывает |
| version | JSON integer 1…9007199254740991; сервер начинает с 1; ожидаемая версия обязательна в PATCH/DELETE |

Null разрешён только для due_date; bool не integer, неявных преобразований типов нет. Для title/description действуют запреты управляющих символов и исключения LF/CR/TAB у description из контракта §2.1. Непарные суррогаты запрещены; валидная пара — одна кодовая точка. NFC/NFKC, изменение регистра и схлопывание пробелов не выполняются. Точная обрезка и подсчёт одинаковы при записи, no-op и сравнении POST.

Due_date — реальная григорианская дата годов 0001–9999; строки с пробелами, сокращённой записью, timestamp, пустая строка и невозможные даты отклоняются. Она хранится без преобразования в UTC. Вычисляемая просрочка не поле Task и не хранится: это функция UI от локального дня и status по контракту §2.3. Сервер не отклоняет вчерашнюю дату и не запрещает done с прошлым сроком.

Форма с шестью дробными цифрами не доказывает микросекундную точность часов. Порядок определяется значением момента, затем ID; новые поля порядка не вводятся. Версия, а не timestamp, является защитой от конкуренции.

### 3.2. SQLite и отметка удаления

Файловая SQLite хранит Task и минимальные неистекающие отметки UUID без пользовательского содержания. Подтверждение успешной записи выдаётся только после надёжного сохранения; сравнение версии и изменение/удаление неделимы. Проверка UUID при POST не должна допускать воскрешение через гонку с DELETE.

Путь задан настройкой приложения и стабилен при смене cwd. Отсутствующий файл создаёт пустое хранилище; существующий повреждённый не затирается. Ошибки доступа/блокировки при чтении или записи не маскируются как 404 либо пустой список. Задачи и отметки сохраняются согласованно после штатного и принудительного перезапуска. Рост отметок зависит от числа удалений; истечение и очистка не вводятся.

Гарантия относится к фактически сохранённому состоянию: сброс/откат резервной копии может утратить сведения об UUID. Проверка остановки процесса не доказывает стойкость при отказе диска или питания. Проверки используют отдельные базы и не затрагивают пользовательские данные. Нормативная граница — контракт §7.

## 4. Операции, повторы и восстановление

Методы, входы, полные примеры, Content-Type, тела и query определены контрактом §1, §3; здесь приведено покрытие сценариями:

| Операция | Проверяемый серверный результат | Приёмка |
| --- | --- | --- |
| POST /api/tasks | id/title обязательны; defaults только при создании; 201 + Task + Location или допустимый повтор 200 | AC-02, AC-13, AC-16 |
| GET /api/tasks | 200 items/total, все существующие Task в стабильном порядке, без отметок UUID | AC-01, AC-03, AC-11 |
| GET /api/tasks/{id} | 200 полная Task либо 404 при корректном отсутствующем ID | AC-03, AC-12, AC-17 |
| PATCH /api/tasks/{id} | version и хотя бы одно пользовательское поле, 200 полная Task; смена статуса этим же методом | AC-05–AC-10 |
| DELETE /api/tasks/{id}?version=… | Ровно один ожидаемый version, атомарное удаление и отметка, 204 без JSON | AC-12–AC-14 |
| GET /api/health | Прежние 200 и {"status":"ok"}; не проверка доступности задач | Проверка регрессии health |

GET/DELETE не принимают непустое тело; query разрешён только DELETE.version. PATCH не применяет defaults к отсутствующим полям. Канонический query version после URL-декодирования — ASCII `[1-9][0-9]*` в диапазоне модели; ведущие нули, знак, дробь, экспонента, пробелы, Unicode-цифры и повторы запрещены.

Правила POST — контракт §5.1: незанятый неотмеченный ID создаёт одну Task; совпавшая Task версии 1 возвращается без изменений; несовместимая существующая запись — task_id_conflict; отметка удалённого UUID — task_id_retired. Отсутствующее due_date эквивалентно null, отсутствующее description — "" после default. Одинаковое содержание с разными UUID не запрещено.

Клиент генерирует один UUID на намерение и удерживает исходный POST; сервер не гарантирует качество случайного генератора. Сеансовое удержание при доступности переживает перезагрузку вкладки, fallback ограничен памятью; после закрытия восстановление не обещано. Это граница интеграции из контракта §5.2, не дополнительное серверное хранилище намерений. Восстановление не отправляет POST автоматически, новый ID не используется для обхода конфликта.

После неизвестного результата записи применяется GET, а не предположение об откате:

- POST: GET 200 позволяет сверить задачу; GET 404 допускает повтор того же исходного POST с тем же ID, который либо создаёт ещё не созданную Task, либо отклоняется отметкой. Новый UUID автоматически не создаётся.
- PATCH: старый повтор уже выполненного реального изменения получает 409; совпадение прочитанных значений не доказывает авторство. UI сохраняет черновик и требует решения о выбранных изменениях с актуальной версией.
- Перемещение: если после сверки статус уже целевой, дополнительный PATCH не нужен; иначе требуется осознанный перенос.
- DELETE: GET 404 подтверждает отсутствие; GET 200 требует нового решения об удалении актуальной Task. Отметка продолжает запрещать старый POST.
- Если GET не удался, неизвестный результат остаётся неизвестным; последний снимок нельзя считать актуальным. Эти сценарии проверяются через реальный backend совместно с UI по контракту §5.3.

## 5. Ошибки и валидация

Нормативные оболочка `error:{code,message,details}`, field и все соответствия — контракт §6.1–6.4. Details всегда массив объектов со строковыми field/code/message, field — имя поля/параметра либо `$`. Независимые ошибки сортируются по field, затем code. Сообщения русские, но машинные решения не зависят от их текста. Актуальная Task не вкладывается в конфликт версии: для неё служит GET.

Покрытию подлежат все предусмотренные верхние ошибки: 400 invalid_json; 415 unsupported_media_type; 422 validation_error; 404 task_not_found; 409 version_conflict, task_id_conflict, task_id_retired, version_exhausted; 405 method_not_allowed с Allow; 503 storage_unavailable; 500 internal_error. У 400/415/404/405/503/500/version_exhausted details=[]; у конфликтов версии/ID — соответствующая деталь из контракта.

Закрытый словарь из **17** details.code (не расширяется этой спецификацией):

- Вход: missing, invalid_type, invalid_length, invalid_value, invalid_format, invalid_date, invalid_characters, invalid_unicode.
- Структура: unknown_field, read_only, unknown_parameter, duplicate_parameter, empty_update, body_not_allowed.
- Конфликты: stale_version, id_conflict, retired.

Точные классификации не копируются в отдельный словарь: обязательна таблица контракта §6.2 и следующие проверки приоритета §6.3:

1. Метод/тип содержимого → JSON → форма/поля/параметры → наличие/занятость/отметка ID → версия → no-op/исчерпание → сохранение. Ранняя ошибка не заменяется поздней.
2. Известное запрещённое поле — read_only; неизвестное — unknown_field. Их значения не проверяются как разрешённые; независимые разрешённые поля проверяются.
3. Разрешённое поле: обязательность → тип → Unicode → применимая обрезка title → длина → применимые управляющие/формат/значение/диапазон. После первой зависимой ошибки поля дальнейшие проверки этого поля прекращаются; другие независимые ошибки собираются.
4. DELETE.version: отсутствие → missing; повтор → duplicate_parameter до разбора значений; затем синтаксис → диапазон. Неизвестные query — unknown_parameter. Непустое тело GET/DELETE — body_not_allowed с field=$; повтор JSON-ключа — 400, не duplicate_parameter.
5. Корректность входа проверяется до поиска: неверная version получает 422 даже у отсутствующего ID. После валидации отсутствие — раньше конфликта версии, конфликт — раньше no-op/исчерпания. Актуальный no-op разрешён на максимуме.

Проверки пересечений: неверный Content-Type и JSON → 415; повтор JSON-ключа → 400; id:null в PATCH → read_only; null разрешённого title → invalid_type; непарный суррогат и избыточная длина → invalid_unicode; слишком длинный title с внутренним TAB → invalid_length; допустимая длина с внутренним TAB → invalid_characters. Due_date="" → invalid_date, due_date числом → invalid_type. `version=01&version=1` → duplicate_parameter, одиночное `01` → invalid_format, каноническое число выше максимума → invalid_value. Проверяются также пропуски, неверные enum/UUID/variant, массив/скаляр/null вместо объекта, empty_update и сортировка нескольких независимых ошибок. Ожидаемые детали и этапы берутся из контракта, а не из стандартного ответа framework.

## 6. Версии и конкурентные операции

Нормативная последовательность — контракт §4. Версия охватывает все пользовательские поля, включая срок. Ошибка проверки входа, конфликт и version_exhausted не меняют ни одно поле; неопределённый результат инфраструктурной ошибки рассматривается отдельно, а не объявляется откатом.

Для валидных запросов к подготовленной задаче с общей исходной версией, при доступном хранилище и без искусственных отказов:

| Порядок/конкуренция | Ожидаемые ответы и состояние |
| --- | --- |
| Два реальных PATCH | Ровно один 200, другой 409/version_conflict; одна прибавка версии |
| Два no-op без третьего изменения | Оба могут завершиться 200; версия/updated_at прежние |
| No-op перед реальным PATCH | Оба могут завершиться 200; только реальное изменение увеличивает версию |
| Реальный PATCH перед старым no-op | PATCH 200; старый no-op 409 |
| Реальный PATCH перед DELETE | PATCH 200, DELETE 409, задача сохранена в новой версии |
| DELETE перед реальным PATCH | DELETE 204, PATCH 404, задача отсутствует, отметка сохранена |
| Два одинаковых POST нового ID до иных действий | Один 201, другой 200; одна Task версии 1 |

Максимум проверяется подготовленным тестовым состоянием: переход с максимума−1 к максимуму успешен; актуальный реальный PATCH на максимуме — 409/version_exhausted с details=[]; no-op — 200; DELETE — 204. Отсутствующая Task — 404, устаревшая версия — version_conflict раньше проверки максимума. Переполнение, сброс версии и автоматическое пересоздание не допускаются.

### Обязательная программа проверки

- **Бизнес-правила автоматически:** title 0/1/200/201 после обрезки; description 0/5000/5001; русский текст/emoji/валидные пары и непарные суррогаты; точный White_Space, U+FEFF, внутренние/крайние TAB, LF/CR/TAB у description; отсутствие скрытой нормализации. Даты 0001-01-01/9999-12-31, високосность, невозможный день, вчера/сегодня/завтра, пустая строка, null и очистка. Проверить все статусы/приоритеты, строгие типы, непереданные поля, служебные/неизвестные поля и version.
- **Контракт автоматически:** каждый метод и класс ошибки, девять полей/типы/UTC/defaults, items/total, Location, 204 без тела, Content-Type, запрет query/тел, 17 details.code и приоритеты из раздела 5. Для отказов сравнить всё состояние; не проверять только HTTP-код.
- **SQLite интеграционно:** отдельный настоящий файл, новый процесс после штатного/принудительного завершения, запуск с другой cwd и прежней настройкой. Набор 1000 задач с подтверждёнными изменениями, сроками и удалениями: 100% ожидаемых записей и отметок сохранены; пользовательское содержание удалённых задач не архивируется. Проверить также выдачу без искусственного отсечения при более чем 1000 задачах.
- **Конкуренция автоматически:** 20 синхронизированных пар двух реальных PATCH исходной версии, в каждой один 200 и один 409; 20 пар одинаковых POST нового ID, в каждой одна Task и ответы 201/200. Отдельно все строки матрицы раздела 6, POST/DELETE, повторы после перезапуска. Последовательная отправка не доказывает гонку; искусственные блокировки не подменяют нормальную конкурентную проверку.
- **Сбои:** отдельно чтение и запись при реальной блокировке/ошибке доступа, повреждение файла без перезаписи; управляемые отказы до, внутри и после фиксации, в том числе удаления с отметкой. До фиксации нет частичных полей/отметок; после подтверждённой фиксации результат сохраняется; при неопределённом моменте допустимо целое старое/новое состояние по завершению транзакции, не произвольная потеря подтверждённого. После сохранения потерять ответ и проверить разрешение исхода. Новый публичный тестовый API не вводится.
- **Сквозные автоматические проверки с UI и реальным backend:** на 30 задачах создание → срок → чтение/редактирование → перенос старой задачи и порядок → обновление клиента/перезапуск сервера → удаление. Две вкладки, конфликт/удаление извне, потерянные ответы всех трёх операций, старый POST после удаления/перезапуска, неверные поля/даты/Unicode, отказ GET при сверке. Подтверждённая доска соответствует серверу, черновик не используется для молчаливой перезаписи. Состояния ожидания проверяются также с задержкой ответа 2 с. Проверки UI тем, 390/1440 px, клавиатуры/сенсора и доступности сохраняются по контракту §8; подмена сервера не подтверждает интеграцию.

При будущих изменениях backend обязательна команда `python -m pytest` в подготовленном окружении. Проверки frontend lint/typecheck/build выполняются при соответствующих изменениях frontend в разрешённом цикле. Итог приёмки должен сопоставить результаты с FR/AC, перечислить непроверенное и ограничения; успешные тесты не доказывают полную корректность.

### Диагностика и дополнительное исследование

Порог Backend ≥95 из 100 ответов ≤1 с при 1000 задачах и остальные числа скорости из контракта §8 — **диагностические**, пока не утверждена воспроизводимая методика. Замеры содержат среду, условия и операции; быстрый ошибочный ответ не считается успешным. Эти числа не SLA и не обязательный барьер. Нормальные измерения не смешиваются с искусственными сбоями. Числа 20 пар, 30/1000 задач относятся к обязательным функциональным проверкам, а не снимаются решением о скорости.

Исследование UI с пятью участниками дополнительно и не является обязательным серверным тестом. Без фактического проведения результат — **«Не проводилось»**. Его протокол и ограничения определены контрактом §8; оно не заменяет корректность, интеграцию и доступность. В этом этапе ни исследование, ни измерения не выполнялись.
