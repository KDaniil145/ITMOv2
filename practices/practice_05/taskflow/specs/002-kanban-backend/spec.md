## Пользовательские сценарии и проверка

### История 1 — записать и вновь получить задачу (P1)

Пользователь сохраняет задачу и получает её после повторного открытия планировщика.

**Причина приоритета**: без надёжного сохранения планировщик не выполняет свою основную функцию.

**Независимая проверка**: создать задачу, прочитать отдельно и в списке, перезапустить сервер с тем же хранилищем и повторить чтение.

**Сценарии приёмки**:

1. Дано пустое хранилище; при получении списка возвращаются пустой массив и количество 0.
2. При создании только с корректным заголовком возвращается задача с уникальным ID, пустым описанием, статусом todo, приоритетом medium, версией 1 и временем создания/изменения.
3. После успешного создания чтение по ID и список содержат одинаковые значения всех полей.
4. После штатного перезапуска и после принудительного завершения процесса ранее подтверждённые операции сохраняются; незавершённая операция не оставляет частичную запись.

### История 2 — изменить содержание и ход работы (P1)

Пользователь редактирует задачу, завершает её или возвращает в работу.

**Причина приоритета**: план должен отражать актуальное состояние работы.

**Независимая проверка**: подготовить задачу с известной версией и выполнить каждую разрешённую смену статуса и редактирование.

**Сценарии приёмки**:

1. Изменение заголовка и приоритета одним запросом сохраняет оба поля, оставляет остальные прежними и увеличивает версию на 1.
2. Для каждой пары разных допустимых статусов переход проходит успешно; завершённую задачу можно открыть заново.
3. Установка текущих значений с актуальной версией возвращает ту же задачу, не меняет версию и updated_at.
4. При одном неверном поле во множественном изменении не сохраняется ни одно поле.
5. Два изменения одной версии: ровно одно проходит, второе получает конфликт; первая запись не перезаписывается.

### История 3 — удалить ненужную задачу (P2)

Пользователь удаляет задачу из своего плана без восстановления.

**Причина приоритета**: ненужные записи не должны засорять список.

**Независимая проверка**: удалить заранее подготовленную задачу и прочитать список до и после перезапуска.

**Сценарии приёмки**:

1. Удаление с актуальной версией возвращает 204 без тела; последующее чтение возвращает 404, список не содержит задачу.
2. Повторное удаление отсутствующей задачи возвращает 404 и не затрагивает другие записи.
3. Удаление с устаревшей версией существующей задачи возвращает 409 и сохраняет запись.

### История 4 — понять отказ и безопасно повторить действие (P1)

Пользователь получает понятную причину отказа и не теряет данные при повторе после сетевой ошибки.

**Причина приоритета**: неоднозначный результат не должен приводить к незаметной потере изменений.

**Независимая проверка**: отправить неверные запросы, повторить создание с тем же ID и изменение со старой версией.

**Сценарии приёмки**:

1. Пустой заголовок отклоняется с указанием поля title; задача не создаётся.
2. Повтор создания с тем же ID и тем же исходным содержимым до дальнейшего изменения записи возвращает существующую задачу без дубликата.
3. После потерянного ответа изменения повтор со старой версией получает конфликт; чтение показывает сохранённое состояние, позволяя решить, нужен ли новый запрос.
4. Недоступное хранилище даёт ошибку сервиса; сервер не сообщает об успешном сохранении и не подменяет данные пустым списком.

### Граничные случаи

- Заголовки длиной 0, 1, 200, 201 символ; пробелы по краям, строка из пробельных символов, кириллица и emoji.
- Описание длиной 0, 5000, 5001 символ; переносы строк; null вместо строки.
- Пропущенные поля, неизвестные поля, неверный тип, массив вместо объекта, пустой PATCH, повреждённый JSON, дубли ключей JSON.
- Неизвестные и отличающиеся регистром статусы/приоритеты; некорректный UUID; корректный, но отсутствующий ID.
- Изменение статуса завершённой задачи, повтор установки того же статуса, изменение и удаление одновременно.
- Повтор POST после изменения или удаления записи; одинаковые заголовки у разных задач.
- Перезапуск в другой рабочей директории с тем же настроенным путём к хранилищу; блокировка, отсутствие прав и повреждение файла хранения.

## Требования

### Функциональные требования

- **FR-001**: сервер — единственный источник истины; все входные данные проверяются независимо от клиента (истории 1, 4).
- **FR-002**: задачи хранятся в локальном файловом SQLite; успешный ответ изменения выдаётся только после надёжного сохранения. Путь стабилен относительно настройки приложения, а не текущего каталога запуска. Новый отсутствующий файл создаёт пустое хранилище; существующий повреждённый файл не заменяется пустым (истории 1, 4).
- **FR-003**: поддерживаются создание, список, чтение по ID, частичное изменение и удаление; правила ответов заданы ниже (истории 1–3).
- **FR-004**: сервер применяет модель, значения по умолчанию и ограничения из таблицы сущности. Не выполняется неявное преобразование чисел, bool или null в строки (истории 1, 4).
- **FR-005**: todo («К выполнению»), in_progress («В работе»), done («Готово») — единственные статусы. Любой статус переходит в любой другой без дополнительных условий; установка того же статуса допустима. Отдельных запретов для done нет (история 2).
- **FR-006**: low («Низкий»), medium («Средний»), high («Высокий») — единственные приоритеты; они не ограничивают переходы (истории 1, 2).
- **FR-007**: любая операция изменения атомарна; ошибка не меняет задачу и её служебные поля (истории 2–4).
- **FR-008**: изменение и удаление требуют ожидаемой версии; сравнение и запись выполняются как одна неделимая операция. Устаревшая версия даёт 409. Реальное изменение увеличивает версию ровно на 1, updated_at не уменьшается (истории 2, 3).
- **FR-009**: сервер сохраняет записи между перезапусками, включая подтверждённое удаление; тесты используют отдельное хранилище и не меняют пользовательские данные (истории 1, 3).
- **FR-010**: все ожидаемые ошибки задач имеют единый формат с русским сообщением; внутренние пути, SQL и трассировки не попадают в ответ (история 4).
- **FR-011**: повторы обрабатываются по правилам ниже; совпадение заголовка само по себе не является конфликтом (история 4).
- **FR-012**: существующий GET /api/health сохраняет 200 и {"status":"ok"}; он не подтверждает доступность хранилища задач.

### Ключевые сущности

**Задача** — одна запись личного плана. Все поля присутствуют в полном ответе.

| Поле | Тип и обязательность создания | Правила |
| --- | --- | --- |
| id | Строка UUID v4, обязательна от клиента | Канонический вид в нижнем регистре; неизменяемый уникальный идентификатор. Клиент создаёт один ID на намерение создать задачу и сохраняет для повтора |
| title | Строка, обязательна | Удалить крайние Unicode-пробелы; затем 1–200 Unicode-кодовых точек. Запретить управляющие U+0000–U+001F и U+007F |
| description | Строка, необязательна, по умолчанию "" | До 5000 Unicode-кодовых точек; без обрезания пробелов; управляющие символы запрещены, кроме LF, CR и TAB |
| status | Строка, необязательна | todo по умолчанию; можно сразу создать в любом допустимом статусе |
| priority | Строка, необязательна | medium по умолчанию |
| created_at | Строка, только сервер | Момент создания UTC в RFC 3339 с суффиксом Z; неизменяемый |
| updated_at | Строка, только сервер | При создании равна created_at; меняется при реальном изменении |
| version | Целое число, только сервер при создании | Начинается с 1; положительное целое, bool не допускается |

Идентичные заголовки разрешены; ID не переиспользуются клиентом для новых намерений. Дата исполнения, исполнитель, метки, проекты, подзадачи, вложения, архив, ручной порядок и история изменений в эту версию не входят.

### Предложение операций API — не согласованный контракт

Общий префикс `/api/tasks`. Тела запросов и ответов — JSON, кроме ответов 204. Полная задача соответствует таблице. Поля и значения перечислений в коде английские, сообщения человеку русские.

| Метод и путь | Вход | Успех |
| --- | --- | --- |
| POST /api/tasks | id, title; опционально description, status, priority | 201, полная задача; Location: /api/tasks/{id}. При допустимом повторе 200, полная задача |
| GET /api/tasks | Без параметров | 200, объект {"items": [задачи], "total": число} |
| GET /api/tasks/{id} | UUID v4 в пути | 200, полная задача |
| PATCH /api/tasks/{id} | version и хотя бы одно из title, description, status, priority | 200, полная задача |
| DELETE /api/tasks/{id} | Параметр запроса version, положительное целое | 204 без тела |

Смена статуса — PATCH с version и status; отдельная операция не нужна. Список содержит все задачи без пагинации и фильтров, сортируется по created_at по возрастанию, затем id по возрастанию; редактирование не меняет порядок. Масштаб первоначального предложения — до 1000 задач, это проверочный объём, а не запрет создания 1001-й задачи. Неизвестные параметры запроса и поля тела отклоняются. GET и DELETE не принимают тело. POST/PATCH требуют Content-Type application/json (параметр charset допустим) и JSON-объект, не массив. Служебные поля нельзя задавать, кроме id при POST и ожидаемой version при PATCH.

Пример создания: `{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт"}`.

Пример изменения: `{"version":1,"status":"in_progress","priority":"high"}`.

### Ошибки и порядок обработки

Единая оболочка: `{"error":{"code":"validation_error","message":"Проверьте поля запроса","details":[{"field":"title","code":"invalid_length","message":"Укажите от 1 до 200 символов"}]}}`.

code — стабильный машинный код, message — русское сообщение, details — всегда массив; field содержит имя поля или `$` для всего запроса. При нескольких ошибках полей возвращаются все обнаруженные ошибки, отсортированные по field, затем code. Клиент не должен разбирать текст message для определения типа ошибки.

| HTTP | code | Условия |
| --- | --- | --- |
| 400 | invalid_json | Повреждённый/пустой JSON, повтор ключа в объекте |
| 415 | unsupported_media_type | Неверный или отсутствующий Content-Type у POST/PATCH |
| 422 | validation_error | Нарушение формы, типов, ограничений; неизвестное поле/параметр; неверный ID или version |
| 404 | task_not_found | Корректный ID отсутствует |
| 409 | version_conflict | Существующая задача имеет другую версию |
| 409 | task_id_conflict | ID создания уже занят другим содержимым |
| 405 | method_not_allowed | Неподдерживаемый метод существующего маршрута; заголовок Allow |
| 503 | storage_unavailable | Нельзя прочитать или подтвердить запись, включая блокировку; допускается повтор после восстановления |
| 500 | internal_error | Непредвиденная внутренняя ошибка без раскрытия подробностей |

Проверки идут последовательно: метод и тип содержимого, разбор JSON, форма и поля, наличие задачи, версия, сохранение. При отсутствии задачи возвращается 404 независимо от переданной корректной версии. В конфликтах version_conflict details содержит поле version и пояснение перечитать задачу; текущее состояние получают отдельным GET. Ошибки хранения не маскируются как 404 или пустой список.

### Повторные запросы и конфликты

- GET не меняет данные и допускает повтор.
- POST использует переданный ID как защиту от дубликатов. Если запись существует, имеет version=1 и её пользовательские поля равны нормализованному запросу с применёнными значениями по умолчанию, возвращаются 200 и существующая задача без изменения времён. Другой набор полей или version>1 даёт 409 task_id_conflict. Одновременные одинаковые POST создают ровно одну запись: один 201, второй 200.
- Если запись уже удалена, повтор старого POST может создать её заново: постоянные квитанции и tombstone-записи не предлагаются. Поэтому автоматический повтор POST допустим только пока клиент не выполнил последующие действия над задачей; после неопределённого результата сначала GET. Это сознательное ограничение первоначального предложения, требующее сравнения с UI.
- PATCH с текущей версией и прежними значениями — успешная операция без изменения данных. Повтор уже выполненного изменения со старой версией — 409, даже если значения совпадают. Клиент сначала перечитывает задачу; автоматическая подстановка новой версии без решения пользователя недопустима.
- DELETE повторно возвращает 404; конечный эффект тот же — отсутствие записи. При гонке удаления и изменения ровно одна операция с исходной версией проходит, другая получает 404 либо 409 в зависимости от победившей операции.
- При 503 клиент не предполагает успех или неуспех записи: после восстановления выполняет GET и применяет указанные правила повторов. Хранилище не должно оставлять частично выполненную операцию.

## Критерии успеха

### Измеримые результаты

- **SC-001**: во всех сценариях создания, чтения, изменения и удаления пользователь получает описанный результат; неверный запрос не изменяет ни одну запись.
- **SC-002**: после штатного и принудительного перезапуска сохраняются 100% подтверждённых изменений в наборе из 1000 задач, включая русский текст, статусы, приоритеты и удаления.
- **SC-003**: в каждой из 20 пар одновременных изменений одной версии принимается ровно одно; ни одно подтверждённое изменение не теряется молча.
- **SC-004**: в 20 парах одновременных одинаковых созданий до дальнейшего изменения получается ровно по одной задаче на ID.
- **SC-005**: на локальном учебном компьютере при 1000 задач и одном активном пользователе результат 95 из 100 последовательных чтений и изменений доступен в пределах 1 секунды от отправки до получения ответа. Среда и измеренные результаты фиксируются при реализации; это предложенный порог, пока не измеренный.
- **SC-006**: каждая предусмотренная ошибка позволяет определить причину и затронутое поле без анализа внутренних журналов; ни один ответ не раскрывает трассировку или путь хранилища.

### Требуемые будущие проверки

После согласования выполнить автоматические проверки бизнес-правил и границ таблицы полей; контрактные проверки каждого метода, успешного ответа и класса ошибки; проверки конкуренции и повторов; интеграционные проверки с настоящим файловым хранилищем, новым процессом сервера и принудительным завершением. Состояние до и после отказа сравнивается целиком. Для 503 отдельно проверить чтение и запись при блокировке и ошибке доступа; для повреждённого файла проверить отсутствие перезаписи.

Сохранить тест /api/health и выполнить backend `python -m pytest` в окружении проекта. После реализации UI дополнительно проверить создание → редактирование → смену статуса → перезагрузку → удаление через реально запущенный backend. Подмена сервера не подтверждает интеграцию. Результаты сопоставить с FR и SC, явно записать непроверенные сценарии; успешные тесты не являются доказательством полной корректности.

На текущем этапе выполнена только проверка документации: приложение и тесты не изменены, проверки будущего поведения не запускались.

## Предположения

- Один пользователь, одна личная доска, локальное приложение; авторизация, облако, Docker и совместное редактирование разными пользователями вне объёма. Несколько вкладок могут конфликтовать, поэтому предложена версия записи.
- Клиент способен создавать UUID v4 и хранить его до завершения попытки создания. Это независимое предложение, а не известная возможность UI.
- Свободные переходы и немедленное необратимое удаление достаточны для личного учебного планировщика. Пустое описание разрешено; срок исполнения не включён.
- SQLite задана пользователем как требование хранения. Новые зависимости и схема реализации сейчас не выбираются. Существующая основа Dashboard, темы и health сохраняется.
- Поля API и SQLite включены по прямому запросу пользователя; обычное ограничение шаблона на технические детали применяется к внутреннему устройству реализации, которое не проектируется здесь.
- Зависимости следующего этапа: независимая UI-спецификация, сравнение расхождений, единый согласованный контракт и отдельные обновлённые спецификации. Затем возможны планирование и задачи реализации в цикле SDD домашки №5.
