# Проверка и запуск будущего Kanban

Phase 1 Spec Kit. **Это руководство для будущей реализации.** Сейчас Kanban/API задач/SQLite/E2E ещё не реализованы, команды и сценарии ниже не запускались. План завершён, не приложение. Перед выполнением требуется отдельный разрешённый цикл задач/реализации. Источники: [план](plan.md), [модель хранения/состояний](data-model.md), [индекс контракта](contracts/README.md), [единый API](../../docs/sdd/kanban-api-contract.md), обе согласованные v2.

## Подготовка окружения на этапе реализации

Работать только внутри TaskFlow; Node24/npm11 и Python≥3.12 по [README](../../README.md). Python должен поддерживать sqlite3. Сохранить текущие версии runtime-зависимостей. После реализации и обновления lockfile frontend установка — npm ci; backend — подготовленное окружение README с test extra.

Одна планируемая новая devDependency @playwright/test обоснована [research R-D9](research.md): требуются автоматические реальные browser E2E, двухвкладочные сценарии, reload и доставка/потеря ответа, чего lint/typecheck/build не делают. Её точная совместимая версия фиксируется при будущей установке в package-lock; сейчас dependency/lockfile не меняются. Для браузерной среды установить выбранный Playwright Chromium по официальной инструкции; системные зависимости/скачивание не происходят на этапе этого плана.

## Будущие обязательные команды качества

Из frontend после реализации:

```bash
npm ci
npm run lint
npm run typecheck
npm run build
npx playwright test tests/unit
npx playwright test tests/e2e
```

Последние две команды доступны **только после** добавления dev runner и тестов из плана; они не являются утверждением существования этих файлов сейчас. В будущем playwright.config.ts выделить наборы tests/unit и tests/e2e; unit helper-тесты используют runner без страницы, E2E — реальный браузер и сервер. Эти пути и конфигурация пока не созданы.

Из backend после реализации:

```bash
.venv/bin/python -m pytest
```

Pytest должен покрывать бизнес-правила, HTTP-контракт, реальную файловую SQLite, конкурентность и процессы. Сам по себе test_health не доказывает задачи/БД. Приёмка проверяет FR/AC/SC, ручной UI и ограничения сверх успешных команд.

## Локальный запуск и изоляция данных

Для ручного будущего прогона из backend:

```bash
TASKFLOW_DB_PATH="$PWD/.test-data/kanban-manual.sqlite3" .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Из frontend в другом терминале:

```bash
npm run dev
```

Открыть Vite (обычно localhost:5173); /api использует существующий proxy к8000. Для проверки restart не использовать --reload: иначе контролируется процесс reloader вместо проверяемого worker. TASKFLOW_DB_PATH — будущая конфигурация research R-D2; для текущей основы без реализации она ещё не включает хранение.

Для автоматических прогонов fixtures создают **уникальный** каталог под backend/.test-data/ и абсолютный путь БД, передаваемый отдельному процессу Uvicorn. Порты и процессы принадлежат harness; после каждой проверки освобождаются только принадлежащие ему ресурсы. Продуктовую БД/пользовательские данные не использовать и не очищать. Создание каталогов/игнорирование будущих тестовых артефактов описать задачами реализации, не редактировать ignore сейчас.

Playwright запускает Vite/Uvicorn как управляемые серверы; тесты не должны незаметно подключаться к чужому уже запущенному backend. Перед сценарием дождаться health и отдельно успешного GET /api/tasks. Health может оставаться200 при503 задач — это ожидаемо. Для restart harness останавливает сервер и запускает новый процесс с тем же абсолютным путём; не переиспользует TestClient и не меняет cwd-зависимый путь.

## Как проверять отказ без подмены сервера

1. Потеря ответа в browser E2E: перехватить нужный запрос, выполнить route.fetch к настоящему серверу, дождаться его фактического завершения и не доставить ответ (abort). Через независимый клиент прочитать Task и проверить commit; затем наблюдать UI-сверку. Порядок доставки не доказывает авторство изменения в другой вкладке.
2. До/внутри commit — внутренние передаваемые тестовые fault points/обёртки storage, выключенные по умолчанию и недоступные по HTTP. Для удаления сбой между SQL вставкой отметки и удалением Task должен откатить обе части. Для процесса использовать harness/barrier до выбранной точки и принудительное завершение, не произвольный sleep как единственное доказательство момента.
3. Для блокировок удержать настоящую SQLite-транзакцию отдельным соединением дольше настроенного ожидания; чтение и запись проверять подходящими режимами lock отдельно. Не путать ожидаемый503 со здоровой гонкой, где второй запрос должен дождаться короткой записи и получить409/200.
4. Старое целое состояние допустимо при отменённой транзакции, новое — послеcommit; подтверждённое сохранение не теряется произвольно. Ни stop процесса, ни эти тесты не доказывают power-loss/disk-failure или сохранность сведений после отката копии.

## Ручная приёмка и отчёт

Отдельно пройти все основные действия клавиатурой, сенсором и с экранным диктором; измерить контраст обеих тем/состояний, цели 44×44 и возвращение/удержание фокуса. Проверить русский текст, отображение пользовательского содержимого как текста, длинные строки/три строки описания/полный просмотр, даты/просрочку при смене дня и зоны, недоступность theme storage, пять перезагрузок и отсутствие вспышки. Автоматизация дополняет эти проверки, не отменяет их.

Диагностические замеры UI 2 с/200 мс, API 95 из 100 ≤1 с и UI на 1000 задачах публикуются со средой/режимом/прогревом/размерами/полным и сетевым временем. До утверждённой методики они не обязательный барьер. Задержка ответа 2 с — обязательная функциональная проверка ожидания, не нарушение числового порога.

Дополнительное исследование пяти участников сейчас: **«Не проводилось»**. При будущем проведении действует протокол UI v2: пять людей вне разработки, 30 одинаковых задач, без подсказок, 4/5 по каждому заданию за 60/30/15 с; сеть не вычитается. Не выдумывать людей/дату или обобщение на всех пользователей.

Итоговый протокол будущей реализации сопоставляет каждый результат с FR/AC/SC, средой и доказательствами; непроверенные случаи/ограничения/известные дефекты явно перечисляются. Отсутствие тестовой среды — «не проверено», не «пройдено». Следующий этап текущего SDD после ревью плана — отдельно разрешённый speckit-tasks, не speckit-implement.
