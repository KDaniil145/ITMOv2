# Модель данных Kanban

Phase 1. Нормативные API-типы/default/null остаются в [контракте §2](../../docs/sdd/kanban-api-contract.md#L17-L74); этот документ отображает их на хранение и внутреннее состояние. Основания: Backend v2 §3/AC-02–18, UI v2 D1–D6/S6–S7, [решения исследования R-D2–R-D7](research.md). Десятого поля Task нет.

## Task: девять полей → таблица tasks

| Поле | API / вход | Хранение SQLite / правило |
| --- | --- | --- |
| id | string, UUID v4, lowercase/variant; POST обязателен; PATCH запрещён | TEXT PRIMARY KEY NOT NULL COLLATE BINARY; неизменяем. Каноничность проверяет Python до SQL. |
| title | string, POST обязателен; PATCH optional | TEXT NOT NULL; после точного White_Space 1–200 Unicode-кодовых точек; запрет U+0000–001F/007F. |
| description | string, POST default "", PATCH optional; "" очищает | TEXT NOT NULL; 0–5000 кодовых точек без обрезки; управляющие запрещены кроме LF/CR/TAB. |
| status | string, todo/in_progress/done, POST default todo | TEXT NOT NULL с CHECK перечисления; любая смена допустима. |
| priority | string, low/medium/high, POST default medium | TEXT NOT NULL с CHECK перечисления. |
| due_date | YYYY-MM-DD/null, POST default null; PATCH null очищает | TEXT NULL; существующий григорианский день, годы 0001–9999; в хранение только каноническая строка, прошлое допустимо. |
| created_at | серверная string UTC/Z, шесть дробных цифр | TEXT NOT NULL COLLATE BINARY, форма YYYY-MM-DDTHH:mm:ss.SSSSSSZ, неизменяемая. |
| updated_at | та же серверная string; при создании = created_at | TEXT NOT NULL; реальная запись не уменьшает момент, no-op не изменяет. |
| version | JSON integer 1…9007199254740991; POST=1, PATCH ожидаемая | INTEGER NOT NULL, CHECK typeof(version)='integer' и границ; bool отвергается до SQL. |

Индекс `(created_at COLLATE BINARY, id COLLATE BINARY)` обслуживает полный список без отдельного поля порядка. Для единого фиксированного UTC-формата сравнение по этому индексу должно быть проверено на эквивалентность сравнению моментов. Времена генерируются приложением, без SQLite CURRENT_TIMESTAMP/усечения. GET выполняет один SELECT, total вычисляется по результату.

Python-валидаторы являются точным источником проверок Unicode/календаря; CHECK/NOT NULL/enum/диапазон защищают внутренние ошибки хранения, но не определяют HTTP/details.code. Не полагаться на SQLite trim()/length() как реализацию контрактного Unicode. Строки без NFC/NFKC/смены регистра/схлопывания; непарные суррогаты отклоняются до кодирования в SQLite. Служебные поля и известные запрещённые поля классифицируются до значений: id:null в PATCH — read_only, title:null в PATCH — invalid_type.

## RetiredTaskId: таблица retired_task_ids

Единственное поле `id TEXT PRIMARY KEY NOT NULL COLLATE BINARY`: минимальная отметка удалённого UUID. Не содержит title, даты удаления, исходного POST, версии или другого содержимого задачи. Отметки не выдаются в Task/items и не удаляются по TTL. Рост зависит от всех удалений.

Инвариант: один ID не присутствует одновременно в tasks и retired_task_ids. Межтабличный инвариант обеспечивает единственный storage-модуль и write-транзакция (схема не требует ORM/триггерного framework). Удаление Task и INSERT отметки совершаются одной транзакцией. Между таблицами нет FK: отметка намеренно переживает удаление. После отката копии гарантии ограничены сведениями фактически сохранённой БД.

## Конфигурация и первичная схема

Путь разрешается один раз из TASKFLOW_DB_PATH относительно backend; при отсутствии настройки — backend/data/taskflow.sqlite3. В тестах — отдельный абсолютный путь. Внутренний PRAGMA user_version=1 отмечает первую схему, не добавляет API-поле. Первая инициализация создаёт обе таблицы/индекс в одной транзакции. Существующий файл сначала проверяется на ожидаемую целостную схему; неизвестная/повреждённая не заменяется, task-запросы дают storage_unavailable. Валидный пустой файл без пользовательских таблиц может быть инициализирован как новая схема; произвольная чужая БД не переиспользуется.

Соединение на одну worker-операцию, rollback journal DELETE, synchronous FULL, timeout=5 s; параметры — внутренняя конфигурация, не новые требования к API/скорости. Health не зависит от успешного открытия этого файла. Схемы миграции исторических задач нет, поскольку в основе task-хранилища ещё нет; дальнейшее изменение user_version потребует явного решения.

## Неделимые операции и переходы состояний

Все запросы сначала проходят полную транспортную/полевую валидацию. Затем POST/PATCH/DELETE открывают BEGIN IMMEDIATE, после которого читают состояние и принимают решение. COMMIT SQL выполняется до успешного ответа; на отказе rollback при открытой транзакции и закрытие соединения. Нельзя применять INSERT OR REPLACE или обрабатывать конфликт INSERT новым UUID.

| Операция | Решение внутри транзакции | Эффект |
| --- | --- | --- |
| POST неотмеченного/незанятого ID | Применены defaults/нормализация | INSERT tasks, version1, created_at=updated_at; после commit 201/Location. |
| POST занятого ID | version1 и равны пять пользовательских полей | Без изменений, 200 Task; иначе409 task_id_conflict. |
| POST отмеченного ID | Отметка есть | Без изменений, 409 task_id_retired. |
| PATCH отсутствующей Task | Нет tasks[id] | 404. |
| PATCH другой ожидаемой версии | Сравнение до no-op | 409 version_conflict. |
| PATCH актуальный/no-op | Равны все переданные нормализованные поля | 200 без увеличения version/updated_at, включая максимум. |
| PATCH актуальный/реальный, version<max | Новый набор пользовательских значений | UPDATE WHERE id/version, version+1, updated_at=max(now,old); остальные поля сохранены. |
| PATCH актуальный/реальный на max | Невозможно увеличить версию | 409 version_exhausted, полностью прежние данные. |
| DELETE существующей Task | Проверена ожидаемая version | INSERT retired id и DELETE WHERE id/version; после commit204, включая max-version. |
| DELETE отсутствующей Task | Нет tasks[id], в том числе есть отметка | 404; другие записи не меняются. |

Несовпадение rowcount у условного UPDATE/DELETE в уже защищённой транзакции не превращается в успех: внутренняя ошибка/отказ без частичной записи и повторная проверка инвариантов в тестах. Предусмотренные конфликты определяются до записи по прочитанному в транзакции состоянию.

Одинаковые POST разных соединений до иных действий — 201/200 и одна запись. Два реальных PATCH исходной версии —200/409; два no-op могут быть200/200. No-op перед PATCH допускает оба успеха, PATCH перед старым no-op —200/409. Реальный PATCH перед DELETE —200/409, DELETE перед PATCH —204/404. Эти результаты предполагают исправное доступное хранилище; lock/commit-отказ отдельно503. Версия никогда не сбрасывается.

## Внутренние модели UI (не серверные сущности)

| Состояние | Содержимое и срок жизни |
| --- | --- |
| BoardSnapshot | Полные Task[] в серверном порядке; total и loading/ready/error/stale. Не является локальным хранилищем продукта. |
| SelectedTask | Последний отдельный GET и baseVersion; не перетирает draft автоматически. |
| TaskDraft | Пять пользовательских значений, dirty, fieldErrors; дата формы может быть пустой строкой до отображения в null. Живёт в feature-state, вне lifecycle диалога; отдельный черновик сохраняется после404/конфликта/очистки intent. |
| OperationById | idle/pending/unknown/reconciling/conflict/exhausted; в pending блокирует повторные действия конкретной Task, не всю доску. |
| CreationIntent | UUID, неизменный serializedBody POST и состояние sending/unknown/reconciling/retry_available/resolved/retired. SessionStorage открытой вкладки при доступности, fallback память; не меняется вместе с редактируемым черновиком. |

POST-переходы: draft → sending → resolved при201/допустимом200; ошибка сети/500/503/невалидный ответ →unknown →reconciling. GET404 →retry_available →**явное** sending с прежним телом; GET200 →сверка/решение, без автоматического POST; GET-ошибка →unknown. Повтор снова потерял ответ →новая сверка, не мгновенный retry. task_id_retired →retired/завершение старого intent. После resolved intent удаляется, отдельный черновик не уничтожается автоматически. Закрытие формы/abort не отменяют серверный commit; закрытие вкладки не гарантирует восстановление.

PATCH/DELETE-конфликт: draft отдельно →GET актуальной Task →показ отличий/подтверждение →запись только выбранных изменений с прочитанной версией, по решению пользователя. Новый конфликт повторяет процесс. GET404 обновляет подтверждённую доску, черновик остаётся; GET-ошибка оставляет stale. Version_exhausted сохраняет черновик, не запускает retry, просмотр/удаление доступны.
