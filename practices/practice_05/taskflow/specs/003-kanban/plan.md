# Технический план: Kanban TaskFlow

**Дата:** 2026-10-30. **Feature:** 003-kanban. **Фактическая Git-ветка:** practice_05, без создания/переключения. **Вход:** [spec.md](spec.md). Статус: Phase 0 и Phase 1 технического планирования завершены; код и тесты приложения не изменялись и не выполнялись.

## Краткое описание

Оставить TaskFlow одним полноценным Kanban-экраном: убрать Dashboard, разделы и заглушки, открывать доску при запуске и после reload. Сохранить логотип, фирменные стили, обе темы и GET /api/health. React управляет отображением/черновиками/сверкой неизвестных исходов; FastAPI проверяет запрос, применяет version и сохраняет удалённые UUID атомарно в SQLite. Один HTTP-контракт связывает обе части, без отдельного интеграционного сервиса и новых runtime-библиотек.

План построен после полного чтения [UI v2](../001-kanban-ui/spec-v2.md), [Backend v2](../002-kanban-backend/spec-v2.md), [контракта](../../docs/sdd/kanban-api-contract.md), [аудита](../../docs/sdd/kanban-v2-audit.md), [итогового журнала](../../docs/sdd/kanban-decisions-final.md), [Constitution](../../.specify/memory/constitution.md), [README](../../README.md), [foundation](../../docs/foundation.md) и общей spec. Исторические F-01/F-02 закрыты в последнем разделе аудита; ранние формулировки аудита не являются текущими блокерами.

## Архитектура и поток данных

1. App сразу отображает KanbanBoard; отдельной навигации и Dashboard нет. App сохраняет логотип, фирменную оболочку, health/theme и переключатель темы.
2. KanbanBoard и TaskDialog используют useKanban. Подтверждённые данные не смешиваются с draft/исходным POST. Транспортный клиент не обращается к sessionStorage и не принимает UI-решений о конфликте.
3. Feature api.ts отправляет ровно пять методов, Content-Type/параметры по контракту, не разбирает204 и проверяет структуру ответа до изменения снимка. Task-представление содержит девять обязательных полей, version — safe integer, timestamp — исходная строка с шестью цифрами. Некорректный ответ не становится пустой доской/успехом.
4. FastAPI Request-router сначала проверяет метод/content-type/JSON/поля/query. Точная последовательность не делегируется coercion FastAPI/Pydantic. После валидации threadpool выполняет одну storage-функцию целиком, включая создание/закрытие соединения. Event loop не блокируется sqlite3.
5. Storage проверяет существование/отметку/version в короткой write-транзакции; возвращает валидированную Task после commit. Ошибки маршрутов задач преобразуются единым builder, включая405/Allow; health независим от файла БД. Интеграционный слой — этот HTTP-клиент, router и контрактные проверки, не новый сервис.

## Хранение и конкурентность

Подробная схема — [data-model.md](data-model.md). Все девять полей в tasks; due_date nullable TEXT, version bounded INTEGER, created_at/updated_at fixed UTC TEXT. Retired_task_ids хранит только UUID, без TTL/истории содержимого. Индекс created_at/id использует BINARY только для единого canonical формата.

Каждый POST/PATCH/DELETE начинает BEGIN IMMEDIATE до чтения; явные SQL COMMIT/ROLLBACK при sqlite3 autocommit=True. POST атомарно проверяет отметку, существующую версию1/пять нормализованных полей и только затем вставляет. PATCH проверяет наличие/version **раньше** no-op; реальный UPDATE WHERE id/version увеличивает версию один раз и не уменьшает updated_at. На max версия не сбрасывается: реальная запись409 version_exhausted, no-op200, DELETE204. DELETE проверяет CAS, сохраняет UUID и удаляет Task вместе.

Изолированные соединения и SQLite-транзакция защищают также разные процессы; Python Lock не заменяет эту гарантию. Total вычисляется по тому же SELECT, что items. Timeout/commit-ошибка503 не является доказательством отката; пользовательский retry автоматически не выполняется. Инициализация схемы не затирает повреждённый файл и не останавливает health. Поведение сериализации, режим журналирования и путь раскрыты в research R-D2–D6.

## Валидация и ошибки

Контракт §§1,2,6 и [F-01 recheck](../../docs/sdd/kanban-v2-audit.md#L114-L127) — нормативные. Transport decoder видит повтор JSON-ключей и query multimap. Сначала известность/допустимость имени, затем тип/Unicode/обрезка/длина/символы/формат; default только POST. Непарные суррогаты не доходят до UTF-8/SQLite; code points и White_Space едины с UI. Даты строго0001–9999, не timestamp; version без bool/float/неявной конверсии. До поиска собираются независимые ошибки, после — отсутствие/version/no-op/max/commit.

Все11 пар HTTP/error.code и17 details.code покрываются тестами; список/условия не переписываются здесь в новый контракт. UI использует верхний code для действия, field для формы, фокус по порядку формы, русское общее сообщение для service/id/version/$/неизвестных ответов. Message не машинный идентификатор, SQL/trace не выдаются. Отказ transport/validation не вызывает изменение данных;500/503/потеря ответа записи переводят UI в неизвестный исход.

## Черновики, POST и точность UI

Подробные состояния — data-model, research R-D7. Отдельно живут список/актуальность, selectedTask/baseVersion, draft/dirty/errors, per-task операция и CreationIntent. React effect делает чтение, но не POST; event-handler блокирует повторный вход до ожидания fetch. Закрытие диалога и abort не очищают неразрешённое намерение.

Session-намерение сохраняет UUID и **serializedBody** первой отправки, retries передают ту же строку. Восстановление без автозаписи; GET404 разрешает один явный retry, повторная неизвестность снова требует GET. GET200 — сверка; retired — конец старого намерения. Ошибка GET не снимает блокировку; новый UUID автоматически не генерируется (закрытая F-02/UI S7.7).

Конфликт формы: черновик отдельно, GET актуального, показать отличия, отправить только выбранные пользователем изменения с этой версией; повторный409 снова сверяется. Конфликт переноса при уже целевом статусе не требует PATCH. DELETE409 требует нового подтверждения; GET404 сообщает отсутствие, не авторство. Exhausted не лечится retry.

После успешной мутации Task подтверждена сразу; затем авторитетный список обновляет порядок. До refresh слияние по полным canonical timestamp/id без Date; ошибка refresh оставляет подтверждение записи и stale-предупреждение. Guard поколений запросов не позволяет позднему старому GET затереть новый ответ; выбранный draft не заменяется фоновыми данными. Server array группируется стабильно, без ручного reorder.

Календарная строка срока не преобразуется в UTC; локальный day/timezone/visibility пересчитывают просрочку без серверной записи. Микросекунды момента не теряются при форматировании/сортировке. Native dialog/DnD и альтернативная кнопка, ref/focus/scroll и live announcements сохраняют пользовательские требования на обеих темах/ширинах.

## Риски и критерии пересмотра

| Риск | Контроль / что должно опровергнуть неверный выбор |
