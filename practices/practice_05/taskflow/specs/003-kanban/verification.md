## Изоляция и использование инфраструктуры

Добавлена одна devDependency `@playwright/test` 1.64.1 (lockfile); основание research R-D9: реальные браузерные E2E и pure TS runner отсутствовали. Новых runtime зависимостей нет. Chromium в этом запуске не устанавливался.

- `cd frontend; npx playwright test tests/unit` — pure TS без браузера/серверов. `npx playwright test --list` — только сборка списка.
- `npx playwright test tests/e2e` — требует заранее подготовленного backend окружения и браузера. `TASKFLOW_TEST_PYTHON` задаёт путь Python с уже установленными существующими зависимостями, по умолчанию python3; например абсолютный путь backend/.venv/bin/python. Два отдельных тестовых порта по умолчанию18765/18766 задаются TASKFLOW_TEST_BACKEND_PORT/FRONTEND_PORT; порты должны отличаться. reuseExistingServer=false, Vite strictPort, backend заранее bind собственного сокета и передаёт FD своему Uvicorn. Занятый порт — отказ, не подключение к чужому процессу.
- Тестовый Vite config живёт в frontend/tests/support; proxy ведёт только на тестовый backend. Конфигурация приложения не меняется. Подготовка task E2E импортирует frontend/tests/e2e/fixtures.ts: отдельная обязательная проверка GET /api/tasks; успешного health недостаточно. Единственный текущий infrastructure smoke намеренно использует только health, поскольку task endpoint ещё отсутствует, и не считается Kanban E2E.
- Backend harness POSIX/Linux запускает процесс без reload; абсолютный TASKFLOW_DB_PATH — только уникальная подпапка backend/.test-data/. ### Границы текущего продукта

Работают только GET /api/tasks и GET /api/tasks/{id}. Валидные POST/PATCH/DELETE продолжают отвечать500/internal_error через прежнюю честную заглушку и не меняют данные; неверные запросы проходят принятую валидацию. У этих маршрутов пока нет успешного поведения CRUD. В интерфейсе видны отключённые «Создать задачу», «Редактировать», «Переместить», «Удалить» с пояснением недоступности; формы и операции записи не реализованы. Принятое условие доступности создания после первичного чтения станет полноценно действовать в US2; этот read-срез не заявляется приёмкой создания.

Браузерные данные подготавливаются непосредственно SQL в отдельном тестовом хранилище, а не неготовым POST. Это не доказательство AC-02 или сохранности реального создания. Read-fixtures не входят в app и не создают публичного диагностического API. Временный тест границ этапа проверяет отсутствие записей у неготовых маршрутов; при разрешённой реализации соответствующей операции он должен обновляться вместе с её контрактными тестами.

### Настоящая интеграция и управление отказами

Playwright по-прежнему запрещает reuseExistingServer, Vite использует strictPort. Тестовый Uvicorn запускается своим процессом с собственным listening socket; абсолютная БД выделяется isolated_database под backend/.test-data/. Для offline fixtures harness пишет уникальный control JSON с путём именно тестовой БД. Helper требует control-файл и DB внутри .test-data, не использует продуктовый TASKFLOW_DB_PATH; metadata и временный каталог удаляются владельцем при завершении. Это отдельная cross-process схема fixtures, не расширение гарантии open_fixture_database.

- На30 задачах проверены реальные список/отдельный GET, счётчики10/10/10, микросекундный порядок, reload, полные сведения и возвращение фокуса. В backend проверены1001 запись без пагинации/отсечения и перезапуск нового Uvicorn с тем же файлом/другой cwd.
- Первичная загрузка задерживается только на транспорте и затем передаётся настоящему Backend; до ответа не показывается ложная пустота. Подтверждённая пустая файловая БД показывает3 пустые колонки.
- Corrupt/restore меняют только файл выделенной тестовой SQLite: сервер действительно даёт503, health остаётся200; первоначальная ошибка допускает retry, ошибка обновления сохраняет30 карточек и stale-предупреждение. Отдельный GET также проверен на loading→реальный503→retry→данные.
- Для404 fixture имитирует внешнее удаление в своей БД, включая отметку; UI получает настоящий404, убирает карточку и возвращает фокус на следующую. Это не реализация/проверка пользовательского DELETE.
- Логически повреждённая Task с пустым title передаётся настоящим сервером из тестового файла; клиент отклоняет весь новый снимок, сохраняет старый и сообщает о невозможности корректного отображения, не фильтрует карточку молча.
- Для гонки чтений перехватывается уже выполненный настоящий GET списка; до доставки его неизменённого ответа fixture обновляет данные, отдельный настоящий GET получает более свежую Task. Доставка старого ответа не откатывает карточку. Ни тело API, ни серверная реализация заглушкой не подменяются.
- Пользовательский HTML-подобный текст показан текстом, без img-элемента/исполнения разметки. Темы восстанавливаются после reload; при отказе preference storage переключение работает в сеансе.

### Что подтверждено именно кодом

Storage использует sqlite3 и BEGIN IMMEDIATE до чтения write-состояния; явный COMMIT до успешного ответа. Version проверяется до no-op/max; DELETE сохраняет только UUID и удаляет Task в одной транзакции. Значения SQL параметризованы. Routes выполняют явную validation до threadpool/storage, существующий health независим от БД. Это статический вывод; исполнение/состояния подтверждены отдельно тестами ниже.

Frontend разделяет confirmed Task, edit draft и исходный serialized POST. Передача записи идёт из обработчиков событий, не из эффекта восстановления; api.ts не выполняет автоматический retry. После неизвестности GET и осознанное действие; ошибочный/неизвестный ответ не становится пустой доской. Порядок сохраняет канонические шестизначные UTC-строки/id без миллисекундного Date. Защита поколения GET не позволяет старому чтению затереть подтверждённый результат. Автоматические проверки этих сценариев также выполнены, наличие кода само по себе не объявляется их доказательством.

Новых runtime-библиотек, API, auth/cloud/Docker/архива или полей модели нет. Логотип/фирменные стили, темы и /api/health сохранены. Формат Task — девять полей, пользовательских пять, null только due_date; служебные значения/строгие типы/Unicode/календарь/версии сопоставлены с API §§2/4/6 и обеими v2.

### Что подтверждено автоматическими тестами

T043: полный HTTP vocabulary проверен независимыми буквальными наборами из контракта, а не сравнением с константами реализации. Валидационные отказы не изменяют ранее прочитанную Task; все поля ответа/ошибки, порядок деталей, отсутствие SQL/trace и приоритеты проверены. Искусственные HTML/новый code проверяют только защиту UI; перед скрытием ответа сервер действительно выполняет запись, затем GET подтверждает состояние.

T044: обе операции прибывают до BEGIN на разных worker-потоках/соединениях.20 нормальных пар POST и20 PATCH не подменяются SQLite-lock failure. Для детерминированных порядков оба запроса также уже перекрываются, но второй BEGIN ждёт явного события COMMIT первого (ContextVar роли переносится в worker). Это управление наблюдаемым порядком, не замена SQLite Python-lock. Проверяется полная Task и retired table, а не один статус.

T045: все исходные пользовательские значения независимо сравниваются при создании; времена/версии и каждый из9 полей полностью сравниваются после restart.101 многочастный PATCH, один DELETE/отметка,1001 активная запись; выдача свыше1000 не обрезана. Два новых PID, обычная остановка и SIGKILL, другая cwd с прежним абсолютным путём. Это не проверка отключения питания/отказа диска/отката backup.

T046: EXCLUSIVE lock удерживается отдельным настоящим соединением и даёт503 на read/create/patch/delete; IMMEDIATE проверяет отказ конкурирующей записи. chmod проверяется при os.geteuid()!=0: чтение файла с mode0 недоступно; read-only файл читается, но не меняется; read-only каталог не принимает новый файл. После восстановления права/байты/целое состояние сверены. Fault до commit оставляет целое старое, после — целое новое; между отметкой и DELETE откатываются обе части.503 не объявляется доказательством отката. Health остаётся200. Fault seams не опубликованы по HTTP.

T047/T048: полный реальный CRUD/restart/reload, задержка2с и текущие recovery/две вкладки/retired/session/no-op/max-наборы пройдены совместно. Касание — browser hasTouch/tap, не физический палец. Проверены доступные имена/фокус/Tab/Escape/role=status/alert, но не фактическое произнесение диктором. Контраст ≥4,5 измерен по computed foreground/background выбранных кнопок/полей/подсказок/сравнения в обеих темах; это не полная ручная оценка всех цветов, состояний и наложений. Ранний rAF после reload не является покадровым ручным исследованием вспышки темы.

## Сверка готовности к сдаче

Изменения CI и новые тесты в этой завершающей проверке не предпринимались.

`docs/sdd/reflection.md` готова как краткая рефлексия по фактическому опыту: сравнивает впечатления от OpenSpec/Spec Kit, независимое согласование UI/Backend, роль координатора, выбор feature и цену подробных спецификаций; не приписывает непроведённые проверки. В README курса отдельный формат или критерии рефлексии не обнаружены. README TaskFlow описывает актуальный запуск, API health, локальную SQLite и имеющиеся команды; новых изменений README для этой фиксации не требуется.
