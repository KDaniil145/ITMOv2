# Исследование технических решений Kanban

Дата: 2026-10-30. Phase 0 навыка speckit-plan. Это решения проектирования для будущей реализации, не результаты тестов приложения. Исследованы полностью [UI v2](../001-kanban-ui/spec-v2.md), [Backend v2](../002-kanban-backend/spec-v2.md), [API-контракт](../../docs/sdd/kanban-api-contract.md), [итоговый журнал](../../docs/sdd/kanban-decisions-final.md), [аудит с закрытием F-01/F-02](../../docs/sdd/kanban-v2-audit.md), [Constitution](../../.specify/memory/constitution.md), [README](../../README.md), [границы основы](../../docs/foundation.md) и существующие файлы приложения. Два исследовательских агента независимо проверили Backend/SQLite и Frontend/E2E без записи файлов и запуска тестов; выводы сопоставлены координатором с первичными источниками.

## R-D1. Минимальное развитие существующей основы

**Решение.** Сохранить React 19.2/TypeScript 5.9/Vite 7.2/Tailwind 4.1 и FastAPI 0.135.1/Uvicorn 0.41.0 по текущим manifest; среда README — Node 24/npm 11, Python ≥3.12. Kanban-доска открывается сразу и остаётся единственным экраном после reload; отдельное состояние выбора раздела не требуется. Сохранить логотип TaskFlow, фирменные стили, health, раннее восстановление темы в index.html и общие CSS-переменные.

**Обоснование.** Сейчас frontend содержит main.tsx, lib/api.ts с одним checkHealth и index.css; backend — main.py с health и один pytest. Нужна функция одной доски, а не новая платформа. Сеть остаётся через относительный /api и существующий proxy Vite.

**Альтернативы.** Router, Redux/query-cache, отдельный frontend/backend rewrite и общий пакет DTO отклонены: текущие требования не оправдывают их стоимость. Два типизированных представления в TS/Python сверяются контрактными примерами и тестами, а нормативный API остаётся один.

**Трассировка.** UI FR-001/008–013; Backend FR-012; контракт §§1,8.

## R-D2. SQLite без ORM и отдельного service/repository слоя

**Решение.** Стандартный sqlite3, две таблицы tasks/retired_task_ids, короткие функции операций в одном storage-модуле. Все записи через параметризованные запросы. Отдельный файл БД определяется TASKFLOW_DB_PATH; отсутствие настройки — backend/data/taskflow.sqlite3 относительно каталога backend, вычисленного от файла модуля. Относительная настройка также разрешается относительно backend, не cwd. Тесты всегда передают свой абсолютный путь.

**Обоснование.** Девять полей и атомарная отметка не нуждаются в ORM/миграционном framework. SQLite-библиотека входит в Python-интерфейс [sqlite3 3.12](https://docs.python.org/3.12/library/sqlite3.html); возможность её наличия в конкретном Python проверяется при будущей подготовке окружения. Путь — внутреннее техническое решение, не новый API.

**Альтернативы.** SQLAlchemy/Alembic, глобальное соединение, in-memory БД продукта и новые инфраструктурные сервисы отклонены. In-memory файл не подтверждает требуемую долговечность.

**Трассировка.** Backend §3.2/FR-002/009, контракт §7. Схема и инварианты — [data-model.md](data-model.md).

## R-D3. Явные транзакции и CAS

**Решение.** Соединение открывается, используется и закрывается в одной worker-функции; между запросами соединение не разделяется. Async route сначала читает/проверяет HTTP, затем отправляет всю блокирующую операцию через доступный FastAPI/Starlette threadpool. Для sqlite3 Python ≥3.12 выбрать явное управление SQL BEGIN/COMMIT/ROLLBACK при autocommit=True; методы Connection.commit()/rollback() в этом режиме не использовать вместо SQL. Соединение без shared cache/read_uncommitted.

POST/PATCH/DELETE: BEGIN IMMEDIATE до чтения состояния; затем проверки/SQL/COMMIT. PATCH UPDATE и DELETE дополнительно ограничены WHERE id/version. Список — один SELECT и total=len(items). Никакой сети/ожидания пользователя внутри транзакции. Режим хранения — rollback journal DELETE, synchronous FULL; начальное ожидание блокировки 5 с — техническая настройка, не API-SLA. BUSY/LOCKED после ожидания →503, без скрытого повтора пользовательской операции.

**Обоснование.** SQLite допускает одного писателя; IMMEDIATE получает write-транзакцию до чтения и устраняет гонку повышения read-транзакции ([SQLite transactions](https://www.sqlite.org/lang_transaction.html), [изоляция](https://www.sqlite.org/isolation.html)). Режим и ожидание изолированы от бизнес-версии. Управление Python autocommit и SQL нужно явно разделять ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html#transaction-control)); sync-настройка подтверждается документацией [SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous).

**Альтернативы.** Только SELECT/затем UPDATE без транзакции, Python Lock как единственная защита разных процессов, INSERT OR REPLACE и автоматический retry CAS отклонены. WAL возможен позже при измеренной необходимости, но сейчас усложняет sidecar/копирование без требования.

**Проверка будущего решения.** 20 пар реальных PATCH, 20 одинаковых POST с разными соединениями и синхронизацией до начала операций; тесты обеих последовательностей PATCH/DELETE, no-op и сбоя commit. Read/write lock failures отдельно от нормальных гонок. Один лишь сериализующий TestClient-вызов не доказательство конкуренции.

## R-D4. Инициализация и отказ хранилища не ломают health

**Решение.** create_app с внутренней конфигурацией пути облегчает тестирование; публичный app сохраняется для текущей команды uvicorn. Инициализация схемы выполняется контролируемо, лениво при операциях задач, в worker-потоке. Создание отсутствующего файла/каталога и пустой новой схемы атомарно; для существующего файла проверяются читаемость, целостность, ожидаемая схема и user_version. Неизвестная/повреждённая схема не затирается, удаление файла и автоматический reset запрещены. Версия первой внутренней схемы — 1; старых task-данных сейчас нет.

**Обоснование.** Недоступная БД должна давать task endpoints 503, не останавливать всё приложение или health. Отказ не кэшируется навсегда: следующий явный запрос может проверить восстановленное хранилище. Проверка состояния внутри операций не требует нового публичного health/storage endpoint.

**Альтернативы.** Обязательная успешная миграция в startup, подмена повреждённого файла пустым и проглатывание исключений с items=[] отклонены. Поздние изменения схемы потребуют отдельного проектирования, сейчас framework миграций не нужен.

## R-D5. Контрактная валидация до нормализации framework

**Решение.** Task-router работает с Request, не с автоматически преобразованными UUID/date/int аргументами. JSON разбирается стандартным json с object_pairs_hook для повторов ключей и запретом не-JSON констант; синтаксическая ошибка →400, корректный JSON неверной формы →422. Query читается как multimap, не dict. Явные чистые валидаторы применяют точно контракт §6.3; тип integer проверяется без bool/float. Ввод известных запрещённых полей даёт read_only прежде типа, неизвестных — unknown_field (закрытая F-01).

**Обоснование.** Стандартные [Python JSON hooks](https://docs.python.org/3.12/library/json.html) позволяют не потерять повтор ключа. FastAPI разрешает собственные [exception handlers](https://fastapi.tiangolo.com/tutorial/handling-errors/); их наличие само по себе не делает стандартный ответ соответствующим контракту. Внешние ошибки задач строятся единым builder: HTTP/error.code/details, русские сообщения, Allow для405, без SQL/trace. Обработчики ограничиваются маршрутами задач; health сохраняет прежний формат.

**Альтернативы.** Только Pydantic coercion/regex без управления приоритетом или перехват всех исключений как422 отклонены. Внутренние TypedDict/dataclass описывают уже валидированные значения; новые schema-библиотеки не нужны. Независимые ошибки собираются, по одному зависимому отказу на поле, сортируются field/code.

**Трассировка.** Backend FR-001/004/010, AC-15, §5; UI FR-018; контракт §§1,2,6 и исправленная строка33. Версию модели/кодовые словари не расширять; технические граничные случаи исходного JSON проверять соответствующими существующими категориями.

## R-D6. Даты, Unicode и точность порядка

**Решение.** Python хранит канонические UTC-строки с шестью дробными цифрами; генерирует время timezone-aware datetime и сериализует явно, а не SQLite CURRENT_TIMESTAMP. created_at неизменяем; updated_at=max(UTC now, прежний момент), version — защита изменений. Фиксированные UTC-строки одинакового формата сортируются в SQLite BINARY по created_at/id; проверка эквивалентности порядку моментов обязательна. UI хранит исходные строки и группирует авторитетный список без JS Date-сортировки.

Для due_date — строгий ASCII YYYY-MM-DD перед календарной проверкой, без Date.parse/преобразования в timestamp. UI использует контролируемое текстовое поле с подсказкой формата и ручным годом; календарные части проверяет арифметически, что избегает особенностей JS-лет 0–99. Локальный день формируется из локальных year/month/day с padding, просрочка сравнивает календарные строки. Timer до полуночи, visibilitychange и периодическая переоценка локального дня/зоны не меняют запись задачи.

Unicode: точный набор White_Space, не встроенный strip()/trim() без заданного набора; непарные суррогаты до длины; кодовые точки, не UTF-16 maxlength; описание не обрезается, NFC/NFKC не вводится. Данные проходят одни правила сохранения/no-op/повтора POST.

**Обоснование/альтернативы.** Это способ выполнить уже принятые требования UI D1–D5/Backend §3/контракт §2. Дополнительные библиотеки времени, десятое поле сортировки, миллисекундное пересортировывание и глобальная нормализация текста не нужны. Эквивалентность строковой сортировки опирается только на единый фиксированный формат; произвольные RFC3339 строки так сравнивать нельзя.

## R-D7. React-состояние и POST-намерение

**Решение.** useReducer/useKanban в пределах feature разделяет подтверждённый список, selectedTask/baseVersion, draft/fieldErrors, операции по ID и отдельное CreationIntent. Инициирование POST — только событие пользователя с немедленной защитой от повторного входа, не useEffect (в основе уже включён StrictMode). Серверные записи не оптимистические.

CreationIntent хранит UUID и неизменную сериализованную строку POST; sessionStorage при доступности, память при отказе. Восстановление только предлагает сверку. Не удалять намерение при закрытии формы/abort запроса. После GET404 — один явный retry того же тела, во время POST/GET блокировка, новый неизвестный ответ требует новой сверки (исправленная UI S7.7). GET200 сверяет Task; retired завершает старое намерение, но не уничтожает отдельный изменённый черновик.

После единичной успешной записи обновить подтверждённую Task и перечитать список; успех записи не отменяется при неудаче перечитывания, доска помечается stale. Не потерять микросекунды: до авторитетного refresh слияние по точным canonical timestamp/id, а не Date. Старый GET, начатый до более нового результата записи/чтения, не должен затереть его: request-generation и версионная проверка при применении ответа. HTTP wrapper отличает подтверждённый отказ от неизвестного исхода/неверного ответа; автоматических retry записей нет.

**Альтернативы.** Общий объект «задача=черновик», замена version перед автоматическим PATCH и очистка intent в finally отклонены: теряют черновик или доказательства неизвестного исхода. SessionStorage не становится источником задач, данные доски берутся с сервера.

## R-D8. Доступные действия без UI-библиотек

**Решение.** Native dialog с контролем cancel/close и возвратом фокуса; несохранённые изменения подтверждаются внутри текущего диалога без вложенной modal-цепочки. Начальный фокус удаления — отмена. DnD desktop на нативных событиях; кнопка «Переместить» с выбором статуса выполняет тот же запрос клавиатурой/касанием. После commit/render — ref задачи, focus и scrollIntoView; после удаления fallback к следующей карточке/колонке. Ошибки aria-describedby, результаты live status; семантические переменные добавляются только в общей CSS в обеих темах при необходимости.

**Обоснование.** Это минимальные механизмы для UI S1–S6/FR-009–012. Возможности описаны в [HTMLDialogElement](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement) и [HTML Drag and Drop](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API). Библиотека DnD, modal-framework, отдельная цветовая палитра компонентов не требуются. Реальную доступность нельзя заключить из выбора API: нужны ручные проверки фокуса/диктора/контраста.

## R-D9. Один обоснованный инструмент браузерной проверки

**Решение.** На этапе реализации добавить только devDependency @playwright/test (и его браузер для тестирования), зафиксировав совместимую версию в package-lock тогда. Здесь установка/изменение manifest не выполняется. Playwright runner также подходит для pure TS helper-тестов без браузера; отдельные Vitest/Testing Library/axe сейчас не планируются. Backend остаётся на имеющихся pytest/httpx.

**Необходимость.** В текущем frontend есть только lint/typecheck/build: они не выполняют обязательные автоматические сквозные сценарии реального браузера, двух вкладок, reload и фокуса. Самописный WebDriver-харнесс сложнее одного dev-инструмента. В production bundle/runtime зависимостей не добавляется.

**Проверка.** Запускать настоящий Vite и Uvicorn с отдельным файлом SQLite; один browser context/две страницы для вкладок и управляемые session-сценарии. Подготовка данных API, крайних служебных значений — офлайн до запуска сервера. Для потери ответа сначала route.fetch до реального сервера, затем abort доставки; самостоятельный GET подтверждает commit. Это проектируемая техника, не готовый тест. Управление процессами/внутренними fault points не вводит публичный диагностический API. [Playwright network](https://playwright.dev/docs/network) и [несколько webServer](https://playwright.dev/docs/test-webserver#multiple-web-servers) подтверждают нужные механизмы.
