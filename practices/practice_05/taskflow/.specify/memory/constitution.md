# Конституция TaskFlow

## Основные принципы

### I. Разделение ответственности frontend и backend

Frontend отвечает за отображение данных, навигацию и взаимодействие с пользователем.
Backend является источником истины для задач: реализует бизнес-правила, проверку данных,
допустимость операций и хранение. Проверки в интерфейсе улучшают обратную связь,
но не заменяют серверную валидацию. Frontend взаимодействует с backend через согласованный
API и не обращается к базе данных напрямую. Такое разделение позволяет независимо
разрабатывать и проверять обе части приложения.

### II. Разработка по спецификациям (Spec-Driven Development)

До реализации Kanban две независимые команды обязаны подготовить первоначальные
спецификации: одна описывает UI, другая — серверную логику. Первоначальные версии
сохраняются как отдельные неизменяемые снимки внутри TaskFlow для последующего сравнения;
их нельзя подменять согласованными редакциями.

Затем команды сравнивают требования и согласуют единый API-контракт: поля и типы данных,
обязательность значений, статусы, приоритеты, операции, форматы запросов и ответов,
коды и структуру ошибок. Обе спецификации обновляются со ссылкой на один контракт;
расхождения и принятые решения документируются. Реализация Kanban, задач, CRUD, форм
и SQLite разрешается только в отдельном цикле SDD домашней работы №5 после согласования
UI, контракта и обеих обновлённых спецификаций. Существующий `/api/health`
не является контрактом задач.

### III. Проверяемость и границы доказательств

Серверная бизнес-логика обязана иметь автоматические тесты основных правил,
граничных случаев и ошибочных операций. Согласованный API обязан иметь автоматические
проверки контракта: структуры и типов запросов и ответов, статусов и ошибок.
Основные пользовательские сценарии обязаны иметь сквозные проверки взаимодействия
UI с реально запущенным backend; подмена сервера не подтверждает такую интеграцию.
Сценарии и ожидаемые результаты определяются в спецификациях.

Успешные тесты подтверждают только проверенные условия и не доказывают полную
корректность функциональности. При оценке готовности обязательны сопоставление
с критериями приёмки, ручная проверка интерфейса и фиксация непроверенных сценариев
и известных ограничений.

### IV. Качество и согласованность интерфейса

Интерфейс обязан сохранять современный визуальный стиль и согласованность
с существующим Dashboard: типографику, отступы, состояния элементов и навигацию.
Все компоненты обязаны поддерживать адаптивную компоновку, полноценные светлую
и тёмную темы. Цвета задаются только через общие семантические переменные
в `frontend/src/styles/index.css`; отдельные цвета в компонентах запрещены.

Обязательны семантическая разметка, доступные названия элементов, управление
с клавиатуры, видимый фокус и читаемый контраст в обеих темах. Информация
не передаётся только цветом. Для взаимодействий с API предусматриваются понятные
состояния загрузки, отсутствия данных и ошибки. Проверки включают экраны
шириной 390 и 1440 px, обе темы и сохранение выбора темы после перезагрузки.

### V. Простота архитектуры

Архитектура использует минимальные средства, достаточные для согласованных требований.
Каждая новая зависимость требует документированного объяснения необходимости
и причин, по которым существующих средств недостаточно. Авторизация, облачные
сервисы, Docker, сложные библиотеки и дополнительная инфраструктура не добавляются
без отдельной задачи и обоснования. Учебный масштаб проекта не оправдывает
усложнение ради предполагаемых будущих потребностей.

## Ограничения проекта

- TaskFlow — учебный веб-планировщик задач с уже реализованной и сохранённой в Git основой.
- Frontend: React, TypeScript, Vite, Tailwind CSS. Backend: Python, FastAPI.
  SQLite — будущее хранилище задач, вводимое только после прохождения этапов SDD.
- Интерфейс и документация ведутся на русском языке, код — на английском.
- Изменять файлы за пределами `practices/practice_05/taskflow` запрещено.
- Перед каждым использованием скриптов Spec Kit необходимо проверить вычисляемый
  корень проекта, пути выходных файлов и побочные записи. Все создаваемые и изменяемые
  файлы должны находиться внутри TaskFlow, а не в корне учебного репозитория.
  Если это не обеспечено, запуск запрещён до исправления способа вызова.
- Существующая основа — Dashboard, темы и проверка API — сохраняется;
  принятие конституции само по себе не разрешает реализацию новых функций.

## Порядок работы и проверки

1. Перед изменениями прочитать `AGENTS.md`, `README.md`, `docs/foundation.md`
   и эту конституцию; проверить разрешённый объём работы и состояние Git.
2. Для Kanban выполнить независимое проектирование, сохранить исходные спецификации,
   согласовать UI и единый API-контракт, обновить обе спецификации, затем подготовить
   план и задачи реализации. До выполнения этих условий реализацию не начинать.
3. Для изменений frontend выполнить из `frontend`: `npm run lint`,
   `npm run typecheck`, `npm run build`. Для изменений backend выполнить
   из `backend`: `python -m pytest` в подготовленном окружении.
   При изменениях задач или API дополнительно выполнить соответствующие
   проверки контракта и сквозные проверки. При изменении только документации
   проверить её полноту, согласованность и фактический список изменённых файлов.
4. Перед признанием этапа завершённым сопоставить результат со спецификациями,
   провести применимые ручные проверки и явно указать ограничения проверки.
5. Изменения сохраняются в Git по завершённым этапам только после отдельного
   разрешения пользователя на соответствующий коммит. Без такого разрешения
   подготовить проверяемый результат и список файлов, но не выполнять `commit`.
   Для `push` также требуется отдельное разрешение; разрешение на коммит его не заменяет.

## Управление конституцией

Конституция задаёт обязательные правила проектирования, реализации и проверки TaskFlow.
Спецификации, планы и задачи обязаны им соответствовать. Явные ограничения пользователя
на объём текущей работы и правила `AGENTS.md` соблюдаются при каждом действии;
обнаруженные противоречия фиксируются и согласуются до затронутой реализации.

Изменение конституции требует описания причины, затронутых принципов и влияния
на существующие спецификации, API-контракт и планы, а также согласования с пользователем.
Связанные документы обновляются только в разрешённом объёме; необходимое,
но не разрешённое обновление фиксируется для отдельного согласования.

Версия следует схеме MAJOR.MINOR.PATCH: MAJOR — несовместимое изменение или удаление
принципов; MINOR — добавление принципа, раздела или существенное расширение правил;
PATCH — уточнение формулировок без изменения смысла. При поправке обновляется дата
последнего изменения, исходная дата принятия сохраняется.

Проверка соответствия обязательна при согласовании спецификаций и API-контракта,
подготовке плана, завершении этапа реализации и ревью. Отклонения нельзя скрывать
успешными тестами: их необходимо устранить либо предварительно согласовать
изменение конституции.
