# Согласование Kanban UI и Backend

Дата: 2026-10-29. Статус: предварительный анализ координатора, обратная связь команд не получена. **Проект API-контракта — «Не согласован».** Документ не разрешает реализацию и не заменяет независимые v1.

## Основания и границы анализа

Первичные источники прочитаны полностью: [AGENTS.md, строки 1–6](../../AGENTS.md#L1-L6), [README.md, строки 1–32](../../README.md#L1-L32), [foundation.md, строки 1–4](../foundation.md#L1-L4), [Constitution, строки 1–122](../../.specify/memory/constitution.md#L1-L122), [UI v1](../../specs/001-kanban-ui/spec.md#L1), [Backend v1](../../specs/002-kanban-backend/spec.md#L1). Номера сверены с текущими v1 по содержимому, а не только по наличию строки.

[Constitution, 16–27](../../.specify/memory/constitution.md#L16-L27) требует сохранить первоначальные снимки и согласовать контракт и обе обновлённые спецификации до реализации. Обозначения категорий: **П** — прямое противоречие двух v1; **Н** — недостающее решение или незакреплённый контракт; **С** — совместимые требования, дополнительный спор о принципе не требуется. Совпадение требований не означает формального согласования командами. Конкретные новые решения ниже являются рекомендациями координатора.

## Предлагаемые решения

Рекомендуемый пакет: сохранить срок как пользовательскую функцию (A01–A02), принять простой серверный порядок вместо обещания конца колонки (A03), принять клиентский UUID и оптимистические версии (A08–A09), согласовать гарантию повторов и оценить долговечную отметку ID как один из вариантов (A10), принять формат ошибок Backend с явными UI-состояниями (A11–A12). Это изменения требований для будущих v2, а не объявление согласия.

Причины выбора: дата нужна уже описанным сценариям; сортировка по созданию не требует нового порядка; UUID позволяет повторить одно намерение создания; version защищает несколько вкладок; сохранённый факт использования ID закрывает случай, который одним GET устранить нельзя. Отметка ID не является восстановлением задачи, архивом или историей изменений. Это возможное усложнение архитектуры: требуются дополнительное долговечное состояние, атомарность удаления с отметкой, правила срока хранения и дополнительные проверки. В соответствии с [Constitution, 59–64](../../.specify/memory/constitution.md#L59-L64) обе команды должны оценить необходимость, стоимость и более простые альтернативы. Отметки не являются обязательным решением; требуемую гарантию повторов и способ её обеспечения ещё предстоит согласовать. Никаких новых зависимостей этим документом не предлагается.

## Проект единого API-контракта — Не согласован

Весь этот раздел — предложение. Основой служат [Backend, 110–117](../../specs/002-kanban-backend/spec.md#L110-L117), [Backend, 123–166](../../specs/002-kanban-backend/spec.md#L123-L166) и [UI, 129–147](../../specs/001-kanban-ui/spec.md#L129-L147); **новые относительно Backend v1 предложения**: due_date и отдельный необязательный вариант защиты повторов — запрет повторного создания удалённого ID с кодом task_id_retired. Все положения про отметки ID и task_id_retired ниже действуют только при выборе этого варианта обеими командами. UI v2 потребуется изменить правило позиции входящей карточки. Ни один из этих пунктов пока не принят обеими командами.

### Модель Task

Полный ответ всегда содержит все перечисленные поля. Неизвестные входные поля запрещены. Типы строгие: bool не число; числа/null не преобразуются в строки.

| Поле | JSON-тип | POST | PATCH | Правило |
| --- | --- | --- | --- | --- |
| id | string | обязательно | запрещено | UUID v4 в каноническом нижнем регистре, неизменяемый; клиент генерирует один раз на намерение |
| title | string | обязательно | необязательно | Обрезать крайние Unicode White_Space; после этого 1–200 кодовых точек; запрет U+0000–U+001F и U+007F |
| description | string | необязательно, default "" | необязательно | До 5000 кодовых точек, пробелы сохраняются; запрет управляющих как для title, кроме LF/CR/TAB; "" очищает |
| status | string | необязательно, default todo | необязательно | todo / in_progress / done; null и другой регистр запрещены |
| priority | string | необязательно, default medium | необязательно | low / medium / high; null запрещён |
| due_date | string или null | необязательно, default null | необязательно | Реальная григорианская дата YYYY-MM-DD, годы 0001–9999; null очищает, "" запрещено; прошлые даты разрешены |
| created_at | string | запрещено | запрещено | Серверный момент UTC RFC 3339 с Z, неизменяемый |
| updated_at | string | запрещено | запрещено | При создании равен created_at; меняется только при реальном изменении, не убывает |
| version | integer | запрещено | обязательно | Положительное целое, старт 1; ожидаемая версия для PATCH, версия результата в ответе |

Для воспроизводимости предложенное множество обрезаемых пробелов: U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028–U+2029, U+202F, U+205F, U+3000. Сначала обрезка title, затем проверка длины/управляющих. Это уточнение координатора, его нужно подтвердить Backend; конкретный алгоритм v1 не называет. Description не обрезается. В PATCH отсутствие пользовательского поля означает «не менять»; null разрешён только для due_date. Дублирующиеся заголовки допустимы.

Русские подписи: todo — «К выполнению», in_progress — «В работе», done — «Готово»; low — «Низкий», medium — «Средний», high — «Высокий». Любая пара статусов допустима, включая создание в done и возврат из done. Приоритет не ограничивает переходы.

Срок не содержит часовой пояс. UI выводит локализованную дату без преобразования в момент UTC; признак «Просрочено» равен `due_date < текущая локальная календарная дата устройства && status != done`. Сегодня не просрочено; пересчёт при смене дня и возвращении к экрану. Вычисляемый признак не хранится как поле задачи. Разные часовые пояса устройств могут давать разный признак — предлагаемая явно принимаемая семантика.

### Методы и форматы

Префикс `/api/tasks`. JSON для запросов/ответов, кроме 204. POST/PATCH требуют `Content-Type: application/json`, charset допустим. GET/DELETE без тела; неизвестные query-параметры запрещены. Авторизация, фильтры, пагинация и ручное упорядочивание не вводятся.

| Метод | Запрос | Успешный ответ |
| --- | --- | --- |
| POST /api/tasks | id, title; опционально description/status/priority/due_date | 201 + Task + Location: /api/tasks/{id}; допустимый повтор 200 + Task |
| GET /api/tasks | Без query | 200 `{"items":[Task],"total":N}`, все существующие задачи; N равен длине items; пусто: `{"items":[],"total":0}` |
| GET /api/tasks/{id} | Канонический UUID v4 | 200 + Task |
| PATCH /api/tasks/{id} | version и минимум одно пользовательское поле | 200 + полная Task; все поля применяются атомарно |
| DELETE /api/tasks/{id}?version=1 | Обязательная ожидаемая версия, десятичная запись положительного целого | 204 без тела |
| GET /api/health | Существующий запрос | 200 `{"status":"ok"}`; не доказывает доступность SQLite |

Список: created_at ASC, затем id ASC; UI группирует его по статусу с сохранением этого порядка внутри колонки. При редактировании или перемещении сортировочный ключ не меняется; конец колонки не гарантируется. Все задачи возвращаются без отсечения на 1000; 1000 — проверочный объём Backend.

Пример POST:

```json
{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","due_date":"2026-11-05"}
```

Пример Task в ответе 201 (Location содержит путь с тем же id):

```json
{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","description":"","status":"todo","priority":"medium","due_date":"2026-11-05","created_at":"2026-10-29T09:00:00Z","updated_at":"2026-10-29T09:00:00Z","version":1}
```

Пример PATCH: `{"version":1,"status":"in_progress","due_date":null}`. При реальном изменении ответ содержит version=2, новый updated_at, due_date=null и остальные сохранённые поля. Идентичные значения с актуальной version дают 200 без изменения version/updated_at. Пустое пользовательское изменение (`{"version":1}`) даёт 422.

### Изменения, удаление, повторы и SQLite

1. Проверка ожидаемой version и запись/удаление неделимы. Реальное изменение увеличивает version ровно на 1. При устаревшей версии существующей задачи — 409 version_conflict; при отсутствующей — 404 task_not_found. Никакого автоматического перезаписывания с новой версией.
2. POST сравнивается с нормализованным запросом с применёнными default, включая due_date. Если запись существует с version=1 и теми же пользовательскими полями, вернуть 200 без изменений времён. Другой запрос или version>1 — 409 task_id_conflict. Одновременные одинаковые создания дают одну запись, 201 и 200.
3. **Необязательный вариант усиления, только при выборе обеими командами**: после удаления хранить долговечную минимальную отметку использованного ID без содержимого задачи. POST с таким ID всегда 409 task_id_retired, никогда не восстанавливает задачу. Удаление задачи и сохранение отметки атомарны; отметка переживает перезапуск и не истекает в пределах жизни хранилища. GET такого ID остаётся 404, повтор DELETE — 404. Новый замысел создания требует нового UUID. Этот вариант требует оценки архитектурной стоимости обеими командами и не предписывается к реализации. При его отклонении команды могут согласовать другую политику, в том числе явно ограниченную гарантию повторов; до выбора политики контракт остаётся открытым.
4. Клиент удерживает ID и точный исходный запрос до разрешения неизвестного исхода POST; редактирование полей в этот период не становится молчаливым повтором другого запроса с тем же ID. Возможность восстановления такого намерения после перезагрузки браузера требует ответа UI; серверная гарантия относится к повтору того же ID.
5. Разрыв связи/503 не подтверждает ни успех, ни неуспех. После восстановления сначала GET. Для PATCH сохранить черновик, сравнить результат и предложить пользователю новое действие с прочитанной версией; совпадение значений не доказывает авторство изменения. Для DELETE GET 404 подтверждает отсутствие; GET 200 требует нового решения об удалении с актуальной версией. Для POST только при выборе варианта пункта 3 GET 404 позволяет повтор исходного запроса с тем же ID: удалённый ID будет безопасно отклонён. Без этого варианта GET 404 не разрешает безопасный повтор сам по себе; нужна отдельно согласованная политика. Не создавать автоматически новый ID для обхода конфликта.
6. Ошибочный запрос не меняет ни пользовательские, ни служебные поля. Подтверждённые задачи, изменения и удаления, а при выборе пункта 3 также отметки ID, сохраняются в локальной файловой SQLite после штатного/принудительного перезапуска. Путь определяется настройкой, а не cwd; отсутствующий файл создаётся, повреждённый не затирается пустым. Ошибка чтения не становится пустым списком. Это требования поведения, схема таблиц и зависимости не выбираются.

### Ошибки и UI-реакции

```json
{"error":{"code":"validation_error","message":"Проверьте поля запроса","details":[{"field":"due_date","code":"invalid_date","message":"Укажите существующую дату в формате ГГГГ-ММ-ДД"}]}}
```

code/message — строки, details — всегда массив объектов field/code/message со строковыми значениями. field — имя поля или `$` для запроса в целом. Все найденные ошибки полей сортируются по field, затем code. Сообщения русские, машинная логика опирается на code. SQL, пути и трассировки не возвращаются.

| HTTP / error.code | Условие | Реакция UI |
| --- | --- | --- |
| 400 invalid_json | Пустой/повреждённый JSON, повтор ключа | Общая ошибка, сохранить черновик |
| 415 unsupported_media_type | Неверный/отсутствующий Content-Type POST/PATCH | Общая ошибка, не повторять автоматически |
| 422 validation_error | Типы, длины, дата, enum, UUID/version, неизвестное поле/query, форма запроса | Известные редактируемые поля связать с ошибками и фокусом; version/id/$ и неизвестные поля — общая ошибка |
| 404 task_not_found | Корректный ID отсутствует | Сообщить отсутствие, обновить доску; черновик сохранить отдельно; для DELETE объяснить, что задача уже отсутствует |
| 409 version_conflict | Существующая задача другой версии | GET, показать актуальность, сохранить черновик, дать осознанно применить изменения или отказаться |
| 409 task_id_conflict | ID занят несовместимой записью | Не генерировать новый ID автоматически; прочитать задачу, разрешить намерение |
| 409 task_id_retired | Предложение: ID уже удалён | Сообщить, что старое создание не повторено; новый замысел только явным действием |
| 405 method_not_allowed | Метод существующего маршрута не поддержан; Allow обязателен | Общая ошибка |
| 503 storage_unavailable | Блокировка/ошибка доступа/невозможность подтвердить хранение | Состояние недоступности; после восстановления GET и правила разрешения исхода |
| 500 internal_error | Непредвиденная ошибка | Общая ошибка без объявления успеха; при неизвестном исходе записи — сверка через GET |

Порядок: метод/тип содержимого → JSON → форма/поля → наличие/занятость ID → версия → сохранение. Для конфликта версии details содержит field=version и указание перечитать задачу, не актуальную Task. Для новых ошибок предлагаются details `[{"field":"id","code":"retired","message":"Идентификатор ранее удалённой задачи нельзя использовать повторно"}]`; invalid_date показан выше. Полный словарь остальных вложенных details.code ещё требует утверждения (Q7); верхние коды в таблице уже перечислены как предложение.

UI сохраняет черновик при всех отказах записи. До подтверждения не объявляет успех; блокирует повторные действия над той же задачей во время ожидания. При 404/409 не обещает, что старое состояние является текущим: после сверки обновляет карточки/счётчики по серверу. При ошибке обновления оставляет последний снимок с предупреждением об устаревании. Неизвестный code, не-JSON ответ или сетевой сбой показываются общей русской ошибкой; отсутствие ответа не изображается как пустая доска. Обычный отказ перемещения сохраняет последний подтверждённый локальный снимок, а не гарантирует неизменность сервера в другой вкладке.
