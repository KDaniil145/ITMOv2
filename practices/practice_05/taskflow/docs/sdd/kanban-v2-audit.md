# Независимый аудит согласованности Kanban v2

Дата: 2026-10-30. **Текущий итог: «Документы согласованы, можно переходить к планированию». Открытых существенных проблем: 0.**

Первоначальный итог: «Требуются исправления», выявлены 2 существенные проблемы. Разделы 1–6 ниже сохранены как история первоначального аудита; их формулировки и цитаты относятся к состоянию до исправлений. Результаты повторной проверки и закрытие находок приведены в конце документа.

Проверены требования документов, а не работающее приложение. Планирование, реализация и тесты приложения не запускались. Единственный создаваемый файл — этот отчёт. Проверяемые документы не исправлялись.

## Источники и метод

Полностью прочитаны [AGENTS.md](../../AGENTS.md), [Constitution](../../.specify/memory/constitution.md), [API-контракт](kanban-api-contract.md), [итоговый журнал](kanban-decisions-final.md), [UI v2](../../specs/001-kanban-ui/spec-v2.md) и [Backend v2](../../specs/002-kanban-backend/spec-v2.md). Далее **C**, **U**, **B** означают соответственно контракт, UI v2 и Backend v2; ссылки указывают точные физические строки.

Применён принцип **claim → source → consistency**: сопоставлялись конкретные нормативные формулировки, таблицы, приоритеты и сценарии, включая конфликтующие условия одного запроса. Заявления авторов о собственной корректности ([U:175](../../specs/001-kanban-ui/spec-v2.md#L175), [B:210](../../specs/002-kanban-backend/spec-v2.md#L210)) не использовались как доказательство. Разрешённая отсылка UI к нормативному контракту не считается отсутствующим требованием: UI не обязан дублировать полную HTTP-схему ([U:5–7](../../specs/001-kanban-ui/spec-v2.md#L5-L7)).

Принятие R1–R6 зафиксировано со слов пользователя в [итоговом журнале:7](kanban-decisions-final.md#L7); отдельные недоступные финальные ответы команд не выдаются за самостоятельно проверенные. Аудит сравнивает доступные документы. Отличия от исторических v1, уже разрешённые журналом, не переоткрываются как новые конфликты.

Существенной считается неоднозначность, которая позволяет получить разные контрактные ошибки для одного запроса либо блокирует обязательный пользовательский сценарий. Отсутствие схемы таблиц/алгоритма транзакций, неутверждённая методика диагностики и отсутствие дополнительного исследования не являются такими проблемами.

## 1. Все девять полей Task

## 4. Существенные расхождения и минимальные исправления

### F-01. Общее правило null конфликтует с приоритетом read_only

**Claim.** [C:33](kanban-api-contract.md#L33): «null для title/description/status/priority/id/version — invalid_type». Ограничения «если поле разрешено в данной операции» в этой фразе нет.

**Противоречащие источники.** [C:241](kanban-api-contract.md#L241) требует read_only для известного запрещённого поля и запрещает проверять его значение как разрешённое. [C:23–31](kanban-api-contract.md#L23-L31) запрещает id в PATCH и version в POST. [B:129–134](../../specs/002-kanban-backend/spec-v2.md#L129-L134) воспроизводит приоритет и **прямо** задаёт `id:null в PATCH → read_only`. [U:133](../../specs/001-kanban-ui/spec-v2.md#L133) также принимает приоритеты C §6.3.

**Контрпример.** Валидный JSON PATCH существующей задачи с `{"version":1,"title":"Отчёт","id":null}`: по общей формулировке C:33 деталь id/invalid_type, по C:241 и B:134 — id/read_only. Аналогично POST с корректными id/title и `version:null`. HTTP в обоих толкованиях 422, но контрактный details.code различается; одна зависимая ошибка на поле не допускает вернуть оба кода. Это внутреннее противоречие общего контракта, проявившееся при сравнении с явным сценарием Backend v2, а не требование изменить согласованный приоритет R3.

**Последствие.** Разные валидаторы/контрактные проверки могут формально следовать разным обязательным фразам. Выбор C §6.3 по смыслу очевиден, однако точное правило C:33 нужно ограничить, а не полагаться на подразумеваемую оговорку.

**Минимальное предлагаемое исправление — в C:33:** «Для **разрешённых в операции полей** null допустим только у due_date; null у остальных разрешённых полей даёт invalid_type. Известные запрещённые поля дают read_only независимо от значения по §6.3». B:134 менять не требуется. После отдельного разрешения исправить только формулировку области применения, без изменения модели/словаря/приоритета R3.

### F-02. Запрет повторов до разрешения исхода блокирует безопасное восстановление POST

**Claim.** [U:80](../../specs/001-kanban-ui/spec-v2.md#L80): «Пока исход не разрешён, повторные отправки и противоречащие записи этого намерения блокируются».

**Противоречащие источники.** [U:77](../../specs/001-kanban-ui/spec-v2.md#L77) разрешает предложить повтор исходного POST после GET 404 и прямо запрещает считать 404 доказательством «никогда не создавалась». [C:178](kanban-api-contract.md#L178) и [B:108](../../specs/002-kanban-backend/spec-v2.md#L108) допускают этот повтор с тем же ID/телом. Блокировка повторного действия **во время ожидания** в [C:184](kanban-api-contract.md#L184) и [U:39](../../specs/001-kanban-ui/spec-v2.md#L39) уже отделена от восстановления неизвестного результата.

**Контрпример.** POST потерял ответ, после восстановления GET вернул 404. Клиент ещё не знает, не создалась задача или была создана и удалена: окончательно разрешить намерение помогает повтор с тем же ID, который вернёт Task либо task_id_retired. U:77 позволяет явный повтор, но U:80 блокирует его до разрешения именно того исхода, для разрешения которого повтор нужен. GET-ошибка также не должна разрешать запись; это отдельная ветка U:67, которая исправления не требует.

**Последствие.** При буквальном применении U:80 пользователь застревает с сохранённым намерением после успешной сверки 404. Ослабить только автоматические повторы недостаточно: текущая фраза блокирует и разрешённый пользователем повтор.

**Минимальное предлагаемое исправление — в U:80:** «Во время выполняющегося POST или GET сверки параллельные отправки и противоречащие записи этого намерения блокируются. После успешного GET 404 разрешён явный повтор неизменённого исходного POST с тем же UUID по S7.4; автоматического повтора и нового UUID нет». Сохранить блокировку при неудавшемся GET и завершение старого намерения на task_id_retired. Это уточнение жизненного цикла, не новая гарантия сервера.

## 5. Отдельная проверка замечания о десяти полях

Текущий UI v2 прочитан полностью, а не оценён по отчёту команды. Ошибочного замечания о якобы десяти полях **в текущем UI v2 нет**. История его удаления без предыдущей редакции не восстанавливалась; вывод относится к реально прочитанному файлу.
