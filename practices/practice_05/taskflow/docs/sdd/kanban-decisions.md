# Журнал согласования Kanban TaskFlow

Дата: 2026-10-29. Раунд: ответы независимых команд на Q1–Q10. **Контракт не согласован.** Это сопоставление позиций и предложения координатора, а не протокол утверждения спорных решений. Реализация и создание v2 не разрешаются этим документом.

## Первичные материалы и правила фиксации

- [Полный ответ UI-команды](ui-feedback-v1.md#L8-L122) сохранён из сообщения пользователя.
- [Полный ответ Backend-команды](backend-feedback-v1.md#L8-L269) сохранён из повторного сообщения пользователя. Первое сообщение обрывалось в Q5; анализ использует полный повторный ответ, а не догадки о продолжении.
- [Первоначальный UI v1](../../specs/001-kanban-ui/spec.md), [первоначальный Backend v1](../../specs/002-kanban-backend/spec.md), [предложения координатора прошлого раунда](kanban-alignment.md) остаются неизменными. Старый отчёт отражает состояние до этих ответов и не подменяет их.
- Основания: [Constitution, 16–27](../../.specify/memory/constitution.md#L16-L27) — неизменяемость v1 и согласование до реализации; [59–64](../../.specify/memory/constitution.md#L59-L64) — простота архитектуры; [31–41](../../.specify/memory/constitution.md#L31-L41) — границы доказательств проверок.

Категории: **«Позиции совпали»** — обе команды явно поддерживают одно правило; **«Есть совместимое решение с уточнениями»** — предложения можно объединить без взаимоисключающих требований, но уточнения необходимо перенести в будущие документы; **«Требуется дополнительное обсуждение»** — остаётся выбор гарантии, внешнего поведения или статуса критерия. Категория не заменяет утверждение единого контракта. Для смешанного вопроса ниже отдельно указано совпавшее ядро и незакрытая часть.

Точные ссылки относятся к физическим строкам сохранённых ответов. Формулировки «рекомендуется» и «предлагается» обозначают вывод координатора, а не дополнительный ответ команды.

## Оценка пяти отдельных вопросов

### Долговечные отметки UUID

Первичные позиции: [UI Q4](ui-feedback-v1.md#L33-L41), [Backend Q4](backend-feedback-v1.md#L58-L84). Рекомендация координатора — минимальные отметки **как кандидат**, если команды подтверждают сильную гарантию в пределах фактического состояния хранилища. Требование защищает не только повтор из текущей вкладки, но и задержанный запрос другой вкладки. Оно не обещает успешное восстановление любого исходного POST после редактирования записи.

| Вариант | Стоимость по материалам и оценке координатора | Ограничение |
| --- | --- | --- |
| Только минимальный UUID после удаления | Дополнительное долговечное состояние и проверка POST; уникальность, транзакционное удаление с отметкой; проверки гонок и сбоев; согласованное копирование состояния. Backend не видит необходимости в новой библиотеке. | Бессрочный рост по числу удалений, а не активных задач. Сброс/откат копии может убрать сведения об ID. |
| Полная квитанция/отпечаток POST | Выше объём сведений и сложность сравнения, политика выдачи старого ответа после изменения/удаления. | Для одного лишь запрета воскрешения избыточна; смысл нужен, если требуется более сильное распознавание исходной операции. |
| Истекающая отметка | Дополнительно срок, очистка и временные правила. | Простое забывание UUID возобновляет риск после окна; сильную гарантию не сохраняет без другого механизма отклонения старого запроса. |
| Нет отметок | Самая простая серверная модель. | Нужен явный отказ от сильной гарантии позднего повтора; UI-кнопки и GET 404 её не обеспечивают. |

Это соразмерное, но реальное усложнение относительно Backend v1, которое оценивают **обе** команды по принципу простоты. «Умеренная стоимость» — качественная оценка Backend, не замер объёма/времени и не доказательство отсутствия затрат. Число удалений и размеры страниц/индексов неизвестны, поэтому оценок в байтах, часах и процентах нет. Жизнь session-намерения UI и жизнь серверной отметки различны: закрытие вкладки не должно разрешать задержанный старый запрос с использованным ID.

Если вариант выбран, принимаются: POST удалённого ID → 409 task_id_retired; GET/DELETE → 404; отметка без содержимого задачи не истекает в пределах жизни хранилища; удаление и отметка неделимы. Проверки должны охватывать обе последовательности POST/DELETE и перезапуск. Нельзя обещать гарантию сверх фактически восстановленного состояния после отката копии. Пока R2 открыт, эти положения условны.

### Словарь ошибок

Источники: [шесть категорий UI и UX](ui-feedback-v1.md#L64-L72), [закрытый словарь Backend](backend-feedback-v1.md#L135-L155), [query version и диапазон](backend-feedback-v1.md#L161-L170), [приоритет валидации](backend-feedback-v1.md#L206).

Backend перечисляет 17 details.code, из которых retired условен выбором отметок; version_exhausted — отдельный **верхний** error.code, не восемнадцатый details.code. UI не запрещает более шести кодов, поэтому расширение требует подтверждения полезности, а не объявления конфликта. Координатор рекомендует принять детализацию Backend как проверяемое серверное объяснение, сохранив небольшое число UI-реакций:

| Предлагаемые details.code | Как UI использует | Цена и остаточное решение |
| --- | --- | --- |
| missing, invalid_type, invalid_length, invalid_value, invalid_date | Ошибка известного поля; общая ошибка для id/version/$ | Уже поддержаны по смыслу UI. Нужны одинаковые нарушения и русские сообщения. |
| invalid_format, invalid_characters, invalid_unicode | Известное поле либо общая ошибка; никаких специальных диалогов | Даёт полезную причину UUID/query/Unicode, но требует точных валидаторов и контрактных примеров. Не создавать отдельные UX-ветки для каждого кода. |
| unknown_field, read_only, unknown_parameter, duplicate_parameter, empty_update, body_not_allowed | Общая ошибка запроса, сохранить черновик | Полезно для диагностики интеграции; дополнительные обработчики и правила классификации на сервере. |
| stale_version, id_conflict, retired (условно) | Основное действие определяется верхним version_conflict/task_id_conflict/task_id_retired | Не разбирать message; retired включать только при выбранном Q4. |

Предложенное объединение до 6 кодов уменьшило бы словарь, но не устранило бы саму валидацию. Цена 17 кодов — точные классификации, стабильность и проверки, а не новая инфраструктура. Стандартный framework-ответ не становится согласованной оболочкой автоматически. Для 400/415/404/405/503/500 Backend предлагает details=[]; при 409 version_conflict — field=version/code=stale_version. Эти примеры уже приведены, не нужно повторно просить их у Backend.

Остаются реальные неоднозначности для R3: принадлежность field при query/body-ошибках; классификация известного пользовательского поля, запрещённого в конкретной операции (например id в PATCH), против неизвестного имени; приоритет дубликата/синтаксиса/диапазона version; пересечения invalid_characters/invalid_unicode/invalid_length. Предлагаемое правило координатора: одна зависимая ошибка на поле, независимые поля собираются; дубликат query проверяется до интерпретации его значения; тип до формата/диапазона. Команды должны утвердить оставшиеся соответствия. Полностью перечислять все побочные случаи новыми вопросами не требуется — нужна одна конечная таблица нарушений и примеры пересечений.

После URL-декодирования только ASCII [1-9][0-9]* для DELETE, ровно один version; лексически допустимое превышение максимума — invalid_value, неверная запись — invalid_format. Это совместимо с UI. Для UI фокус идёт по порядку формы, даже если сервер сортирует details по field/code. Непарный суррогат предлагается считать invalid_unicode, не ошибкой длины; отсутствие NFC/NFKC означает отсутствие скрытого изменения пользовательского текста.

### Диапазон версий и version_exhausted

Источник новой позиции: [Backend Q7, диапазон](backend-feedback-v1.md#L170). В UI-ответе нет отдельного согласия на предел 9007199254740991 или version_exhausted; нельзя приписывать его общему согласию с версиями.

Координатор считает безопасный integer-предел оправданной небольшой детализацией: UI должен передать ожидаемую версию без потери точности. Исчерпание почти недостижимо в учебной нагрузке, но добавление верхней границы требует определённого поведения. Рекомендуется не вводить сброс версий, BigInt/строковый тип или автоматическое пересоздание задач ради этого случая. Цена — проверка границы, один стабильный код и общая UI-ошибка, а не новая подсистема.

Предложение для R4 (ещё не утверждено):

- Вход PATCH.version — JSON integer без bool/преобразований, DELETE — каноническая строка query; диапазон обоих 1…9007199254740991, превышение → 422 validation_error с invalid_value.
- При корректном запросе сначала наличие задачи и совпадение версии. Отсутствующая задача → 404; несовпавшая версия → 409 version_conflict, даже если текущая версия максимальная.
- При актуальной максимальной версии реальный PATCH → 409 version_exhausted, details=[], без любых изменений данных и updated_at; no-op → 200 без изменений. Это новое уточнение координатора к предложению Backend, не цитата команды.
- DELETE с актуальной максимальной версией → 204: удаление не нуждается в увеличении версии. GET остаётся доступен. Не делать задачу неудаляемой из-за исчерпания.
- UI сообщает по-русски, что изменение невозможно из-за предела версии; сохраняет черновик и не делает бесконечный retry/молчаливую замену ID. Перечитывание само по себе не снимает предел.

Проверка будущей границы должна использовать подготовленное тестовое состояние, а не триллионы PATCH и не публичный диагностический API. Пока R4 открыт, код не считается принятым.

### Пять участников и статус SC-002

[UI v1 SC-002](../../specs/001-kanban-ui/spec.md#L154) содержит 4/5, 30 задач и 60/30/15 секунд. [UI Q10](ui-feedback-v1.md#L89-L102) предлагает перевести его в дополнительную проверку; [Backend Q10](backend-feedback-v1.md#L240-L250) отклоняет только роль обязательной **серверной** приёмки и допускает влияние сохранённого UI-критерия на готовность продукта. Это совместимые роли, но не одинаковое решение об обязательности продуктового критерия.

Рекомендация координатора — в будущем пакете разделить обязательную функциональную/интеграционную/доступную приёмку и отдельное исследование удобства; изменение статуса SC-002 требует явного утверждения R6. До этого исходный критерий существует и не может быть засчитан, исключён или объявлен дополнительным по одному предложению UI. Это не требует изменения Constitution и не разрешает менять v1.

Протокол UI совместим с Backend: пять реальных людей вне разработки; одинаковые 30 задач, сброс перед сессией, заранее подготовленный текст; без обучения действиям Kanban и подсказок; одна фиксированная конфигурация первого исследования; отдельно по каждому заданию ≥4/5 в 60/30/15 секунд; время до видимого подтверждённого результата, сеть фиксируется, но не вычитается. Подсказка не проходит критерий «без подсказок». Ширины и темы отдельно проверяются функциональной матрицей. Это маленькое формирующее исследование, не доказательство 80% успешности всех пользователей.

Стоимость — набор и организация пяти человек, подготовка одинакового состояния, проведение и протоколирование; фактическая доступность, длительность сессий и дата неизвестны. Роли предложены: координатор набирает, UI проводит/оценивает, Backend обеспечивает данные/сервер/измерение сети. Эти роли не означают, что люди уже приглашены или дата назначена. Если выбран обязательный статус и людей нет — «не проверено», общую готовность по этому критерию не заявлять; серверную корректность оценивать отдельно.

### Пороги производительности и проверка сбоев

Источники: [UI Q9](ui-feedback-v1.md#L80-L88), [Backend Q9](backend-feedback-v1.md#L218-L238), [Backend v1 SC-005](../../specs/002-kanban-backend/spec.md#L176). Это предложения, а не измеренные результаты.

| Показатель | Чья позиция | Оценка и предлагаемый статус до утверждения |
| --- | --- | --- |
| UI на 30 задачах доступен для взаимодействия ≤2 с после открытия | UI | Кандидат. Нужны начало открытия/конец готовности, режим первого/повторного открытия и условия запуска. |
| Видимая реакция UI ≤200 мс | UI | Кандидат для локального подтверждения начала действия/индикатора, а не обещание завершения серверной записи. Не противоречит API до 1 с. Значение смысла «реакции» нужно закрепить. |
| Задержка ответа 2 с | UI | Условие функциональной проверки ожидания и доступности остальных задач, не порог скорости успешной записи и не нарушение нормального benchmark. |
| ≥95 из 100 успешных ответов ≤1 с при 1000 задачах | Backend | Кандидат на обязательный порог отдельно для списка, GET задачи и реального PATCH. Отдельные серии по 100 — рекомендуемая конкретизация, не уже принятое правило. Ошибочные быстрые ответы не успех. |
| UI на 1000 задачах | UI | Диагностический функциональный прогон на зависания/доступность карточек без придуманного числового норматива. |

Пороги совместимы по предмету измерения; спор — об обязательности и воспроизводимости, а не о разнице чисел 30/1000 или 200 мс/1 с/2 с. Нужны оборудование, ОС/браузер, режим сборки/сервера, размеры текстов/ответа, прогрев, начало/конец замера и число прогонов. Рекомендация: опубликовать один короткий протокол среды; до его утверждения считать замеры диагностическими, а не подтверждать прохождение порогов. Для UI тоже нужно согласовать правило успешности серии, вместо неявной подмены единичным удачным запуском. Оборудование и показатели не выдуманы и не измерялись.

Реальные SQLite/новый процесс, 20 синхронизированных пар реальных изменений, 20 одинаковых POST, блокировка/отказ доступа/повреждение и сбои до/внутри/после commit — предложенная Backend функциональная приёмка, не стресс-бенчмарк. Нельзя смешивать её с нормальной серией задержек без искусственных отказов. Потеря ответа проверяется отдельно: сервер реально выполняет операцию, а ответ не достигает клиента; mock вместо сервера не доказывает обработку. Сбой до commit не должен оставлять смесь полей; после подтверждённого commit состояние обязано сохраняться. Для неопределённого момента до подтверждения допустимо целое старое/новое состояние в зависимости от завершения транзакции, не произвольная потеря подтверждённого изменения. Принудительный stop процесса не доказывает стойкость при отказе диска, питании или откате резервной копии.

## Дополнительные вопросы, необходимые для завершения согласования

Ниже только оставшиеся решения. Вопросы Q1, базовые Q2/Q3/Q5/Q6 и Q8 не переотправляются: ответы уже даны. Примеры ошибок и матрица гонок также получены. Каждой команде достаточно ответить по относящимся к ней R1–R6: принять конкретное предложение либо дать мотивированную альтернативу и ожидаемые результаты. Отсутствие возражений не является утверждением.

**R1 — Backend предлагает, UI подтверждает: единая форма времени.** Принимаем ли created_at/updated_at как UTC `YYYY-MM-DDTHH:mm:ss.SSSSSSZ` с ровно шестью цифрами дробной секунды и сортировку по значению момента, затем каноническому UUID? Это конкретизация координатора: Backend запросил единый формат/точность, но сам точность не выбрал. Сохранить created_at, не обещать хронологию создания при откате часов; updated_at при реальном изменении не убывает. Если шесть цифр неприемлемы, предложить одну другую точность без нового поля порядка. Ответ нужен для точного формата Task и воспроизводимой сортировки; UI не должен обрезать точность для собственного пересортировывания.

**R2 — обеим: выбор гарантии повторов.** Подтверждаете ли после оценки умеренной, но ненулевой стоимости минимальную неистекающую отметку UUID с атомарным удалением, 409 task_id_retired для POST, 404 для GET/DELETE и оговоркой о сбросе/откате хранилища? Это не обязанность до вашего выбора. При отказе назвать конкретную альтернативу и явную более слабую гарантию, а не обещать отсутствие воскрешения при забытом ID. Сеансовое удержание POST из UI Q3 остаётся совместимым отдельным ограничением клиента.

**R3 — Backend уточняет конечную таблицу, UI принимает или предлагает сжатие: ошибки.** Принимается ли 17-кодовый словарь Backend (retired условен R2) с общей реакцией UI на служебные/технические ошибки, отклонением непарных суррогатов и без NFC/NFKC? Если UI не видит пользы части кодов, указать только необходимые объединения. Backend закрепить field и классификацию пересечений: запрещённое известное поле против неизвестного, повторённый version против его неверного значения, неверный Unicode/управляющие/длина. Предложение: одна зависимая ошибка на поле; дубликат query до значения; далее тип, Unicode, обрезка title, длина, допустимые символы/формат/диапазон с явным порядком применимых проверок. Для даты тип до календаря; для тела GET/DELETE field=$/body_not_allowed. Нужна одна конечная карта, не новые UX-ветки. Канонический DELETE `[1-9][0-9]*` после декодирования и сбор независимых ошибок уже совместимы.

**R4 — обеим: предел версии и исчерпание.** Принимается ли 1…9007199254740991 для PATCH и DELETE; неверный входной диапазон → 422 invalid_value; при актуальном максимуме реальный PATCH → 409 version_exhausted/details=[], no-op → 200, DELETE → 204; наличие и конфликт версии проверяются раньше исчерпания? UI подтвердить общую русскую ошибку без автоматического retry/пересоздания; Backend — отсутствие изменений при отказе. Если отвергается новый код, назвать другое конечное поведение при максимуме, а не оставлять переполнение неопределённым.

**R5 — обеим: статус измерений в программе приёмки.** Какие из предложенных 2 с UI/200 мс реакции/95 из 100 API ≤1 с делаем обязательными сейчас, а какие оставляем диагностикой? Подтвердить единую среду/точки замера, отдельные серии списка/GET/реального PATCH по 100 успешных ответов и правило серии UI; назначить ответственного за фиксацию среды, не выдумывая её. Рекомендация при отсутствии условий — диагностика с публикацией результатов до отдельного утверждения порогов; функциональные сбои/сохранность при этом не становятся необязательными. Этот вопрос блокирует итоговую программу приёмки, а не JSON-форму API; если пороги выносятся за пределы API-контракта, это нужно явно закрепить в согласованном пакете требований.

**R6 — UI/координатор, Backend подтверждает границу ответственности: статус пяти участников.** Утверждаем ли предложение UI сделать будущий SC-002 дополнительным формирующим исследованием при обязательных воспроизводимых функциональных/интеграционных/доступных проверках? Либо сохраняем обязательным продуктовым критерием, который при отсутствии пяти реальных участников остаётся непроверенным и мешает заявить общую готовность? Серверную приёмку SC-002 не заменяет в обоих вариантах. Протокол/роли уже совместимы; повторно спрашивать их не нужно, а фактический набор/дата понадобятся только для проведения исследования. Это решение о приёмке будущих спецификаций, не о HTTP; его можно явно вынести в отдельный согласованный протокол, но нельзя молча снять обязательность v1.
