# Единый API-контракт Kanban TaskFlow

Статус: **окончательная запись принятого пакета Q1–Q10/R1–R6 для последующих UI v2 и Backend v2**. Основание принятия — сообщение пользователя о согласии обеих независимых команд в отдельных сессиях Codex; происхождение и сверка описаны в [итоговом журнале](kanban-decisions-final.md). Полные финальные ответы R1–R6 в файлах недоступны и самостоятельно не прочитаны. Правила R3 ниже воспроизводят опубликованный пакет, принятие которого подтверждено пользователем; отдельная недоступная финальная таблица не цитируется.

Документ задаёт поведение будущего API, а не описывает уже реализованные endpoint. Реализация, v2, план и задачи этим этапом не создаются. Сервер — источник истины; UI не обращается к SQLite напрямую. Поля/значения API английские, сообщения человеку русские. Интерфейс, ограничения проекта и отдельный цикл SDD сохраняются.

## 1. Общие правила обмена

Префикс задач `/api/tasks`. Пять операций: создание, список, чтение одной, частичное изменение, удаление. Отдельного маршрута перемещения нет. Одна личная доска, без авторизации, фильтров, поиска, пагинации и ручного порядка. Полная выдача не обрезается на 1000 задачах; 30 и 1000 — объёмы проверок, не лимит создания.

POST/PATCH требуют `Content-Type: application/json` (параметр charset допустим) и JSON-объект. Пустой/повреждённый JSON и повтор ключа JSON дают 400 invalid_json; синтаксически корректный массив/скаляр/null вместо объекта — 422 validation_error. Неявных преобразований типов нет. GET/DELETE тела не принимают; непустое тело — 422/body_not_allowed. JSON-ответы содержат JSON; у 204 тела нет и клиент не пытается разобрать JSON.

Query-параметры разрешены только для DELETE — обязательный version. В остальных операциях задачи query не предусмотрены. Неизвестные поля тела и query отклоняются; служебные поля разрешены только в явно указанных операциях. Неподдерживаемый метод существующего маршрута даёт 405 с Allow. Существующий GET /api/health сохраняет 200 `{"status":"ok"}` и не подтверждает доступность хранилища задач.

Основание: [Backend v1, операции/форматы](../../specs/002-kanban-backend/spec.md#L123-L133), [Backend Q7–Q8](backend-feedback-v1.md#L133-L216), [UI Q8](ui-feedback-v1.md#L73-L79).

## 2. Task и входные модели

Полная Task во всех успешных ответах одной задачи содержит **все девять полей** таблицы. Серверные id/created_at не изменяются. Пользовательские поля: title, description, status, priority, due_date. Title и description — текст, не исполняемая разметка.

| Поле | JSON-тип и правило полного ответа | POST | PATCH |
| --- | --- | --- | --- |
| id | string, канонический UUID v4 в нижнем регистре, корректный variant | Обязательно, задаёт клиент | Запрещено; ID в пути |
| title | string; после обрезки 1–200 Unicode-кодовых точек | Обязательно | Необязательно |
| description | string, 0–5000 Unicode-кодовых точек | Необязательно, default "" | Необязательно; "" очищает |
| status | string: todo / in_progress / done | Необязательно, default todo | Необязательно |
| priority | string: low / medium / high | Необязательно, default medium | Необязательно |
| due_date | string YYYY-MM-DD или null | Необязательно, default null | Необязательно; null очищает |
| created_at | string UTC, `YYYY-MM-DDTHH:mm:ss.SSSSSSZ` | Запрещено, сервер | Запрещено |
| updated_at | string UTC, тот же формат с ровно шестью дробными цифрами | Запрещено, сервер | Запрещено |
| version | JSON integer, 1…9007199254740991 | Запрещено, сервер начинает с 1 | Обязательно, ожидаемая версия |

В PATCH кроме version должно быть хотя бы одно пользовательское поле. Отсутствующее пользовательское поле сохраняет значение; default при PATCH не применяется. `{ "version": 1 }` даёт 422 с empty_update. Передача пользовательского поля с прежним значением может быть no-op. Сначала определяется, разрешено ли поле для текущей операции: неизвестное поле даёт unknown_field, известное запрещённое — read_only независимо от его значения. Для разрешённых полей null допустим **только** у due_date; если null для разрешённого поля недопустим, возвращается invalid_type. Например, id:null в PATCH → read_only, а title:null в PATCH → invalid_type. Bool не считается integer; строки/числа/bool/null не преобразуются друг в друга. Одинаковые заголовки разных задач разрешены.

UUID используется в одном каноническом формате и в POST.id, и в пути: например `8b28fe8b-7a58-4c84-a733-1135f31237fe`. Клиент создаёт новый UUID только для нового намерения создания; повтор того же намерения использует прежний ID и исходное тело. Сервер проверяет форму, UUID version/variant, но не качество генератора случайных чисел клиента.

Основание модели: [Backend v1, поля](../../specs/002-kanban-backend/spec.md#L106-L119), [Backend Q1](backend-feedback-v1.md#L12-L28), [Q3](backend-feedback-v1.md#L42-L56), [Q6](backend-feedback-v1.md#L115-L131), [Q7, предел version](backend-feedback-v1.md#L170), [итог R1–R4](kanban-decisions-final.md#r1).

### 2.1. Строки и Unicode

Title обрезается только с краёв по множеству White_Space:

`U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028–U+2029, U+202F, U+205F, U+3000`.

После обрезки title имеет 1–200 кодовых точек; U+0000–U+001F и U+007F запрещены. Description не обрезается, до 5000 кодовых точек; тот же запрет управляющих, кроме LF/CR/TAB. Поэтому крайний TAB title удаляется, внутренний TAB запрещён, TAB в description допустим. U+FEFF не входит в обрезку. NFC/NFKC, изменение регистра и схлопывание внутренних пробелов не выполняются. Непарные суррогаты отклоняются как invalid_unicode.

Длина — число Unicode-кодовых точек, не байтов, UTF-16 единиц и не графем. Валидная surrogate-пара представляет одну кодовую точку. UI считает по тому же правилу и не обещает, что одна кодовая точка равна одному видимому символу. Те же преобразования применяются при записи, определении no-op и сравнении повторного POST.

Основание: [принятый White_Space из проекта](kanban-alignment.md#L60), [UI Q6](ui-feedback-v1.md#L55-L61), [Backend Q6](backend-feedback-v1.md#L115-L131), [пакет R3](kanban-decisions.md#L117), [подтверждение R3](kanban-decisions-final.md#r3).

### 2.2. Статусы, приоритеты и переходы

| Значение API | Русская подпись | Правило |
| --- | --- | --- |
| todo | К выполнению | Статус по умолчанию |
| in_progress | В работе | Допустимый статус |
| done | Готово | Допустимый статус, возврат разрешён |
| low | Низкий | Приоритет |
| medium | Средний | Приоритет по умолчанию |
| high | Высокий | Приоритет |

Только перечисленные значения в точном регистре допустимы. Любой статус переходит в любой другой без дополнительных условий; установка того же статуса допустима. Создать можно сразу в любом статусе, включая done. Приоритет и срок не ограничивают переходы. Перемещение — PATCH с ожидаемой version и целевым status; не задаёт положение карточки внутри колонки.

Основание: [Backend v1, FR-005/006](../../specs/002-kanban-backend/spec.md#L95-L96), [UI Q8](ui-feedback-v1.md#L73-L79), [Backend Q8](backend-feedback-v1.md#L208-L216).

### 2.3. Календарная дата и служебные моменты

Due_date — существующая григорианская дата в точной форме YYYY-MM-DD, годы 0001–9999. Пустая строка, timestamp, сокращённый формат, пробелы и невозможные даты отклоняются как invalid_date (для строкового типа). Отсутствие срока — null, не "". Прошлые даты разрешены.

Дата не преобразуется в UTC. UI вычисляет «Просрочено», когда due_date меньше локальной календарной даты устройства и status != done; сегодня не просрочено. Пересчёт при смене дня, возвращении во вкладку и изменении соответствующего состояния; смена часового пояса может изменить признак. Вычисляемый признак не поле API и не хранится в SQLite. UI позволяет ручной ввод года в согласованном диапазоне.

Created_at/updated_at — серверные моменты UTC с суффиксом Z и ровно шестью дробными цифрами, например `2026-10-29T09:00:00.123456Z`. При создании равны; created_at неизменяем. Updated_at меняется только при реальном изменении, не убывает; no-op оставляет его прежним. Откат системных часов не даёт гарантии, что новая задача окажется последней в сортировке.

Основание: [UI Q1](ui-feedback-v1.md#L10-L16), [Backend Q1–Q2](backend-feedback-v1.md#L12-L40), [Backend v1, updated_at/version](../../specs/002-kanban-backend/spec.md#L98), [R1](kanban-decisions-final.md#r1).

## 3. Методы, успешные запросы и ответы

| Метод и путь | Вход | Успех |
| --- | --- | --- |
| POST /api/tasks | Объект с id, title; необязательно description, status, priority, due_date | 201 + полная Task, Location: /api/tasks/{id}; допустимый повтор — 200 + Task |
| GET /api/tasks | Без query и тела | 200 `{"items":[Task],"total":N}` |
| GET /api/tasks/{id} | Канонический UUID v4 в пути, без query/тела | 200 + полная Task |
| PATCH /api/tasks/{id} | Объект с version и минимум одним пользовательским полем | 200 + полная Task после атомарной операции, включая no-op |
| DELETE /api/tasks/{id}?version=1 | UUID в пути, ровно один обязательный query version, без тела | 204 без тела |

GET списка возвращает все существующие задачи, без отметок удалённых ID. Total — целое число, равное длине items; пустой результат ровно `{"items":[],"total":0}`. Ошибку хранилища нельзя выдавать как пустую доску. Список упорядочен по **значению момента** created_at ASC, затем каноническому id ASC. UI группирует по status, сохраняя относительный серверный порядок без потери микросекунд; не пересортировывает по времени, усечённому до миллисекунд. Изменение текста/приоритета/срока/статуса не меняет ключ сортировки. При переносе UI объявляет целевую колонку, обеспечивает фокус и видимость карточки; временное размещение в конце с перестановкой после reload не соответствует контракту.

Основание: [Backend v1, 127–133](../../specs/002-kanban-backend/spec.md#L127-L133), [UI Q2](ui-feedback-v1.md#L17-L23), [Backend Q8](backend-feedback-v1.md#L208-L216), [R1](kanban-decisions-final.md#r1).

### 3.1. Примеры

POST /api/tasks:

```json
{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","due_date":"2026-11-05"}
```

201, `Location: /api/tasks/8b28fe8b-7a58-4c84-a733-1135f31237fe`:

```json
{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","description":"","status":"todo","priority":"medium","due_date":"2026-11-05","created_at":"2026-10-29T09:00:00.123456Z","updated_at":"2026-10-29T09:00:00.123456Z","version":1}
```

GET /api/tasks при этой единственной задаче:

```json
{"items":[{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","description":"","status":"todo","priority":"medium","due_date":"2026-11-05","created_at":"2026-10-29T09:00:00.123456Z","updated_at":"2026-10-29T09:00:00.123456Z","version":1}],"total":1}
```

PATCH /api/tasks/8b28fe8b-7a58-4c84-a733-1135f31237fe:

```json
{"version":1,"status":"in_progress","due_date":null}
```

200 после реального изменения:

```json
{"id":"8b28fe8b-7a58-4c84-a733-1135f31237fe","title":"Подготовить отчёт","description":"","status":"in_progress","priority":"medium","due_date":null,"created_at":"2026-10-29T09:00:00.123456Z","updated_at":"2026-10-29T09:01:00.000001Z","version":2}
```

DELETE того же ID с `?version=2` → 204 без тела. GET после него → 404 task_not_found. Повтор исходного POST → 409 task_id_retired, а не новое создание.

## 4. Версии, атомарность и конфликты

Version относится ко всей Task, включая due_date. Сравнение ожидаемой version и изменение/удаление — одна неделимая операция. Неуспешная валидация, конфликт или исчерпание версии не меняют пользовательские и служебные поля.

После полной валидации запроса:

1. Нет задачи → 404 task_not_found независимо от корректной ожидаемой версии.
2. Есть задача, версия отличается → 409 version_conflict, даже если переданные поля совпадают с текущими.
3. Актуальная версия и все переданные значения после нормализации прежние → 200 no-op, version/updated_at без изменения.
4. Актуальная версия, реальное изменение, version < 9007199254740991 → все поля атомарно, version +1, updated_at не убывает, 200 Task.
5. Актуальная максимальная версия, реальный PATCH → 409 version_exhausted с details=[], никаких изменений. No-op на максимуме остаётся 200. DELETE на актуальном максимуме остаётся 204.

Некорректный входной version проверяется **до поиска задачи**: 422, даже если ID отсутствует. PATCH.version — JSON integer без bool и преобразований в диапазоне 1…9007199254740991. DELETE.version после стандартного URL-декодирования — ASCII `[1-9][0-9]*`, в том же диапазоне. `01`, `+1`, `1.0`, `1e0`, пробелы, пустое значение и Unicode-цифры не принимаются; повтор параметра отклоняется даже при одинаковых значениях. Лексически допустимое превышение диапазона — invalid_value, нарушение записи — invalid_format.

| Конкурирующие операции исходной версии | Допустимый результат |
| --- | --- |
| Два реальных PATCH | Один 200; другой 409 version_conflict |
| Два no-op | Оба могут вернуть 200 |
| No-op перед реальным PATCH | Оба могут вернуть 200, версию увеличивает только реальный PATCH |
| Реальный PATCH перед старым no-op | PATCH 200; старый no-op 409 |
| Реальный PATCH перед DELETE | PATCH 200, DELETE 409 |
| DELETE перед реальным PATCH | DELETE 204, PATCH 404 |

Повтор DELETE отсутствующей задачи с корректным запросом → 404, эффект — отсутствие задачи. Подтверждение UI требуется до удаления; после 409 оно запрашивается заново для актуальных сведений. Серверная версия не заменяется автоматически клиентом.

Основание: [Backend Q5](backend-feedback-v1.md#L86-L113), [UI Q5](ui-feedback-v1.md#L42-L54), [Backend Q7](backend-feedback-v1.md#L170), [R4](kanban-decisions-final.md#r4).

## 5. Повторы POST, удалённые UUID и неизвестный результат

### 5.1. Серверные правила

- GET безопасно повторять, он не меняет данные.
- Новый POST с валидным незанятым и неотмеченным ID создаёт Task версии 1: 201.
- Если Task существует с version=1 и её **все пользовательские поля** равны нормализованному POST с применёнными default (включая due_date), вернуть 200 существующую Task без изменения времён/версии. Пропуск due_date и null эквивалентны; пропуск description и "" эквивалентны.
- Другие пользовательские поля либо version>1 → 409 task_id_conflict, даже если после редактирований значения вернулись к исходным. Равенство заголовка само по себе не определяет дубликат.
- Два одновременных одинаковых POST нового ID до дальнейших действий дают ровно одну Task: один 201, другой 200.
- При удалении задачи атомарно сохраняется минимальная долговечная отметка UUID. Отметка не содержит пользовательского содержимого, не истекает в течение жизни сохранённого состояния хранилища. Старый POST этого ID → 409 task_id_retired, независимо от пользовательских полей валидного запроса. GET и повтор DELETE такого ID → 404.
- DELETE и запись отметки не оставляют промежуточного состояния «задача удалена, отметки нет». При гонке с POST после зафиксированного удаления POST не создаёт задачу; POST, завершившийся до удаления, может вернуть существующую задачу по обычным правилам. Порядок операций не даёт разрешения воскрешать ID.
- Сброс/восстановление старой копии ограничивает гарантию фактически сохранёнными сведениями. Гарантии сверх этого состояния не заявляются. Отметки и задачи сохраняются согласованно.

Основание: [Backend v1, повторы](../../specs/002-kanban-backend/spec.md#L161-L166), [Backend Q1, сравнение due_date](backend-feedback-v1.md#L26), [Backend Q4](backend-feedback-v1.md#L58-L84), [R2](kanban-decisions-final.md#r2). Разрешение воскрешения из v1 заменено R2, остальные правила совпавшего POST версии 1 сохранены.

### 5.2. Жизненный цикл намерения UI

Клиент удерживает один UUID и исходный POST после первой отправки до разрешения исхода. Повтор использует тот же ID/тело; изменённый черновик не превращается незаметно в другое создание с прежним ID. При доступном сеансовом хранилище намерение переживает перезагрузки открытой вкладки; при недоступности — только память, с понятным предупреждением при неизвестном результате. После разрешения исхода запись намерения удаляется. Восстановление не отправляет POST автоматически.

После закрытия вкладки восстановление намерения не гарантируется; при следующем открытии сначала загружается серверная доска. Автоматический POST или новый UUID для обхода конфликта запрещены. Новый замысел создания — только осознанное действие пользователя. Это не гарантия отсутствия двух вручную созданных задач с одинаковым содержимым и разными UUID.

### 5.3. Сверка после разрыва связи/503/500/непонятного ответа

Не объявлять ни подтверждённый успех, ни доказанный неуспех записи. Сохранить черновик и выполнить GET после восстановления:

| Операция | Действие после GET |
| --- | --- |
| POST | GET 200 — сверить задачу; GET 404 — повтор исходного POST с тем же ID защищён отметками от воскрешения, но может дать task_id_retired. Новый ID автоматически не создавать. |
| PATCH | Сохранить черновик, показать актуальные/отличающиеся поля; пользователь выбирает актуальную версию либо явно применяет выбранные изменения с её version. Совпадение значений не доказывает авторство. Новый 409 обрабатывается заново. |
| Перемещение | После 409/сверки статус уже целевой — сообщить текущее состояние, без лишнего PATCH; другой — предложить осознанный перенос с актуальной версией. |
| DELETE | GET 404 подтверждает отсутствие: «Задача уже отсутствует», не «Вы удалили задачу». GET 200 требует нового подтверждения актуального удаления. |
| GET не удался | Последний снимок остаётся с предупреждением об устаревании; разрешение исхода не закончено. |

При 404 отсутствующая задача удаляется из подтверждённого состояния после сверки; черновик остаётся отдельно. Его перенос в новую задачу возможен только явным действием. При обычном отказе UI сохраняет последний подтверждённый снимок, не обещая неизменность сервера в другой вкладке. Во время ожидания повторные действия над этой задачей блокируются, остальные задачи доступны. Изменение карточек/счётчиков и объявление успеха — после подтверждённого результата.

Основание: [UI Q3–Q5](ui-feedback-v1.md#L24-L54), [UI Q7, неизвестный исход](ui-feedback-v1.md#L70), [Backend Q5, потеря ответа и гонки](backend-feedback-v1.md#L100-L113), [UI v1, повторные нажатия](../../specs/001-kanban-ui/spec.md#L92-L95).

## 6. Ошибки

Оболочка всех предусмотренных ошибок задач:

```json
{"error":{"code":"validation_error","message":"Проверьте поля запроса","details":[{"field":"due_date","code":"invalid_date","message":"Укажите существующую дату в формате ГГГГ-ММ-ДД"}]}}
```

Error.code/message — строки; details всегда массив объектов со строковыми field/code/message. Field содержит имя затронутого поля/параметра, для запроса целиком — `$`. Известное редактируемое поле UI связывает с формой; id/version/$, неизвестные и прочие служебные ошибки показываются общим сообщением. Фокус на первом ошибочном поле **в порядке формы**, независимо от сортировки details. Верхний error.code определяет реакцию, message не разбирается машинно. Русские сообщения не раскрывают SQL, внутренние пути или трассировки. Неизвестный code/поле или не-JSON ответ отображаются общей русской ошибкой без вывода технического содержимого и без потери черновика.

### 6.1. HTTP и верхний error.code

| HTTP | error.code | Условие / details |
| --- | --- | --- |
| 400 | invalid_json | Пустой/повреждённый JSON POST/PATCH или повтор ключа JSON; [] |
| 415 | unsupported_media_type | Неверный/отсутствующий Content-Type POST/PATCH; [] |
| 422 | validation_error | Неверная форма/тип/поле/параметр/UUID/дата/version; details по словарю |
| 404 | task_not_found | Корректный запрос к отсутствующей задаче; [] |
| 409 | version_conflict | Версия существующей задачи не совпала; field=version, code=stale_version |
| 409 | task_id_conflict | Занятый ID не удовлетворяет правилу повтора POST; field=id, code=id_conflict |
| 409 | task_id_retired | ID присутствует в долговечной отметке удаления; field=id, code=retired |
| 409 | version_exhausted | Актуальная максимальная версия и реальный PATCH; [] |
| 405 | method_not_allowed | Неподдерживаемый метод существующего маршрута; Allow, details=[] |
| 503 | storage_unavailable | Невозможность прочитать или подтвердить сохранение, включая блокировку/ошибки доступа; [] |
| 500 | internal_error | Непредвиденная ошибка без раскрытия внутренностей; [] |

### 6.2. Закрытый словарь 17 details.code

| details.code | Значение |
| --- | --- |
| missing | Отсутствует обязательное поле или параметр |
| invalid_type | Неверный JSON-тип, в том числе запрещённый null |
| invalid_length | Недопустимая длина строки |
| invalid_value | Неверный enum или значение вне допустимого диапазона |
| invalid_format | Неверный UUID или синтаксис query version |
| invalid_date | Строка срока нарушает формат, диапазон лет или календарь |
| invalid_characters | Запрещённые управляющие символы |
| invalid_unicode | Непарный суррогат |
| unknown_field | Неизвестное имя поля тела |
| read_only | Известное поле, запрещённое в этой операции, например created_at в POST или id в PATCH |
| unknown_parameter | Неизвестный query-параметр |
| duplicate_parameter | Query-параметр повторён, даже с одинаковыми значениями |
| empty_update | PATCH не содержит пользовательских полей |
| body_not_allowed | Непустое тело GET/DELETE, field=$ |
| stale_version | Ожидаемая версия существующей задачи не совпала |
| id_conflict | ID занят несовместимой записью |
| retired | ID был удалён и отмечен |

### 6.3. Приоритеты и сбор ошибок

Порядок из принятого опубликованного R3 и Backend Q7:

1. Метод и тип содержимого → разбор JSON → форма/поля/параметры → наличие/занятость/отметка ID → версия → no-op/исчерпание → сохранение. Ошибка раннего этапа не подменяется ошибкой позднего: неверный Content-Type раньше invalid_json, неверная version раньше 404.
2. В теле имя, отсутствующее в модели операции и не являющееся известным полем Task, — unknown_field; известное, но запрещённое в операции, — read_only. Значение запрещённого/неизвестного поля не проверяется как разрешённое поле; независимые ошибки разрешённых полей собираются.
3. Для разрешённого поля: обязательность → тип → корректность Unicode → применимая обрезка title → длина → применимая проверка управляющих символов/формата/значения/диапазона. Зависимые проверки после первой ошибки поля не выполняются. Title/description: Unicode раньше длины, длина раньше запрета управляющих; due_date: тип/Unicode до проверки даты; status/priority — точный enum; id — канонический UUID v4/variant.
4. Для DELETE version: missing при отсутствии; duplicate_parameter до интерпретации повторённых значений; далее канонический синтаксис, затем диапазон. Повтор `version=01&version=1` — duplicate_parameter, не invalid_format; единственный `01` — invalid_format, единственное каноническое число выше максимума — invalid_value. Неизвестные query дают unknown_parameter. GET/DELETE с непустым телом — body_not_allowed на `$`.
5. Одна зависимая ошибка на поле, все обнаруженные независимые ошибки других полей собираются. Details сортируется по field, затем code. Повтор JSON-ключа — 400 invalid_json, не duplicate_parameter.
6. После успешной валидации: отсутствие задачи имеет приоритет над сравнением корректной version; несовпадение версии — над no-op и исчерпанием. Актуальный no-op разрешён даже на максимуме. Все записи и проверки гонок атомарны.

Основание: [Backend v1, оболочка и этапы](../../specs/002-kanban-backend/spec.md#L141-L157), [Backend Q7](backend-feedback-v1.md#L133-L206), [опубликованный пакет R3](kanban-decisions.md#L117), [подтверждение принятия R3](kanban-decisions-final.md#r3), [R4](kanban-decisions-final.md#r4). Порядок не выдаётся за самостоятельно прочитанную приватную финальную таблицу Backend; основание — принятие пользователем опубликованного пакета целиком.

### 6.4. Примеры конфликтов и сервиса

409 version_conflict:

```json
{"error":{"code":"version_conflict","message":"Задача была изменена","details":[{"field":"version","code":"stale_version","message":"Загрузите актуальную задачу перед новым изменением"}]}}
```

409 task_id_retired:

```json
{"error":{"code":"task_id_retired","message":"Задача с этим идентификатором ранее удалена","details":[{"field":"id","code":"retired","message":"Не повторяйте создание удалённой задачи"}]}}
```

409 version_exhausted:

```json
{"error":{"code":"version_exhausted","message":"Достигнут предел версии задачи, изменение невозможно","details":[]}}
```

404 и 503:

```json
{"error":{"code":"task_not_found","message":"Задача не найдена","details":[]}}
```

```json
{"error":{"code":"storage_unavailable","message":"Хранилище задач временно недоступно","details":[]}}
```

Тексты примеров иллюстрируют русские сообщения; контрактным идентификатором остаётся code. Конфликт версии не содержит актуальную Task: её получают отдельным GET. Автоматическая подстановка новой версии, повтор при version_exhausted и создание нового ID для обхода конфликтов не выполняются.

## 7. SQLite и границы подтверждения

Локальная файловая SQLite хранит Task и минимальные отметки удалённых UUID. Подтверждённые записи/изменения/удаления/отметки сохраняются после штатного и принудительного перезапуска. Успех записи отдаётся после надёжного сохранения; операция не оставляет частичных полей или разрыва между удалением и отметкой. Путь определяется настройкой приложения, а не cwd. Новый отсутствующий файл создаёт пустое хранилище; существующий повреждённый файл не заменяется пустым. Ошибки доступа/блокировки не маскируются как 404 или пустая выдача.

Конкретные таблицы, индексы, зависимости и механика транзакций относятся к последующему проектированию, а не добавляются этим контрактом. Отметка не архив и не история: содержимое задачи не сохраняется, восстановления/отмены удаления нет. Гарантии не распространяются сверх фактически сохранённого состояния после сброса или отката копии. Проверка перезапуска процесса не доказывает поведение при отключении питания или отказе диска.

Основание: [Backend v1, FR-001–009](../../specs/002-kanban-backend/spec.md#L91-L99), [Backend Q4](backend-feedback-v1.md#L58-L84), [Backend Q9](backend-feedback-v1.md#L218-L238), [R2](kanban-decisions-final.md#r2).

## 8. Обязательная проверяемость и необязательные исследования

Обязательны автоматические проверки бизнес-правил/границ, каждого метода и класса ошибки, форматов/типов/приоритетов, реальная файловая SQLite и новый процесс после штатного/принудительного завершения, сохранность всех полей/сроков/удалений/отметок, отсутствие частичных результатов. Конкуренция проверяется 20 синхронизированными парами реальных изменений одной версии и 20 парами одинаковых POST; последовательная отправка не доказывает гонку. Отдельно no-op, PATCH/DELETE в обоих порядках и исчерпание версии.

Обязательны отказы чтения/записи при блокировке/ошибке доступа, повреждённый файл без перезаписи, управляемые сбои до/внутри/после сохранения и потерянный ответ. Проверять целое состояние, а не только код ответа; искусственная потеря ответа не заменяет реальный backend и не требует нового публичного диагностического API.

Сквозные сценарии с реально работающим backend: создание → срок → чтение/редактирование → перенос/порядок → обновление клиента и перезапуск сервера → удаление; конфликты двух вкладок, удаление извне, потеря ответа POST/PATCH/DELETE, повтор после удаления/перезапуска, ошибки Unicode/дат/полей, отказ GET при сверке. UI: обе темы, 390/1440 px, клавиатура/сенсор, фокус/видимость/объявления, формы/черновик, загрузка/пустое/ошибка; существующая основа сохраняется. Подмена backend подтверждает только отдельное поведение UI, не интеграцию.

По R5 числовые показатели скорости **диагностические** до утверждения воспроизводимой методики: UI 30 задач ≤2 с до доступности и ≤200 мс до видимой реакции, Backend при 1000 задач ≥95/100 ≤1 с, UI-прогон на 1000. Эти цифры не SLA и не обязательный проходной барьер. Задержка ответа 2 с используется для проверки ожидания/блокировки повторов, а не для подмены benchmark. Замеры публикуются с условиями; быстрый ошибочный ответ не успешное измерение.

По R6 пять участников — дополнительное исследование удобства. Если не проводилось, результат **«Не проводилось»**. При проведении: пять реальных людей вне разработки, одинаковые 30 задач/условия, без подсказок, ≥4/5 отдельно по заданиям 60/30/15 с до видимого подтверждённого результата, сеть фиксируется отдельно, но не вычитается; протокол UI Q10. Результат не обобщается на всех пользователей и не заменяет серверную корректность. В этом этапе исследование не выполнялось.

Основание: [Constitution, 31–41](../../.specify/memory/constitution.md#L31-L41), [UI Q9–Q10](ui-feedback-v1.md#L80-L102), [Backend Q9–Q10](backend-feedback-v1.md#L218-L250), [R5](kanban-decisions-final.md#r5), [R6](kanban-decisions-final.md#r6). Соответствие UI v2/Backend v2 этому документу нужно проверить отдельно до следующего разрешённого цикла SDD; успешные тесты будущей реализации не заменяют эту проверку.

## 9. Результат сверки claim → source → consistency

[Итоговый журнал](kanban-decisions-final.md) содержит полную таблицу изменений Q1–Q10 и основания R1–R6. Здесь проверены критические стыки:

| Claim | Source | Consistency |
| --- | --- | --- |
| Task содержит due_date и повторы сравнивают её | Backend Q1, UI Q1 | Отсутствие/null едины; срок не timestamp и не updated_at. Исключение Backend v1 заменено принятой позицией. |
| Серверный порядок не меняется от переноса | Backend Q2, UI Q2, R1 | Ожидание конца колонки из UI v1 снято; микросекунды не теряются при группировке. |
| Версия проверяется до no-op/исчерпания | Backend Q5/Q8 и R4 | Старый no-op — конфликт; два актуальных no-op могут пройти. Удаление максимальной версии разрешено. |
| Удалённый ID нельзя повторно создать | Backend Q4, UI Q4 и R2 | Устранено воскрешение из v1; GET 404 не требует различать историю ID, POST защищён отметкой. |
| 17 details.code и приоритеты не зависят от текста message | Backend Q6/Q7, опубликованный R3, переданное принятие R3 | Ошибки полей и общие различаются по field; верхний code задаёт действие; независимые ошибки собираются. |
| Диагностика/исследование не снимают обязательную корректность | R5/R6, Constitution | Числа и участники отделены от обязательных функциональных/интеграционных проверок. |

Новых существенных противоречий с учётом принятого пакета не выявлено. Полные частные финальные ответы не проверялись; этот предел доказательств сохраняется. Если предоставленная позднее финальная конкретизация R3 расходится с опубликованным принятым порядком, требуется сверка соответствующей части, а не молчаливая замена требований. Методика производительности остаётся отдельной будущей работой и не делает диагностические пороги обязательными сейчас. Ни контракт, ни журнал не подтверждают готовность ещё не созданных v2 или реализации.
