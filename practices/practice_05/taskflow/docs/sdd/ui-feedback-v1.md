# Ответ UI-команды — раунд 1

Источник: полный ответ исходной UI-сессии Codex, переданный пользователем в этом раунде. Ниже сохранён текст ответа без внешних квадратных скобок сообщения-передачи. Позиция команды не означает утверждение общего контракта.

## Исходный ответ (полностью)

```text
Ниже — позиция UI-команды по документу согласования (docs/sdd/kanban-alignment.md). Это ответы для обсуждения; общий контракт пока не считаю согласованным.

1. Q1 — Срок выполнения: согласен.

   Срок прямо входит в пользовательский запрос. Исключать его ради сокращения Backend не предлагаю. Поддерживаю due_date как YYYY-MM-DD или null, очистку через null, допустимость прошлых дат и вычисление просрочки по локальному календарному дню устройства. Преобразование в UTC здесь может ошибочно сдвинуть дату.

   Диапазон 0001–9999 приемлем как граница контракта, но интерфейс должен позволять ввести год вручную, без пролистывания тысяч лет. Изменение признака просрочки при смене часового пояса принимаю как следствие выбранной семантики.

   Сценарии и проверки: создание, редактирование и очистка срока; вчера/сегодня/завтра; високосный день и несуществующая дата; смена дня и возвращение во вкладку; done и возврат из него; сохранность даты после перезагрузки. Затрагивает сценарии 1–2, FR-002–004 и SC-001.
2. Q2 — Отказ от конца колонки: согласен с условием.

   Для учебной версии принимаю created_at ASC, id ASC: стабильный порядок после обновления важнее первоначального предположения о конце колонки. Дополнительное серверное состояние порядка сейчас не выглядит необходимым.

   Однако перемещённая карточка может оказаться далеко от места действия. UI должен объявлять целевую колонку, сохранять фокус на перемещённой карточке и при необходимости делать её видимой. Не следует временно показывать её в конце, а после обновления переставлять.

   Сценарии и проверки: перенос старой задачи в колонку с более новыми, редактирование без перестановки, одинаковый created_at, обновление страницы. Проверяем одинаковый порядок до и после обновления и сохранение фокуса. Потребуется изменить ожидание сценария 3 и предположение о порядке в будущей UI v2.
3. Q3 — Клиентский UUID и удержание POST: согласен частично.

   Один UUID v4 на намерение создания приемлем. UUID пользователю не показывается. После первой отправки сохраняются ID и исходное тело; сетевой повтор использует их повторно. Изменённый черновик нельзя незаметно отправлять как повтор того же запроса.

   Не согласен требовать бессрочного восстановления незавершённого POST после закрытия браузера. Для первой версии предлагаю удерживать намерение в пределах открытой вкладки, включая её перезагрузки, через доступное сеансовое хранилище. При его недоступности — только в памяти, с понятным предупреждением при неизвестном результате. После разрешения исхода запись удаляется. Автоматической отправки при восстановлении нет.

   После закрытия вкладки восстановление намерения не гарантируется. При следующем открытии сначала загружается серверная доска; создание не повторяется автоматически. Это ограничение нужно явно принять, а не изображать как полную защиту от дублей.

   Проверки: потерянный ответ, повтор с тем же ID и телом, перезагрузка вкладки, недоступное хранилище, изменение черновика после отправки. Затрагивает сценарий 2, FR-004/007 и SC-003.
4. Q4 — Бессрочная отметка удалённого ID: поддерживаю гарантию, механизм условно.

   Поздний повтор старого создания не должен воскрешать удалённую задачу. Запрет повторов только в текущем UI этого не обеспечивает: существует другая вкладка и уже отправленные запросы.

   Минимальная долговечная отметка использованного ID выглядит соразмерной этой гарантии. Поддерживаю вариант при подтверждении Backend, что он не требует существенного усложнения или новых зависимостей. Внутреннее устройство хранения UI-команда не предписывает.

   Квитанция с ограниченным сроком — возможная альтернатива, но после истечения срока сервер должен отклонять старое намерение, если обещана защита от воскрешения. Простое удаление сведений о повторе оставляет проблему. Более простой ограниченный режим допустим только с явным отказом от надёжного повтора неизвестного POST; по UX это хуже.

   Проверки: потерянный ответ POST → удаление в другой вкладке → повтор исходного POST; тот же сценарий после перезапуска сервера. Ожидание — задача не восстанавливается, новый UUID автоматически не создаётся.
5. Q5 — Конфликты версий и отсутствие задачи: согласен, с уточнением действий.

   version нужна для редактирования, перемещения и удаления даже в персональном приложении с несколькими вкладками. Автоматически подставлять новую версию и повторять запись нельзя.

   Предлагаю следующие сценарии:
   - Форма, 409: сохранить черновик, получить актуальную задачу, показать различающиеся значения. Пользователь выбирает актуальную версию либо явно применяет выбранные изменения поверх неё. Отправлять только выбранные изменения, чтобы не затереть остальные поля. Новый конфликт обрабатывается заново.
   - Перемещение, 409: получить актуальную задачу. Если статус уже целевой — сообщить текущее состояние без повторного PATCH. Если другой — предложить повторить перенос с актуальной версией.
   - Удаление, 409: показать актуальные сведения и снова запросить подтверждение удаления.
   - 404: убрать отсутствующую задачу из подтверждённого состояния после сверки. Черновик сохранить отдельно; перенос черновика в новую задачу допускается только явным действием.
   - GET завершился ошибкой: оставить последний снимок с предупреждением; разрешение конфликта ещё не завершено.
   При DELETE сообщение «Задача уже отсутствует» корректнее, чем «Вы удалили задачу».

   Проверки: две вкладки, одновременные операции одной версии, повторный конфликт, удаление извне, отказ GET. Формулировки сценариев 3.3/4.3 необходимо уточнить: отказ не гарантирует неизменность сервера.
6. Q6 — Поля, null, Unicode и длины: согласен.

   Принимаю название 1–200 кодовых точек после согласованной обрезки, описание до 5000, сохранение его пробелов, "" для очистки описания и null только для срока. Отсутствующее поле PATCH сохраняет значение. Строгие типы, запрет неизвестных и служебных входных полей приемлемы.

   Пользователь должен видеть ограничения рядом с полем. Клиентский счётчик обязан считать кодовые точки: обычная длина строки может иначе учитывать emoji. При этом кодовая точка не всегда равна одному видимому символу — нельзя обещать обратное в подсказке.

   Проверки: граничные длины, emoji и составные символы, перечисленные Unicode-пробелы, управляющие символы, переносы описания, очистка полей. Ошибки клиентской и серверной проверки должны совпадать. Затрагивает сценарий 2 и FR-004.
7. Q7 — Ошибки и version query: согласен с основой, полного согласования пока нет.

   UI достаточно стабильных категорий missing, invalid_type, invalid_length, invalid_value, invalid_date, unknown_field; дополнительные коды нужны только при отличающемся поведении или полезном объяснении. Раздувать словарь ради каждой технической разновидности ошибки не предлагаю.

   Известные редактируемые поля получают ошибки у полей. id, version, $ и неизвестные поля — общую ошибку. Фокус должен переходить к первому ошибочному полю в порядке формы, независимо от серверной сортировки details.

   Для DELETE предлагаю один обязательный version в канонической записи положительного целого: без знака, дроби, пробелов и ведущих нулей. Повторённый параметр отклонять. Backend должен подтвердить точную семантику.

   При 503, сетевом сбое, 500 или непонятном ответе результат записи может быть неизвестен: сохраняем черновик, не объявляем неуспех записи доказанным, начинаем сверку. Неизвестный код или не-JSON ответ дают понятное русское сообщение без технического содержимого.

   Проверки: все категории ошибок, несколько ошибок одновременно, неизвестный код/поле, HTML вместо JSON, недоступность сервера и неизвестный результат записи. Затрагивает FR-004/007/011/013.
8. Q8 — Методы, оболочка списка, no-op и done: согласен.

   Предложенные CRUD-методы, items/total, полная Task в успешных ответах и 204 без тела удовлетворяют UI. Отдельный endpoint перемещения не требуется.

   Создание сразу в done допустимо. No-op с актуальной версией не должен менять версию и время изменения. В неизменённой форме UI может закрыть редактирование без PATCH; запрос только с version отправлять не должен. Старая версия требует проверки конфликта даже при совпадении переданных значений.

   Проверки: пустой список, соответствие total числу элементов, создание в каждом статусе, no-op, устаревшая версия, удаление без разбора JSON и повтор DELETE с 404. Связано со сценариями 1–4.
9. Q9 — Объём и задержка совместной приёмки: согласен с разделением, нужны измеримые условия.

   Сохраняю 30 задач для основной UI-приёмки и 1000 для отдельной Backend-проверки. Серверный результат не подтверждает скорость интерфейса.

   Предлагаю совместную функциональную приёмку на 30 задачах и отдельный прогон UI на 1000 для выявления зависаний и недоступных карточек, без заявления, что такой объём уже оптимизирован.

   Предлагаемые цели для согласования: в зафиксированной локальной среде доска из 30 задач доступна для взаимодействия не позднее двух секунд после открытия; видимая обратная связь на действие появляется в пределах 200 мс. Измерять полное пользовательское время и отдельно сеть. Проверить также искусственную задержку ответа в две секунды: индикатор ожидания, блокировку повторного действия и доступность остальных задач.

   Общий набор: CRUD → срок → перенос и порядок → обновление клиента/сервера → конфликт → удаление извне → потерянные ответы POST/PATCH/DELETE → восстановление. Нужен реальный Backend; управляемое внесение сетевых сбоев не должно подменять серверную обработку.
10. Q10 — Пять участников: согласен с честной проверкой, возражаю против безусловного обязательного барьера.

    Пять участников полезны для небольшой формирующей проверки удобства, но их доступность сейчас неизвестна. Результат 4/5 нельзя обобщать на 80% всех пользователей.

    Предлагаю в будущей UI v2 сделать этот критерий дополнительной пользовательской проверкой. Обязательную приёмку построить на воспроизводимых сценариях, доступности и интеграции. Если решено сохранить SC-002 обязательным, при отсутствии участников он остаётся непроверенным — самопроверка его не заменяет.

    Если участники доступны, предлагаю протокол:
    - Координатор организует набор и дату; представитель UI проводит сессии, Backend обеспечивает работающее окружение и подготовку данных.
    - Пять человек, не участвовавших в разработке, проходят одинаковые задания без обучения действиям Kanban.
    - Каждый получает одинаковую доску из 30 задач и заранее подготовленный текст новой задачи. Данные восстанавливаются перед каждой сессией.
    - Для первого исследования фиксируется одна конфигурация устройства и браузера; обе ширины и темы проверяются отдельно по функциональной матрице.
    - Для каждого из трёх заданий отдельно требуется минимум 4 успешных результата из 5 в пределах 60/30/15 секунд.
    - В протоколе записываются полное время, сетевое ожидание, ошибки и помощь ведущего. Подсказка означает невыполнение условия «без подсказок».
    Время следует считать до видимого подтверждённого результата, сохраняя сетевую составляющую отдельно. Назначать фактическую дату и утверждать наличие участников сейчас оснований нет.

Оставшиеся разногласия

- Q3: не принимаю бессрочное восстановление POST после закрытия браузера как обязательное требование первой версии.
- Q4: гарантию отсутствия воскрешения поддерживаю; конкретный механизм и стоимость ещё требуют ответа Backend.
- Q7: словарь ошибок и точные правила version ещё не закрыты.
- Q9: объёмы совместимы, но предложенные пороги и среда измерения ещё не утверждены.
- Q10: предлагаю дополнительный статус исследования на пяти участниках вместо безусловного обязательного барьера. При сохранении исходного требования нужны реальные участники.

Вопросы к Backend-команде

- Гарантируется ли одинаковый порядок created_at/id после изменения, переноса и перезапуска?
- Какую гарантию даёте старому POST после удаления, в том числе из другой вкладки и после перезапуска? Какова стоимость варианта task_id_retired?
- Подтверждаете ли проверку версии до признания PATCH no-op и отсутствие частичных изменений при конфликте?

- Какое окружение и способ внесения сбоев используем для общей интеграционной проверки?

Файлы не изменялись. UI v2 и код не создавались; commit и push не выполнялись.
```
