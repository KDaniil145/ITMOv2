Источник: полный ответ исходной Backend-сессии Codex, повторно переданный пользователем после обрыва первого сообщения в Q5. Ниже сохранён полный текст последнего сообщения; он заменяет ранее полученный неполный фрагмент. Позиция команды не означает утверждение общего контракта.

## Исходный ответ (полностью)

```text
Прочитал документ координатора (docs/sdd/kanban-alignment.md) полностью и повторно сверил Backend v1. Ответ UI-команды не читал.

Предложение реализуемо в учебном масштабе. Основное усложнение связано с точностью повторов, конкурентных операций и обработки сбоев. Ниже — позиция Backend-команды для сравнения; предварительный контракт пока не согласован.

Q1. Добавление due_date — согласен.

Поле имеет понятный пользовательский смысл и не требует усложнения модели времени.

Предлагаю принять:

- POST: отсутствие поля или null означает отсутствие срока.
- PATCH: отсутствие поля сохраняет срок; null очищает; строка заменяет.
- Ответ Task всегда содержит due_date.
- Допускается только существующая григорианская дата YYYY-MM-DD, годы 0001–9999. Пустая строка, timestamp, сокращённая запись и дата с пробелами отклоняются.
- Прошлые даты разрешены. Срок не ограничивает переходы статуса.

В SQLite достаточно nullable текстового значения в каноническом формате. Преобразование в UTC не требуется. Признак просрочки не хранится: UI вычисляет его по своему календарному дню только для незавершённых задач.

Повтор POST: сравнение обязательно включает due_date. Отсутствующее поле и явный null эквивалентны после применения default. Другая дата при том же существующем ID — 409 task_id_conflict, даже если остальные поля совпадают.

Последствия и проверки: расширяются модель, полные ответы, создание, PATCH и сравнение повторов. Нужны високосные даты, невозможные даты, границы лет, очистка, no-op, сохранение после перезапуска. Смена дня и часового пояса — преимущественно UI-проверки. UI должен отдельно подтвердить поддержку всего предложенного диапазона лет.

Q2. created_at ASC, id ASC — согласен.

Это простой воспроизводимый порядок без дополнительного состояния. Перемещение, изменение приоритета, срока или текста не меняет сортировочный ключ. После перезапуска порядок сохраняется; UI группирует список по статусам, сохраняя относительный порядок.

Необходимо закрепить единый формат и точность серверных времён. Сортировать следует по значению момента, а не по произвольным строкам RFC 3339 с разной точностью.

Оговорка: такой порядок не гарантирует конец колонки для перемещённой задачи. При совпавшем времени создания порядок задаёт UUID, а при переводе системных часов назад даже новая задача может оказаться раньше предыдущих.

Альтернатива при возражении UI: серверный монотонный номер входа в колонку, обновляемый атомарно только при реальной смене статуса. Это надёжнее одного времени входа, но добавляет поле и правила выделения последовательности. Сейчас рекомендую обойтись без него.

Последствия и проверки: основная модель не расширяется. Проверять одинаковый created_at, перенос старой задачи к новой, редактирование и повторное чтение после перезапуска. Локальную перестановку нельзя выдавать за сохранённый серверный порядок.

Q3. Клиентский UUID и восстановление намерения — согласен со стороны Backend, возможность UI требует подтверждения.

Поддерживаю обязательный UUID v4 в каноническом нижнем регистре. Сервер проверяет форму, версию UUID и variant, но не может проверить качество случайной генерации клиента.

В Backend v1 есть моя внутренняя неоднозначность. В будущей редакции история должна звучать:

> При создании с обязательными id и корректным title, без остальных пользовательских полей, возвращается задача с заданным ID и значениями по умолчанию.

Серверная генерация ID этим предложением не подразумевается. Первоначальный снимок сейчас не меняем.

Для повторов UI удерживает ID и исходный запрос до разрешения результата. Редактирование формы в этот период не должно незаметно превращаться в другой POST с прежним ID.

Альтернатива: серверный ID плюс отдельный ключ идемпотентности. Это не устраняет необходимость хранить клиентское намерение и добавляет серверное состояние, поэтому пока преимуществ не вижу.

Последствия и проверки: отсутствие ID — 422; неверная каноничность — 422; одинаковый ID не создаёт две записи. Восстановление после перезагрузки браузера требует отдельного UI-решения. Без сохранённого намерения нельзя обещать безопасное автоматическое возобновление POST.

Q4. Долговечная отметка удалённого UUID — согласен рассматривать, но не считаю выбор уже сделанным.

Замечание координатора верно: ограничение Backend v1 недостаточно для нескольких вкладок. GET 404 не отличает никогда не созданную задачу от созданной и затем удалённой.

Моя рекомендация — выбрать минимальную долговечную отметку, если принимаем гарантию «поздний повтор POST никогда не воскрешает удалённую задачу».

| Вариант | Гарантия | Стоимость и ограничения |
|---|---|---|
| Отметка удалённого UUID | Запрещает повторное создание этого ID в течение жизни хранилища | Дополнительный набор UUID, атомарность удаления и отметки, бессрочный рост |
| Полная квитанция создания | Позволяет точнее распознавать повторы исходной операции | Хранение исходного запроса или отпечатка, дополнительные правила ответов и удаления |
| Отметка с истечением срока | Защита только внутри установленного окна | Очистка, правила времени; позднее воскрешение снова возможно |
| Без отметок | Минимальная серверная модель | Нельзя гарантировать отсутствие воскрешения при поздних запросах из другой вкладки |

Минимальная отметка содержит только UUID; дата удаления для самой гарантии не обязательна. Содержимое задачи не сохраняется. Возможная схема — отдельный набор удалённых ID, обновляемый в одной транзакции с удалением задачи. Новая библиотека для этого сама по себе не требуется.

Стоимость для SQLite умеренная, но не нулевая: дополнительная проверка POST, уникальность отметки, отсутствие состояния «задача удалена, отметки нет», сохранность после сбоя, резервное копирование вместе с задачами. Объём растёт с числом удалений, а не числом активных задач.

Если выбираем отметки:

- POST удалённого ID → 409 task_id_retired.
- GET и повтор DELETE → 404.
- Отметка не истекает в пределах жизни данного хранилища.
- Сброс или восстановление старой копии хранилища ограничивает гарантию его фактическим состоянием.

Если отказываемся: необходимо явно принять ограниченную гарантию. UI-контроль повторов уменьшает риск, но не останавливает уже отправленный задержанный запрос другой вкладки.

Проверки: гонка POST/DELETE, повтор после удаления и перезапуска, сбой между действиями удаления и отметки, отсутствие частичного результата. Окончательный выбор оставляю открытым для сопоставления позиций команд.

Q5. Версии, 409/404 и потерянные ответы — согласен с уточнениями.

Версия должна относиться ко всей задаче, включая due_date. Проверка версии и операция неделимы.

| Ситуация | Ответ и эффект |
|---|---|
| Реальный PATCH с актуальной версией | 200, версия +1 |
| No-op PATCH с актуальной версией | 200, версия и updated_at прежние |
| PATCH со старой версией, даже с совпавшими значениями | 409 |
| PATCH отсутствующей задачи | 404 |
| DELETE существующей задачи с актуальной версией | 204 |
| DELETE существующей задачи со старой версией | 409 |
| DELETE отсутствующей задачи с корректным запросом | 404 |

После потери ответа:

- PATCH: GET показывает текущее состояние, но совпадение значений не доказывает, кто выполнил изменение. Черновик сохраняется; повтор с новой версией требует решения пользователя.
- DELETE: GET 404 подтверждает отсутствие. GET 200 не разрешает автоматически удалить актуальную запись.
- POST: GET 200 позволяет сверить запись; GET 404 сам по себе недостаточен для безопасного повтора без выбранной политики Q4.

Важное уточнение к Backend v1: правило «из двух операций одной версии проходит ровно одна» относится к двум реальным изменениям. Два no-op могут оба вернуть 200. Если no-op выполняется раньше реального PATCH, оба также могут завершиться успешно. Это не потерянное изменение.

Для гонки реального PATCH и DELETE исходной версии:

- первым завершился PATCH → 200, DELETE → 409;
- первым завершился DELETE → 204, PATCH → 404.

Последствия и проверки: новых полей сверх version нет; требуется корректная транзакционная реализация. Проверять обе последовательности гонок, no-op после нормализации заголовка, потерю ответа после сохранения и отказ последующего GET. Старый локальный снимок после 404/409 нельзя представлять как актуальное состояние сервера.

Q6. Null, Unicode, длины и неизвестные поля — согласен.

Подтверждаю предложенное координатором точное множество White_Space и порядок обработки: сначала обрезка title, затем проверка длины и запрещённых символов.

При этом:

- NFC/NFKC, изменение регистра и схлопывание внутренних пробелов не выполняются.
- description не обрезается; "" очищает.
- Null разрешён только для due_date.
- Отсутствие пользовательского поля PATCH означает «не менять».
- Длины считаются в Unicode-кодовых точках, не в байтах, UTF-16 единицах или видимых графемах.
- Неизвестные и запрещённые служебные поля отклоняются.
- Непарные суррогаты следует отклонять как некорректный Unicode, чтобы результат не зависел от возможностей записи строки.

Таким образом, крайний TAB у заголовка удаляется, внутренний TAB запрещён; U+FEFF не входит в предложенное множество обрезки.

Последствия и проверки: единые правила должны использоваться при записи, no-op и сравнении POST. Нужны emoji, составные символы, неразрывные пробелы, управляющие символы и строгие типы. UI нельзя полагаться только на обычный maxlength для совпадения с серверным подсчётом.

Q7. Ошибки и query version — согласен с оболочкой, предлагаю следующую конкретизацию.

Для описанного объёма предлагаю закрытый словарь details.code:

| Код | Нарушение |
|---|---|
| missing | Отсутствует обязательное поле или параметр |
| invalid_type | Неверный JSON-тип, включая null там, где он запрещён |
| invalid_length | Нарушена длина строки |
| invalid_value | Неверный enum или значение вне допустимого диапазона |
| invalid_format | Неверный UUID либо синтаксис query version |
| invalid_date | Строка срока не соответствует формату, диапазону или календарю |
| invalid_characters | Запрещённые управляющие символы |
| invalid_unicode | Непарный суррогат |
| unknown_field | Неизвестное поле тела |
| read_only | Известное, но запрещённое в этой операции поле |
| unknown_parameter | Неизвестный query-параметр |
| duplicate_parameter | Query-параметр повторён |
| empty_update | PATCH не содержит пользовательских полей |
| body_not_allowed | Непустое тело GET/DELETE |
| stale_version | Версия существующей задачи не совпала |
| id_conflict | ID занят несовместимой записью |
| retired | ID удалён; только при выборе отметок |

Для 400, 415, 404, 405, 503 и 500 предлагаю details: []: верхнего кода достаточно. Повтор ключа JSON относится к 400 invalid_json, а не к duplicate_parameter.

Чтобы ошибки были предсказуемы, проверка конкретного поля последовательная: обязательность → тип → формат/значение. Зависимые проверки после провала не выполняются; независимые ошибки других полей собираются и сортируются по field, затем code.

DELETE query version:

- Ровно один параметр version.
- После стандартного URL-декодирования — только ASCII-запись [1-9][0-9]*.
- 01, +1, 1.0, 1e0, пробелы, пустая строка и Unicode-цифры запрещены.
- Повтор параметра запрещён даже с одинаковыми значениями.
- Отсутствие → missing, повтор → duplicate_parameter, неверная запись → invalid_format.
- Неизвестные параметры → unknown_parameter.

Дополнительно предлагаю общий безопасный для JSON-клиента диапазон версий 1…9007199254740991. Для PATCH требуется именно JSON integer, без bool и неявного преобразования. Превышение диапазона → invalid_value. Если сервер когда-либо достигнет максимума, реальный PATCH должен отказать без переполнения; предлагаю 409 version_exhausted с пустым details. Это дополнение требует согласования, хотя практически для учебного проекта недостижимо.

Примеры:

Последствия: уточняется контракт, модель ошибок и матрица проверок; модель задачи почти не затрагивается. Строгие правила требуют явных обработчиков, нельзя считать стандартные ответы framework автоматически соответствующими контракту. Тексты сообщений не являются машинными идентификаторами. Для неверного запроса валидация предшествует поиску задачи: например, неверная version даёт 422 даже для отсутствующего ID.

Q8. Методы, items/total, no-op и создание в done — согласен.

Поддерживаю пять операций задач, полный Task в успешных ответах создания/изменения, items/total, пустой список и 204 без тела. total равен длине items; отсечения на 1000 нет.

Создание сразу в любом допустимом статусе разрешено. Отдельный маршрут перемещения не нужен. {"version":1} — 422 empty_update; PATCH с явно переданным неизменившимся пользовательским полем — допустимый no-op.

Повтор POST возвращает 200 только для совпавшей записи версии 1, включая срок. После реального изменения — 409, даже если значения позднее вернулись к исходным.

Последствия и проверки: дополнительных сущностей нет. Проверять каждый маршрут, статусы, полные ответы, Location при 201, отсутствие тела 204, no-op и создание в done. /api/health сохраняется отдельно и не заменяет чтение задач.

Q9. Объём, SQLite, сбои и производительность — согласен с разделением приёмки; возражаю против автоматического превращения всех показателей в обязательные.

30 задач для UI и 1000 для Backend совместимы. Это проверочные наборы, не ограничения числа задач.

Предлагаю обязательную серверную приёмку после согласования строить на следующем:

- Реальная файловая SQLite, отдельное тестовое хранилище, чтение новым процессом после штатного и принудительного завершения.
- Сохранность всех подтверждённых полей, включая срок, удаления и выбранные отметки ID.
- Двадцать синхронизированных пар реальных изменений одной версии и двадцать пар одинаковых POST. Запуск запросов подряд не является проверкой конкуренции.
- Реальная блокировка записи, ошибка доступа, повреждённый файл; никакой замены повреждённой базы пустой.
- Управляемые сбои до сохранения, внутри транзакции, после сохранения до отправки ответа. После восстановления допустимо целое старое или целое новое состояние, но не смесь.
- Отдельная проверка потери ответа. Искусственный отказ не должен требовать публичного диагностического API.
- Сквозная цепочка через реальный backend: создание → срок → редактирование → статус → перезапуск → удаление.

Сохраняю предложение Backend v1: не менее 95 из 100 запросов в пределах секунды при 1000 задач, но его ещё нужно сделать воспроизводимым. Предлагаю измерять отдельно список, отдельное чтение и реальный PATCH; фиксировать оборудование, размеры текстов, режим запуска, прогрев и отсутствие искусственных блокировок. Ошибочный быстрый ответ не считается успешным измерением.

Это пока кандидат на обязательный серверный критерий, а не уже утверждённая обязанность. Смешанная выборка без определения операций недостаточно точна. Альтернатива до согласования условий — диагностический замер с публикацией результатов без объявления прохождения порога.

Принудительное завершение процесса не доказывает сохранность при отключении питания, отказе диска или восстановлении старой резервной копии. Такие гарантии нельзя приписывать этому тесту.

Последствия: расширяется программа проверок и уточняются SC-002–SC-005. Пользовательский API не должен усложняться ради тестирования.

Q10. Пять участников — согласен как с отдельной проверкой удобства, не согласен считать её обязательной серверной приёмкой.

Результат «четыре из пяти участников выполнили сценарии» оценивает продукт и UI. Он не доказывает атомарность SQLite, сохранность или корректность версии; серверные автотесты, в свою очередь, не доказывают удобство интерфейса.

Backend может подготовить одинаковые наборы из 30 задач, обеспечить работающий сервер и помочь измерить сетевое ожидание. Организацию участников, сценарии и оценку выполнения предлагаю закрепить за UI/координатором.

Нужны пять реальных участников без подсказок, одинаковые исходные условия, заранее определённые начало/конец каждого задания и критерии успеха. Время сетевого ожидания фиксируется отдельно, но не вычитается из общего пользовательского времени, если критерий явно не изменён.

Если участников нет, результат остаётся непроверенным. Альтернатива — отдельно согласовать изменение будущего критерия; самопроверка его не заменяет.

Последствия: изменений API и модели нет. Появляется отдельный протокол продуктовой приёмки. Если критерий сохраняется в согласованной UI-спецификации, он может блокировать общую готовность продукта, но не должен подменять оценку серверной корректности.

Вопросы к UI-команде

1. Поддерживает ли UI диапазон дат 0001–9999, явную очистку через null и локальную календарную семантику?
2. Принимает ли порядок по созданию, включая попадание старой перемещённой задачи в середину колонки?
3. Где и как долго сохраняются UUID и исходный POST при неизвестном результате, включая перезагрузку браузера?
4. Нужна ли строгая гарантия отсутствия воскрешения удалённой задачи? Приемлема ли ради неё долговечная отметка UUID?
5. Как сохраняется черновик при 404/409 и оформляется осознанное повторное применение с новой версией?
6. Принимает ли UI подсчёт кодовых точек, точную обрезку и предложенный словарь ошибок?
7. Кто организует пять участников и какие операции входят в общий измеряемый сценарий?

Оставшиеся разногласия и незакрытые решения

- Нельзя пока выбрать за обе команды долговечные отметки или ограниченную гарантию повторов.
- Не подтверждены отказ UI от конца колонки и восстановление клиентского намерения.
- Требуют утверждения словарь ошибок, диапазон версий и поведение при его исчерпании.
- Формулировку гонок необходимо ограничить реальными изменениями, исключив no-op.
- Условия обязательного порога производительности ещё не определены.
- Проверка на пяти участниках относится к продуктовой приёмке; включение её в обязательную серверную приёмку отклоняю.
```
