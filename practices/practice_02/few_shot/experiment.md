# Few-shot

- Артефакт Практики 1: `practices/practice_01/tests_e2e.md`, строка 8 «Слишком большой diff → контролируемый отказ»
- Что хотим улучшить: сделать сценарий конкретным, однозначным и проверяемым, не меняя требований проекта

## Примеры

### Хороший результат

Сценарий: PR содержит секрет в изменённой строке
Предусловия: в diff присутствует API token
Действие: пользователь отправляет PR на review
Наблюдаемый результат: агент возвращает security-риск с конкретным `file:line`
Подтверждение: риск можно сопоставить с соответствующей строкой diff

### Плохой результат

Сценарий: Проверить, что система правильно обрабатывает плохой PR

Почему это плохой результат:
- непонятны конкретные предусловия
- действие сформулировано расплывчато
- нет наблюдаемого ожидаемого результата
- непонятно, как подтвердить успешность сценария

## Запрос

Техника: Few-shot. Артефакт: `practices/practice_01/tests_e2e.md`. Цель: сделать один из существующих E2E-сценариев более конкретным, однозначным и проверяемым, не меняя требований проекта. Используй приведённые хороший и плохой примеры как ориентир качества. Не добавляй новых продуктовых требований, не меняй смысл сценария и другие сценарии, не используй другие техники.

## Что получили

Выбран худший сценарий по соответствию хорошему примеру — «Слишком большой diff → контролируемый отказ» (строка 8). Дефициты:
- предусловие неоперационально: порог «Неизвестно / требует уточнения», вход нельзя построить однозначно;
- сценарий и наблюдаемый результат не позволяют отличить этот случай от других 4xx;
- нет способа подтверждения, Evidence ссылается на общий раздел TO BE/ADR.

Предложена улучшенная версия: предусловие привязано к превышению предусмотренного проектом порога; результат — HTTP 4xx (слишком большой запрос) без трассировки стека и без вызова LLM; Evidence — ADR, `tests_integration` и способ подтверждения (тестовый double, сверхпороговый вход).
