# ADR: решение для первого рабочего сценария

- Статус: proposed
- Дата:
- Ответственные:

## Контекст

AS IS (по analysis.md):
- POST `/api/reviews` принимает JSON `payload`, из которого без валидации извлекается `payload["diff"]`.
- `ReviewService.review(diff)` формирует промпт и вызывает компонент LLM через `LLM.generate`.
- Возвращается `{"comment": answer}`.

Подтверждённые проблемы:
- Риск `KeyError` и HTTP 500 при отсутствии ключа `diff` (семантика Python, отсутствие валидации).
- Отсутствие обработки исключений `llm.generate` — возможны неконтролируемые 500.

Потенциальные риски (требуют уточнения):
- Отсутствие ограничения размера `diff` — возможны задержки/ошибки.
- Prompt injection — diff включается в промпт напрямую.

## Решение

Предлагаем минимальные изменения TO BE без добавления новых подсистем:
- Добавить валидацию входа в слое API: проверка наличия поля `diff` и базовой корректности типа.
- Добавить проверку/ограничение размера `diff` до формирования промпта. Конкретный порог — Неизвестно / требует уточнения.
- Обернуть вызов `llm.generate` обработкой исключений и возвращать контролируемый 5xx.
- Сохранить успешный путь: `{"comment": answer}` при валидном входе и успешном ответе LLM.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Асинхронная обработка/очереди | Выходит за рамки минимальных изменений; нет подтверждённой необходимости |
| Внешний фильтр/проксирование запросов | Добавляет компоненты без необходимости; цель достигается в текущем слое API |
| Полная перестройка контракта API | Нет источников, требующих изменения успешного пути и структуры ответа |

## Последствия и главный риск

- Положительные последствия:
  - Снижение числа неконтролируемых 500 из-за отсутствующего `diff` и исключений LLM.
  - Предсказуемое поведение при некорректном и слишком большом входе.
- Ограничения:
  - Точный порог размера `diff` не определён (Неизвестно / требует уточнения).
  - Формат и тексты ошибок 4xx/5xx требуют согласования.
- Главный риск:
  - Неверно выбранный порог по размеру `diff` может ухудшить UX или надёжность.
- Как проверим риск:
  - Пилотные проверки на реальных/тестовых примерах разных размеров diff; уточнение порога и формата ошибок (план проверки, не выполнен).
