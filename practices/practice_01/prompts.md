## P1-01 — полный ответ модели

Ниже — обзор PR с проблемами и рисками, упорядоченными по важности, с привязкой к файлам и строкам из диффа.
Высокая важность
1. app/api.py:35-38 — Нет валидации входа, возможен KeyError
- Функция объявлена как create_review(payload: dict), а далее используется payload["diff"]. Если ключ diff отсутствует, будет 500 (KeyError) вместо 422 с понятной ошибкой.
- Рекомендация: ввести Pydantic-модель запроса с обязательным полем diff и явной схемой ответа.
2. app/review_service.py:19-22 — Неограниченный размер входного diff
- diff целиком инлайнится в промпт без ограничений/усечений. Большие диффы приведут к перерасходу токенов, задержкам, ошибкам LLM или падениям.
- Рекомендация: ограничить размер diff (напр. усечение по токенам/строкам), добавить защиту по длине и указание пользователю/клиенту.
3. app/review_service.py:19-22 — Риск prompt injection
- Дифф вставляется в промпт без экранирования/структурирования, что облегчает внедрение инструкций через дифф.
- Рекомендация: жёстко структурировать промпт (системные инструкции отдельно), трактовать diff как данные (например, YAML/JSON-блок), добавлять предупреждения LLM игнорировать инструкции из diff.
4. Совместимость с версией Python — dictstr, str и Protocol
- Использование dict[str, str] и Protocol требует Python 3.9+ (или typing_extensions для 3.8). Если целевая версия <3.9, код упадёт при импорте.
- Рекомендация: подтвердить версию рантайма; при 3.8 — заменить на Dict[str, str] и from typing_extensions import Protocol.
5. app/api.py:35-38 — Нет обработки ошибок LLM/сервиса
- Любое исключение в LLM (таймауты, код 5xx внешнего провайдера и т.п.) приведёт к 500 без контролируемого ответа.
- Рекомендация: оборачивать вызов сервиса, маппить исключения на 4xx/5xx, возвращать стабильные ответы с кодами и сообщениями.
Средняя важность
6. app/api.py:35-38 — Синхронный handler
- Обработчик синхронный. В FastAPI синхронные функции исполняются в threadpool, но для «долгих» LLM-вызовов лучше явный async (или фоновая задача) и таймауты.
- Рекомендация: сделать endpoint async, либо увести работу в background task/очередь, добавить таймауты.
7. Контракт API расплывчатый
- Возвращается dict[str, str] с ключом comment. Нет стабильной схемы ответа/кодов. Нет метаданных (severity, список находок, структура).
- Рекомендация: описать response_model с полями, пригодными для UI/интеграций; возможно возвращать массив findings, категорию, позиции в diff.
8. Инъекция зависимостей
- from app.dependencies import review_service подразумевает глобальный синглтон. Это затрудняет тестирование и конфигурирование, может быть проблемой для состояния/пулы соединений.
- Рекомендация: использовать DI через Depends/fastapi, либо фабрику в старте приложения; минимум — убедиться, что зависимость потокобезопасна.
9. Логирование/обсервабилити
- Нет логирования вызовов/исключений/latency. Для LLM-сервисов это критично.
- Рекомендация: добавить логирование: размер diff (с ограничением), время выполнения, коды ошибок.
10. Безопасность: отсутствие ограничений/квот/аутентификации
- Endpoint не защищён (по коду не видно auth), нет rate limiting — может использоваться для DoS.
- Рекомендация: явные требования к авторизации, квоты, лимиты по размеру/частоте.
Низкая важность
11. app/review_service.py:9-13 — Стиль определения Protocol
- Замена однострочного ... на многострочный — «шум» без пользы; может конфликтовать с линтерами.
- Рекомендация: вернуть компактный вариант или следовать принятому code style.
12. Нейминг и язык сообщений
- Поле payload общее; лучше доменное имя (например, ReviewRequest). Текст промпта на английском — проверьте требования к i18n.
13. Документация и тесты
- Нет тестов для ReviewService.review и для /api/reviews. Нет описания в README/OpenAPI что именно возвращает endpoint.
- Рекомендация: unit-тест на ReviewService (ограничение длины, корректная сборка промпта), интеграционный тест на API (валидный/невалидный вход, ошибки LLM).
Открытые вопросы
- Какая целевая версия Python? Если <=3.8, текущие типы сломают импорт.
- Требуются ли аутентификация/авторизация для этого endpoint? Если да — нужно добавить сейчас.
- Каков ожидаемый формат и максимальный размер diff? Есть ли ограничения на стороне LLM-провайдера?
- Нужна ли асинхронность/очередь для длительных LLM-операций, или допустим синхронный путь?
- Какие поля должны быть в ответе для интеграций/фронтенда? Нужна ли структура findings?

## P1-02 — полный ответ модели

Ниже — до 5 существенных подтверждённых проблем, основанных только на diff и семантике Python/общих правилах надёжности и безопасности.

1) Нет валидации входа, возможен KeyError

- File: app/api.py
- Line: Неизвестно / требует уточнения
- Problem: Прямой доступ к полю `payload["diff"]` без проверки наличия ключа приведёт к `KeyError` и 500 вместо контролируемой ошибки клиента.
- Evidence: 
  ```diff
  +@app.post("/api/reviews")
  +def create_review(payload: dict) -> dict[str, str]:
  +    return review_service.review(payload["diff"]) 
  ```
- Basis / Rule: В Python доступ к отсутствующему ключу словаря через `dict[key]` вызывает `KeyError`. Без обработки исключение дойдёт до веб-слоя как 500.
- Risk: Неконтролируемые 500-ошибки, ухудшение UX, невозможность корректной диагностики клиентских ошибок.
- Verification: Отправить POST `/api/reviews` с пустым JSON `{}` и убедиться, что возникает необработанная ошибка сервера (ожидаемо 500 из-за `KeyError`).

2) Неограниченный размер diff (ресурсные риски и ошибки LLM)

- File: app/review_service.py
- Line: Неизвестно / требует уточнения
- Problem: Весь входной diff инлайнится в промпт без ограничений/усечения.
- Evidence:
  ```diff
  +    def review(self, diff: str) -> dict[str, str]:
  +        prompt = f"Review this pull request and find problems:\n{diff}"
  +        answer = self.llm.generate(prompt)
  +        return {"comment": answer}
  ```
- Basis / Rule: Общий принцип надёжности — отсутствие ограничений на размер входа может привести к перерасходу ресурсов, превышению лимитов провайдера LLM и таймаутам.
- Risk: Ошибки/исключения LLM, задержки, рост стоимости, падения сервиса при больших диффах.
- Verification: Передать большой diff (многострочный текст) и наблюдать рост времени/ошибки от LLM или сервиса.

3) Риск prompt injection (инструкции внутри diff)

- File: app/review_service.py
- Line: Неизвестно / требует уточнения
- Problem: Пользовательский diff вставляется напрямую в текст промпта; инструкции/подсказки внутри diff могут повлиять на поведение модели.
- Evidence:
  ```diff
  +        prompt = f"Review this pull request and find problems:\n{diff}"
  +        answer = self.llm.generate(prompt)
  ```
- Basis / Rule: Общепризнанный принцип безопасности LLM — недоверенные данные нельзя смешивать с инструкциями без изоляции/структурирования, иначе возможна prompt injection.
- Risk: Модель игнорирует системные инструкции/цели, выдаёт некорректные/манипулируемые ответы.
- Verification: В diff включить строки с инструкциями (например, «ignore previous instructions») и проверить, что ответ модели следует им.

4) Нет обработки исключений при вызове LLM

- File: app/review_service.py; app/api.py
- Line: Неизвестно / требует уточнения
- Problem: Исключения при `self.llm.generate(...)` не обрабатываются и приведут к 500.
- Evidence:
  ```diff
  +        answer = self.llm.generate(prompt)
  ```
  и возврат значения без try/except в `create_review`.
- Basis / Rule: В Python необработанные исключения поднимаются вверх по стеку; в веб-ручке это приводит к 500.
- Risk: Нестабильность API, непредсказуемые 500 без понятных сообщений, трудности диагностики.
- Verification: Смоделировать исключение в `llm.generate` (например, тестовым двойником, кидающим `RuntimeError`) и наблюдать 500 от `/api/reviews`.

Правила для context.md

Сохрани существующий шаблон context.md

Заполняй только существующие поля и секции

Факт можно записать как подтверждённый только если он прямо следует из разрешённых источников

Если информация является разумным предположением, явно пометь её как допущение

Если информации недостаточно, укажи "Неизвестно / требует уточнения"

Не превращай найденные во время code review потенциальные проблемы в подтверждённые факты о всей системе

Не придумывай отсутствующий продуктовый или технический контекст


Правила для problem.md

Сохрани существующий шаблон problem.md

Заполняй только существующие поля и таблицы

Не придумывай

- пользователей без достаточного основания
- бизнес-процессы без достаточного основания
- текущие числовые значения метрик
- результаты тестов, которые не выполнялись
- результаты HTTP-запросов, которые не выполнялись
- требования проекта, которых нет в разрешённых источниках

Если текущее значение метрики неизвестно, укажи способ будущего измерения вместо выдуманного результата

Например, если запрос с пустым JSON фактически не выполнялся, не пиши

"Ручной вызов с {} возвращает 500"

Вместо этого можно написать

"Способ замера: отправить POST /api/reviews с пустым JSON и зафиксировать HTTP status"


Review Output Format

Для каждого подтверждённого замечания второго запуска используй следующую структуру

<краткое название проблемы>

- File: <путь к файлу>
- Line: <номер строки или диапазон строк>
- Problem: <что именно не так>
- Evidence: <конкретный фрагмент diff>
- Basis / Rule: <на каком основании это считается проблемой>
- Risk: <к чему может привести проблема>
- Verification: <как человек может проверить это утверждение>

Verification описывает способ проверки

Не утверждай, что проверка была выполнена, если она фактически не выполнялась

Workflow

Работай по следующему порядку

Этап 1 — чтение

1. Прочитай TRAINING_PR.diff
2. Прочитай problem.md
3. Прочитай context.md
4. Прочитай prompts.md
5. На этом этапе не изменяй файлы

Этап 2 — ревью

1. Найди кандидатов на проблемы
2. Для каждого кандидата найди Evidence
3. Для каждого кандидата найди допустимый Basis / Rule
4. Проверь, следует ли вывод непосредственно из доступных данных
5. Отбрось неподтверждённые кандидаты
6. Оцени существенность оставшихся кандидатов
7. Выбери не более 5 наиболее существенных

Этап 3 — планирование изменений

1. Определи, какие существующие поля относятся к текущему запуску P1-02
2. Определи, какие поля problem.md и context.md можно заполнить без предположений
3. Определи, какие поля должны остаться пустыми или получить отметку "Неизвестно / требует уточнения"
4. Убедись, что план не изменяет P1-01
5. Убедись, что план не затрагивает Peer review

Этап 4 — редактирование

1. Точечно внеси необходимые изменения в context.md
2. Точечно внеси необходимые изменения в problem.md
3. Заполни существующую строку P1-02 в prompts.md
4. Заполни существующий раздел Master Prompt v1
5. Сохрани результат второго ревью как P1-02
6. Не изменяй остальные части файлов без необходимости

Этап 5 — финальная проверка

1. Повторно прочитай каждый изменённый файл
2. Проверь, что существующая структура сохранена
3. Проверь, что P1-01 не изменён
4. Проверь, что Peer review не изменён
5. Проверь, что P1-02 заполнен
6. Проверь, что Master Prompt v1 заполнен
7. Проверь, что нет дублирующихся секций
8. Проверь, что нет придуманных результатов тестов
9. Проверь, что нет придуманных значений метрик
10. Проверь, что не были изменены запрещённые файлы


Verification

Для каждого кандидата на проблему проверь

- есть ли конкретное Evidence в TRAINING_PR.diff
- есть ли допустимый Basis / Rule
- следует ли утверждение непосредственно из Evidence
- не требует ли утверждение отсутствующего контекста
- не выдаётся ли предположение за подтверждённый факт

Допустимым Basis / Rule может быть

- семантика Python
- поведение стандартной библиотеки Python
- явно предоставленное правило из Context Pack
- общий принцип безопасности или надёжности, если его применение напрямую следует из изменённого кода и не требует отсутствующего контекста

Если Evidence недостаточно или Basis / Rule требует отсутствующего контекста, отбрось кандидата

Не придумывай название, номер или содержание правила проекта


Pre-write Check

Перед записью новой информации в файл проверь

1. В какой конкретно существующий раздел должна попасть эта информация
2. Существует ли этот раздел уже
3. Относится ли информация к текущему запуску P1-02
4. Не изменяет ли она P1-01
5. Есть ли разрешённый источник для утверждения
6. Не выдаётся ли предполагаемый результат проверки за выполненную проверку
7. Не придумывается ли значение метрики
8. Не удаляется ли существующая информация
9. Не создаётся ли новая структура вместо существующей

Если информация не проходит эту проверку, не записывай её как подтверждённый факт


Stop

Не останавливай анализ после нахождения первых 5 кандидатов

Сначала проверь весь доступный TRAINING_PR.diff

После этого выбери не более 5 наиболее существенных подтверждённых проблем

Заверши работу только после редактирования разрешённых файлов и финальной проверки результата


DoD

Работа считается завершённой, если

- проанализирован весь TRAINING_PR.diff
- выбрано не более 5 наиболее существенных подтверждённых проблем
- для каждой проблемы есть Evidence
- для каждой проблемы есть допустимый Basis / Rule
- для каждой проблемы есть способ Verification
- P1-01 остался без изменений
- строка P1-02 заполненa
- Master Prompt v1 заполнен в существующем разделе
- существующие таблицы и структура файлов сохранены
- Peer review не заполнен агентом
- в problem.md и context.md заполнены только поля, для которых достаточно информации
- неизвестные данные не были придуманы
- результаты невыполненных тестов не выдаются за реальные
- значения неизмеренных метрик не придуманы
- не использованы запрещённые файлы, источники или действия

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Да (в P1-01 указаны файл и номера строк) | Да (File указан; Line — «Неизвестно / требует уточнения», см. Evidence) | С master prompt привязка стала аккуратнее: ссылки на файлы и цитаты diff без недостоверных номеров строк |
| Вывод подтверждён diff или правилом | Частично (ряд выводов основаны на предположениях и внешнем контексте) | Да | В P1-02 оставлены только выводы, непосредственно следующие из diff и семантики Python |
| Соблюдены границы AI | Частично (в P1-01 есть предположения про auth/квоты/структуру ответа) | Да | Master prompt ограничил выводы рамками доступных источников |
| Есть воспроизводимая проверка | Частично (проверки описаны не везде) | Да (описан способ Verification) | Во втором запуске для каждого пункта указан воспроизводимый способ проверки. Также зафиксирован недостаток мастер-промпта: инструкция «Не изменяй строку P1-01» защищает историю, но мешает заполнению аналитических колонок; в будущем формулировка должна различать неизменяемый исторический результат и разрешённую последующую оценку. |
