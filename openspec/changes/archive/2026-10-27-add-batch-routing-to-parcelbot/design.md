# Design

## Context

Проект ParcelBot (practices/practice_04/demo): бизнес‑логика маршрутизации для одной посылки реализована в `service.choose_belt(weight, priority=False)` (см. строки 11–17 в practices/practice_04/demo/service.py). MCP‑сервер (`mcp_server.py`) предоставляет инструмент `route_parcel`, который делегирует вызов в `choose_belt` без дублирования правил (строки 10–24 в practices/practice_04/demo/mcp_server.py). Требования практики и правила для агентов зафиксированы в `AGENTS.md`.

## Goals / Non-Goals

**Goals:**
- Добавить новый MCP‑инструмент `route_parcels` для пакетной маршрутизации списков посылок, используя существующую бизнес‑логику `choose_belt`
- Обеспечить изоляцию ошибок на уровне элемента (ошибка одной посылки не прерывает обработку списка)
- Сохранить обратную совместимость существующих API: `choose_belt` и `route_parcel` не меняют поведение

**Non-Goals:**
- Изменение публичного поведения `choose_belt`/`route_parcel`
- Добавление внешних зависимостей, кроме уже используемого FastMCP

## Decisions

- Реализация `route_parcels` в `mcp_server.py` рядом с `route_parcel`, с итерацией по входному списку и делегированием в `choose_belt` для каждого элемента
- Формат результата (per-item):
  - Успех: {"belt": "standard"|"express"|"heavy"}
  - Ошибка (доменная): {"error": "текст ошибки"}
  - В каждом элементе ровно одно из полей; список результатов той же длины и порядке, что `parcels`
- Валидация ввода и границы FastMCP:
  - Параметр инструмента: именованный `parcels` — список объектов; каждый объект имеет `weight: number` (обязателен) и `priority: bool` (необязателен; по умолчанию False)
  - Per-item доменная ошибка: для числового `weight` ≤ 0 вернуть {"error": "weight must be positive"}
  - Предвалидация FastMCP: нечисловой `weight`, отсутствующий `weight`, `priority=null`/неверный тип могут быть отклонены до вызова функции и привести к `is_error=true` на всём вызове. В таких случаях per-item обработка не выполняется. Клиентам следует соблюдать входной контракт; per-item ошибки применяются после успешной валидации формы
- Тестовые кейсы: успех, смешанные приоритеты, пустой список, частичные ошибки

Альтернативы:
- Прерывать обработку при первой ошибке — отклонено: не соответствует требованию «ошибки отдельных элементов не прерывают обработку»
- Возвращать смешанный список строк/ошибок — отклонено: предпочтительнее структурированный результат

## Risks / Trade-offs

- Риск несовместимости формата результата для клиентов: смягчается явной спецификацией и тестами
- Потенциальные большие списки посылок — линейная обработка, без параллелизма; приемлемо для учебного проекта

## Migration Plan

- Добавить `route_parcels` и новые тесты; существующие тесты остаются без изменений
- Проверить `make test` в demo и MCP_DEMO при необходимости

## Open Questions

- Нужна ли стандартизация сообщений для иных доменных ошибок помимо `weight ≤ 0`? (например, предел размера списка, max items)
